## 0. 共通方針

| # | 方針 |
|---|---|
| C-1 | **文字コードは取込元ごとに異なる**。MUFG/UFJ-VISA は Shift_JIS、新生銀行は **UTF-8（BOM付き）**。取込時に UTF-8 へ統一（`iconv-lite` 等）し、**BOM・改行（CRLF）を吸収**。`source_type` ごとにエンコーディングを定義する（§各節の冒頭） |
| C-2 | 金額は **カンマ除去＋全角→半角**して整数（円）化。空文字は0扱い |
| C-3 | 日付は複数形式を ISO8601 へ：`YYYY/M/D`・`YYYY/MM/DD`（ゼロ埋め）・`YYYY年M月D日` を両対応 |
| C-4 | 全角英数字・記号（`１`, `，`, `＊`, `Ａ-Ｚ`）は摘要・数値とも**半角正規化**（表示用原文は `raw_payload` に保持） |
| C-5 | `source_type` と `account_ref`（口座/カード識別子）を取込バッチに付与。`account_ref` は `sub_accounts.linked_account_ref` と対応。**口座マスタ（F-IMP-8）**: 取込口座は linked_account_ref を持つ補助科目として登録され、`sub_accounts.import_source_type` に取込形式を記憶する。取込フォームは**この口座マスタからの選択式**（account_ref のフリーテキスト手入力は廃止＝タイポによる別口座誤登録を防止）で、選択口座の source_type を自動設定。未登録の口座は取込時に自動登録される（旧データは import_source_type=null＝形式は手動補正）。 |
| C-6 | **冪等性（出現インデックス方式）**: `dedup_hash = hash(取引日, 金額, 方向, 摘要, 出現インデックス)`。同一(取引日,金額,方向,摘要)が**同一取込内**に複数あれば 0,1,2… の連番で識別する。UNIQUE(account_ref, dedup_hash) で再取込スキップ（[data-model] F-IMP-4）。**残高列・支払回数には依存しない**（欠落/同一値での衝突＝取りこぼしを避ける。残高/回数は `raw_payload` に温存し突合に利用）。同一取込内の同日同額同摘要の別取引は別 hash で全件保持、同一データ再取込はグループ順が安定なので冪等。スキップした重複は総件数＋**明細サンプル（日付/金額/摘要・先頭50件）を取込結果に返す**（黙って落とさない）。<br>**既知の限界（要件のトレードオフ）**: 出現インデックスは取込単位でリセットするため「再取込は冪等」（同一ファイルの二重計上ゼロ）を優先する。その帰結として、**別取込（非重複期間の別ファイル）に現れた同日同額同摘要の“新規の別取引”は、内容だけでは再取込と区別できず**スキップされる（重複一覧に現れる＝黙って落ちない。別取引なら手入力で追加）。残高/回数を鍵に使う旧方式は逆に取りこぼしが多かったため、再取込冪等を優先しこの限界を許容する。強制取込/復元を伴う本格的な重複候補レビューは将来拡張（§7）。<br>**移行**: 旧スキーム（残高/回数依存・区切り子なし）で取込済みの行は、deploy 時の `migrateUserDb` で新方式へ**再ハッシュ（冪等バックフィル）**し、再取込の二重計上を防ぐ。 |
| C-7 | 原CSV行は `raw_transactions.raw_payload`（JSON）に保持（監査・電子帳簿保存） |
| C-8 | **会計期間ゲート**: 取込対象は**開いている会計期間（`fiscal_years.status='open'`）の `[start_date, end_date]`** のみ（取引日で判定）。**翌期分は `raw_transactions` に入れない**（保留しない＝ただ無視）。年度繰越で翌期が open になってから取り込む。範囲外で除外した件数と end_date を取込結果に表示（黙って落とさない）。同じゲートは**仕訳化（draft 生成）にも効く** — 繰越を跨いで残った過年度明細は仕訳化できない（単発＝拒否／バッチ＝件数を返してスキップ）。詳細 [acquisition-skill-spec §5](./acquisition-skill-spec.md) |
| C-9 | **部分取込・エラーリカバリ**: パースは**行単位 try-catch**で、取引行と判定できたが日付/金額を解釈できない行は退避し、正常行は取り込む（1行壊れても全体を止めない）。`import_batches.status` を **done/partial/failed** で記録（done=全件成功 / partial=一部失敗だが取込あり / failed=失敗ありで取込0）、`error_count` と `error_sample`（先頭N件の `[{rowNo,raw,message}]` JSON）を保存。取込結果に件数＋行単位内訳を返し UI で表示（黙って落とさない）。見出し・注記・登録番号など「取引行でない行」はエラーにせずスキップ。 |
| C-11 | **汎用列マッピング（ユーザー定義フォーマット）**: 組込3形式（§1〜§3）に無い銀行/カードCSVを、**コード変更なしで列マッピング設定だけ**で取り込めるようにする（[roadmap Phase3「対応フォーマット拡充」]）。設定は `import_formats` テーブルに保存し、`source_type` 文字列空間に **`format:{id}`** として組込形式と共存（口座マスタ・dispatch は組込/ユーザー定義を同じ選択軸で扱う）。対象は**1行=1取引型**（＋スキップ可能なヘッダ/空行）。複数行種別が混在するカード型（確定/未確定・注記行・登録番号行の分類＝§2）は組込 `card_mufg_visa` が担い、汎用パーサの対象外。詳細仕様は §8。 |
| C-10 | **残高同期・突合**: 銀行 CSV の差引残高/残高を `raw_transactions.balance` に保持（残高が壊れていても取引行は失敗させない＝null 化）。口座(`account_ref`)別に**残高チェーン**で連続性を検証する：各行の取引後残高(post=残高)を「供給」、取引前残高(pre=残高−符号付き金額〔入金:+ / 出金:−〕)を「需要」とし、各行の pre を別行の post に結びつける。結べない行はその直前に**未取込の取引（取りこぼし）**がある疑い（口座期首の1件のみ正当、それ以上を差異として報告）。**取込順・CSVの並び順（昇順/逆時系列）・複数バッチ分割に依存しない**（残高そのものでチェーンを辿るため正常データを誤検知しない）。dedup の残余（同日同額同摘要の別取引が再取込と区別できずスキップ）も残高不連続として独立検知する安全網。残高列を持たない明細（カード等は `balance=null`）は対象外。限界: 区間の欠落取引の符号付き合計が0（+X と −X が両方未取込）は残高が連続するため検知不可。 |

## 1. 三菱UFJ銀行 普通預金（`source_type = bank_ufj`、Shift_JIS）

### 1.1 ヘッダ・例
```
"日付","摘要","摘要内容","支払い金額","預かり金額","差引残高"
"2026/5/11","クレジット","","193,945","","37,717,278"
```

### 1.2 列マッピング → `raw_transactions`
| CSV列 | 変換 | raw_transactions |
|---|---|---|
| 日付 | `YYYY/M/D` → ISO | `txn_date` |
| 摘要 | そのまま | `description`（主） |
| 摘要内容 | あれば description に連結 | `description`（補） |
| 支払い金額 | カンマ除去・整数 | 値ありなら `direction='out'`, `amount` |
| 預かり金額 | カンマ除去・整数 | 値ありなら `direction='in'`, `amount` |
| 差引残高 | 整数 | 保持（dedup補助・突合用。残高自体は導出なので正本にしない） |

- **direction判定**: 支払い金額 > 0 → `out`、預かり金額 > 0 → `in`（両方空はスキップ）。
- 差引残高は `raw_payload` に温存（残高同期・突合用）。`dedup_hash` には用いない（出現インデックス方式・C-6）。
- 例の「クレジット 193,945 出金」= カード引落 → 仕訳候補 `借) 未払金(カード) / 貸) 普通預金`（自動仕訳ルール側、§5）。

## 2. 三菱UFJ-VISA カード利用明細（`source_type = card_mufg_visa`、Shift_JIS）

最もクセが強い。**取引行・見出し行・注記行が混在**する。

### 2.1 ヘッダ・例（抜粋）
```
"確定情報","お支払日","ご利用店名（…）","ご利用日","支払回数","何回目","ご利用金額（円）","現地通貨額・通貨名称・換算レート"
"","","【林　雄一郎　様】","","","","",""                                  ← 見出し（カード名義）
"確定","2026年6月10日","ＥＴＣ　京浜川崎　－港北","2026年4月1日","　１","","210","車種：普通車"
"確定","2026年6月10日","CLAUDE.AI SUBSCRIPTION / ANTHROPIC.COM","2026年5月5日","　１","","35,945","　２２０．００　ドル　…１６３．３８７"
"","","","","","","","内海外利用事務手数料　　１，３３２円"        ← 注記（直前取引に付随）
"","","","","","","","（内消費税　　　１２１円）"                  ← 注記
"","","【消費税課税対象合計】","","","","","１０％対象　１，５５２円　内消費税　１４１円"  ← 集計見出し
"","","","","","","","登録番号　Ｔ５０１０００１００８８４６"        ← カード会社の適格請求書登録番号
```

### 2.2 行の分類（パース前処理）
| 種別 | 判定 | 扱い |
|---|---|---|
| **取引行** | `確定情報` が非空（確定/未確定）かつ `ご利用日` が**非空** | `raw_transactions` 化（日付/金額の解釈失敗は退避＝C-9。日付の解釈可否で取引行を判定しない＝silent drop 防止） |
| 見出し行 | `店名` が `【…】` で始まる／名義行 | スキップ |
| 注記行 | キー列（確定情報・日付・金額）が空で末列のみ値 | **直前の取引行に付随情報として連結**（海外手数料・内消費税等）。MVPは `raw_payload` に保持しスキップ可 |
| 登録番号行 | 末列が `登録番号 T…` | カード会社の**適格請求書登録番号**として記録（インボイス。取引先＝カード会社） |

### 2.3 列マッピング（取引行）→ `raw_transactions`
| CSV列 | 変換 | raw_transactions |
|---|---|---|
| 確定情報 | 確定/未確定 | `raw_payload`（未確定の扱いは §2.4） |
| お支払日 | `YYYY年M月D日` → ISO | 保持（未払金の決済予定日） |
| ご利用店名 | 全角正規化（原文も保持） | `description` |
| **ご利用日** | `YYYY年M月D日` → ISO | **`txn_date`（会計上の発生日はこれ）** |
| 支払回数 | 全角→半角整数（`　１`→1） | 保持（分割払い） |
| 何回目 | 同上 | 保持 |
| ご利用金額（円） | カンマ除去・整数 | `amount`、`direction='out'` |
| 現地通貨額… | 海外取引の補足 | `raw_payload`（為替・通貨） |

- **取引日 = ご利用日**（発生主義）。お支払日は未払金の決済タイミング。
- カード利用は原則 `direction='out'`。仕訳候補 `借) 経費科目 / 貸) 未払金(三菱UFJ-VISA…)`（§5）。
- `dedup_hash` は **出現インデックス方式**（C-6）。カードは連番（何回目）が無いため、従来の `何回目` 依存では同日同店同額の一回払いが衝突して片方落ちていた既知バグを、(ご利用日, 金額, 方向, 店名) グループ内の出現インデックスで識別して解消。支払回数/何回目は `raw_payload` に温存。

### 2.4 エッジケース
- **未確定行**: 取り込むと後で金額変動の可能性。MVPは「確定のみ取込」を既定とし、未確定は除外（または draft 扱いで取込し確定時に洗い替え）。要確認。
- **海外利用**: 取引本体＋「内海外利用事務手数料」「内消費税」の注記。手数料を別計上するかは運用方針（MVPは合計額で1取引＋注記保持）。
- **明細書発行手数料**: 通常の課税仕入（内消費税あり）。取引行として計上。
- **全角数値**: 注記の金額（`１，３３２円`）も全角→半角で抽出可能にしておく。
- **適格登録番号 `T…`**: カード会社発行手数料等のインボイス対応。取引先（カード会社）の `counterparties.invoice_reg_no` に記録。

## 3. 新生銀行 普通預金（`source_type = bank_shinsei`、UTF-8 BOM付き）

UFJ銀行（§1）と同型の入出金明細だが、**エンコーディングが UTF-8（BOM付き）**で、出金/入金が別カラム。

### 3.1 ヘッダ・例
```
"取引日","摘要","出金金額","入金金額","残高","メモ"
"2026/05/01","地方税","35","","2916330",""
"2026/05/01","国税","109","","2916365",""
"2026/05/01","税引前利息","","718","2916474",""
"2026/04/01","税引前利息","","742","2915906",""
```

### 3.2 列マッピング → `raw_transactions`
| CSV列 | 変換 | raw_transactions |
|---|---|---|
| 取引日 | `YYYY/MM/DD`（ゼロ埋め）→ ISO | `txn_date` |
| 摘要 | 全角正規化 | `description` |
| 出金金額 | カンマ除去・整数 | 値ありなら `direction='out'`, `amount` |
| 入金金額 | カンマ除去・整数 | 値ありなら `direction='in'`, `amount` |
| 残高 | 整数 | 保持（dedup補助・突合用。正本にしない） |
| メモ | あれば description へ連結 | `raw_payload`（補） |

- **direction判定**: 出金金額 > 0 → `out`、入金金額 > 0 → `in`（両方空はスキップ）。
- **BOM吸収必須**: 先頭列名が `﻿取引日` になりやすい。デコード後に BOM をstripしてからヘッダ照合する。
- `dedup_hash` は出現インデックス方式（C-6・同MUFG銀行§1）。残高は `raw_payload` に温存し dedup には用いない。
- **受取利息と源泉の論点（仕訳化§5の注意点）**: サンプルの `税引前利息`＝受取利息、**同日にセットで出る** `国税`・`地方税` ＝その利息に対する源泉徴収（国税=所得税・復興特別所得税15.315%、地方税=道府県民税利子割5%）。利子割は2016年に**法人**は廃止されたが**個人は存続**するため、個人の預金利息は 国税＋地方税の約20.315% が源泉される（サンプル: 国税109＋地方税35＝144 ≒ 718×20.3%）。
  - ⚠️ **新生CSVの「国税」は消費税ではなく利息の所得税源泉**。`税引前利息` と必ず同日・対になっている。消費税の納付はこの口座でなく **UFJ側（摘要 `税金 シヨウヒゼイ`）で連携**される（§5・accounting §6）。
  - 仕訳: 利息本体 → **`借) 普通預金 / 貸) 事業主借`**、源泉（国税・地方税）→ **`借) 事業主貸 / 貸) 普通預金`**。個人の預金利息は事業所得でなく利子所得のため、事業用口座でも**損益に含めない**（法人と違い受取利息勘定は使わない）。利用者の実運用と一致。

## 4. EC（Amazon/楽天）商品明細の取得と取込

商品ごとの明細が要るが、Amazonは公式CSVが**バッチで遅く月次運用に不適**、楽天は**CSV出力不可**。
→ **取得手段を本体から切り離し**、間に**正規化中間フォーマット（§4.2）**を1枚かませて疎結合にする（[PRD F-IMP-6]）。

```
[取得層（差し替え可）] → EC明細 正規化フォーマット(§4.2) → importer → raw_transactions(EC) → draft仕訳(§5)
   ├ AIエージェント・スキル + /schedule 月1   ← 現在の本命（Claude Code → 将来ローカルLLM/他AI）
   ├ 注文確認メールの解析                       ← 代替（ToS的に堅い）
   ├ Amazon公式データリクエストCSV               ← 予備（遅延大）
   └ 手動入力                                   ← 常時フォールバック
```

### 4.1 取得層と方針

| 取得層 | 状況・方針 |
|---|---|
| **AIスキル（Claude Code等）** | **本命**。LLMがページを意味抽出するためDOM変更に強い。月1低頻度なのでLLMコストは誤差。本人セッション・ヘッドフルで2FAはその場対応。**製品配布もスキル配布**（対象＝エンジニアでClaude Code等を保有）。本体はスキルを内蔵しない（[PRD F-IMP-5/R-1]） |
| 注文確認メール解析 | Amazon/楽天とも品名・数量・金額入りメールを送る。サイト改変の影響を受けず、製品配布でも現実的な代替 |
| Amazon公式CSV | `Retail.OrderHistory` 等。商品明細は取れるがリクエスト→メール配信でバッチ遅延、月次運用に不向き→予備 |
| 手動入力 | 確実。混在注文だけ手動でも実用的 |

- **金額の正確性担保（必須）**: LLM抽出を鵜呑みにしない。取得層は**生証跡（HTML/スクショ/メール原文）を保存**し、取込結果は必ず **draft 仕訳**として人が確認画面で承認（§5・status）。確定申告データなので妥協しない。
- 取得層がどれでも下流（importer・仕訳・帳簿）は不変。本体が保証するのは**中間フォーマットの受け口＋importer**だけ。
- **全取込が「取得 → 正規化ファイル → import」に統一**: 銀行/カードは既にCSVが出力可（人が手動DL→§1〜§3形式）、ECは取得スキルが正規化CSVを合成（§4.2形式）。違いは「正規化ファイルを誰が作るか」だけ。
- **運用モデル（無人cron不可）**: `/schedule`＝リマインドのみ／人が起動／ヘッドフル／**ログイン・2FA・CAPTCHAは人**（認証情報はAIに渡さない）／抽出はAI／draft承認は人。詳細は [acquisition-skill-spec.md](./acquisition-skill-spec.md)。

### 4.2 EC明細 正規化中間フォーマット（取得層 → importer の契約）

取得層が出力する1注文＝複数明細行のJSON/CSV。最低限の必須項目：

| フィールド | 必須 | 用途 |
|---|---|---|
| `source` | ○ | `amazon` / `rakuten` / 店舗名 |
| `order_id` | ○ | 注文番号（冪等性・突合キー） |
| `order_date` | ○ | 注文日（ISO。発生日） |
| `order_total` | ○ | 注文合計＝**ご請求額（税込）**。`Σ line_amount + shipping − points_used` と一致。**カード明細との突合キー＝日付＋金額**（§4.3） |
| `shipping` | – | 送料・手数料（注文レベル・非負円整数）→ 借)雑費（§4.3 方式B） |
| `points_used` | – | ポイント利用（注文レベル）→ 貸)事業主借（個人ポイントで肩代わり） |
| `points_earned` | – | ポイント付与（注文レベル・任意・請求額に無影響）→ 借)事業主貸・貸)雑収入 |
| `line_no` | ○ | 明細連番 |
| `item_name` | ○ | 品名（`description`・分類学習キー） |
| `quantity` | ○ | 数量 |
| `line_amount` | ○ | 明細金額（税込・**その商品の値引き反映後の純額**＝適格請求書PDFの商品別小計。経理は税込経理。割引は別フィールドを持たず純額化） |
| `proposed_account` | – | **仕訳候補**: AIが分類した科目名/コード（旧 `category_hint` を格上げ・[acquisition-skill-spec §6/§7]）。本体が `account_id` へ検証 |
| `treatment` | – | `expense`=経費 / `owner_draw`=事業主貸 / `unresolved`=未確定 |
| `reason` | – | 分類理由（承認UI表示＋監査）。空可だが推奨 |
| `confidence` | – | high / medium / low |
| `policy_ref` | – | 適用した分類ポリシーの版/ルールID |
| `payment_hint` | – | 決済元（どのカード等）。突合の補助 |
| `evidence_ref` | ○ | 生証跡（HTML/スクショ/メール）のパス・ID（監査・電子帳簿保存） |
| `currency` | – | 既定 JPY |

- 本表は概念フィールド。**実APIのJSONキーは camelCase**（`orderId`/`lineNo`/`proposedAccount`…）＝[ec-import-api.md §0]が正。
- `dedup_hash` は `source + order_id + line_no`（再取得スキップ）。
- importer はこれを `raw_transactions`（EC）へ落とし、§4.3 のクリアリング勘定モデルで draft 仕訳化。**借方科目＝仕訳候補（`proposed_account`、AI分類）／貸方＝未払金（チャネル別補助）**。`proposed_account` は勘定科目マスタで `account_id` に検証し、未知/曖昧は **未確定勘定＋flag**。
- **分類の担い手**: EC（スキルトラック）は **AIが分類**（確定履歴 ▶ md ポリシー）。本体の `auto_journal_rules`/institution は**手動CSV（UIトラック）専用**で、EC明細には適用しない（[acquisition-skill-spec §7.1]）。仕訳候補も **全件 draft** で人が承認。

### 4.3 ★ 未払金クリアリング勘定の連鎖（二重計上の回避）

EC（Amazon/楽天）の購入は**カード明細にも決済として現れる**（`ＡＭＡＺＯＮ．ＣＯ．ＪＰ`, 楽天関連）。
費用は**最上流（EC商品明細）で一度だけ**計上し、下流（カード→銀行）は**未払金の付替え／決済**にする。
これにより二重計上を防ぐ。`未払金` は**チャネル別の補助科目（Amazon/楽天/各カード）＝クリアリング勘定**として持つ（参照データの未払金補助科目と一致）。

仕訳の連鎖（Amazon購入 → カード → 銀行）:
```
① EC商品明細（最上流で費用確定。品目ごとに経費/事業主貸を判定。line_amount=値引き反映後の純額）
   借) 消耗品費 等        / 貸) 未払金(Amazon)      ← 経費にするもの
   借) 事業主貸           / 貸) 未払金(Amazon)      ← 経費にしないもの
①' 注文レベル調整（方式B＝未払金を“ご請求額”にそろえる。1明細1仕訳で本体が機械生成）
   借) 雑費(送料)         / 貸) 未払金(Amazon)      ← shipping（未払金を増やす）
   借) 未払金(Amazon)     / 貸) 事業主借            ← points_used（個人ポイントで肩代わり＝未払金を減らす）
   借) 事業主貸           / 貸) 雑収入              ← points_earned（任意・未払金に無影響）
② カード明細（費用でなく“付替え”）
   借) 未払金(Amazon)     / 貸) 未払金(UFJ-VISA)
③ 銀行引落（現金決済）
   借) 未払金(UFJ-VISA)   / 貸) 普通預金(UFJ)
```
→ ①+①' の `未払金(Amazon)` 純額（貸−借）＝**ご請求額**（カード明細と一致）。ネットで `費用/事業主貸/雑費 − 雑収入 ÷ 普通預金`、各未払金は0に相殺。
- **割引**は §4.2 のとおり `line_amount` を純額化（按分しない）。**送料/ポイント**だけ注文レベル調整で持つ。
- 突合: `Σ line_amount + shipping − points_used = order_total`。ズレは抽出ミス＝warning（黙って合わせ込まない）。

**カード1行の仕訳は上流のEC連携の有無で分岐する:**
| 状況 | カード明細「AMAZON」行の仕訳 |
|---|---|
| Amazon連携あり | `借) 未払金(Amazon) / 貸) 未払金(該当カード)`（付替え。費用にしない） |
| Amazon連携なし | `借) 経費科目 / 貸) 未払金(該当カード)`（カード行が費用そのもの） |

**取込元をまたぐ突合（名寄せ）が必要:**
- EC商品明細の合計 ↔ カード明細の同額行を、**突合キー＝日付＋金額**（必要なら店名）で対応づける。
- 突合できたカード行は「付替え」、できなければ「費用」と判定。
- `raw_transactions` に**決済リンク**（下流行→上流行の参照）を持たせる（[data-model] への追補事項, §7）。

## 5. 取込後の仕訳化（自動仕訳との接続）

**2トラックで分類の担い手が異なる**（[acquisition-skill-spec §7.1]）:
- **UIトラック（手動CSV）**: [data-model §2.9] の `auto_journal_rules` → `mapping_history` → institution → 未確定 で `raw_transactions` → 仕訳候補（draft）を生成。**銀行/カードの手動CSV取込（§1〜§3）はこのトラック**。
- **スキルトラック（連携取込）**: **AIが分類**（確定履歴 ▶ md ポリシー。[acquisition-skill-spec §7.2]）。`auto_journal_rules`/institution は**関与しない**。
  - **EC**（Amazon/楽天・§4.2）: 借方＝AI科目、貸方＝未払金チャネル（§4.3）。[ec-import-api.md]。
  - **銀行**（`bank_ufj`・[bank-import-api.md]）: **普通預金が一脚**で direction が貸借を決め、相手科目をAIが分類（摘要→科目・[classification-policy.md §5]）。冪等は出現インデックス方式で**UIトラックと互換**（同一口座を両トラックで二重計上しない）。利息/源泉/消費税は md 明記でAIが確信提案（institution と同じ正解を、ルールエンジンでなくAIが出す）。
  - 確定実績は `mapping_history` へ書き戻し、次回のAI提案に優先反映（[data-model §2.9.2]）。

下表はパターン別の候補仕訳（いずれも **draft**・人が承認）:

| パターン | 候補仕訳 |
|---|---|
| EC商品明細（amazon/rakuten） | `借) 経費科目 or 事業主貸（品目ごとに**AIが分類**: 消耗品費/新聞図書費/事業主貸 等。[acquisition-skill-spec §7]） / 貸) 未払金(Amazon/楽天)` |
| カード利用・**EC突合あり**（§4.3） | `借) 未払金(Amazon/楽天) / 貸) 未払金(該当カード)`（付替え。費用にしない） |
| カード利用・**EC突合なし**（card_mufg_visa, out） | `借) 経費科目（ルール推測） / 貸) 未払金(該当カード補助科目)` |
| 銀行・カード引落（bank_ufj, out, 摘要=クレジット等） | `借) 未払金(カード) / 貸) 普通預金` |
| 銀行入金（bank_ufj / bank_shinsei, in） | `借) 普通預金 / 貸) 売上 or 売掛金回収（ルール推測）` |
| **受取利息**（bank_shinsei, in, 摘要=税引前利息） | `借) 普通預金 / 貸) 事業主借`（事業所得に含めない。§3.2） |
| **利息の源泉**（bank_shinsei, out, 摘要=国税/地方税。**税引前利息と同日**） | `借) 事業主貸 / 貸) 普通預金`（源泉分も損益外。§3.2） |
| **消費税の納付**（bank_ufj, out, 摘要に `シヨウヒゼイ`/税金） | `借) 租税公課 / 貸) 普通預金`（税込経理。accounting §6） |
| 公共料金・通信（東京電力/IIJ/ラクテンブロードバンド等） | 水道光熱費・通信費へ（mapping_history学習で精度向上） |

- **未払金はチャネル別補助科目（クリアリング勘定）**で持つ。最上流で費用、下流は付替え（§4.3）。
- カード行は**EC突合の有無で費用 or 付替えに分岐**（§4.3）。突合キー＝日付＋金額。
- **摘要「国税/地方税」はソースで意味が異なる**: 新生（bank_shinsei）で税引前利息と同日のものは**利息源泉＝事業主貸**。消費税納付はUFJ側の摘要 `税金 シヨウヒゼイ` で来る（**租税公課**）。源泉と納付を取り違えない。
- **金融機関特有の既定自動仕訳（実装済み・`journal/institutionRules`）**: 上表の **受取利息→事業主借** / **利息源泉(同日の税引前利息あり)→事業主貸** / **消費税納付(シヨウヒゼイ)→租税公課** は、`source_type`・方向・摘要・**同日利息の有無**から相手科目を決める**既定**として組込済み。優先順位は **ユーザールール(`auto_journal_rules`) → 履歴(`mapping_history`) → 既定(institution) → 未確定勘定**（ユーザーの明示指定/学習が常に既定に優先）。生成物は `source='auto_institution'` の **draft** で、確認画面での承認を要する。
  - **摘要照合の正規化**: 邦銀(UFJ 等)の Shift_JIS 明細は**半角カナ（`ｼﾖｳﾋｾﾞｲ`）**で出力されるため、照合時のみ NFKC 正規化して全角同等に扱う（保存値 `description`・`dedup_hash`・履歴 `pattern` は不変＝照合だけ全角化。半角カナ＋濁点を合成）。
  - 国税/地方税は**厳密一致**で判定（`外国税額控除`・`国税還付` 等「国税」を包含する別摘要を源泉と誤らない）。新生の国税/地方税は**同日に税引前利息がある場合のみ**源泉と判定し、予定納税等を誤分類しない。UFJ の国税/地方税は対象にしない（新生の源泉と取り違えない）。
  - **学習の汚染防止**: `auto_institution` で確定した仕訳は `mapping_history` に学習しない（institution は毎回決定的に再導出されるため履歴不要。特に文脈依存の源泉を coarse pattern として焼き付け同日ガードを迂回するのを防ぐ）。
  - **法的ゲート（`legalRisk:medium`）**: 既定マッピングの妥当性（特に源泉20.315% の損益外処理・消費税納付の区分）は**税理士サインオフ対象**。本機能は「黙って確定」せず候補(draft)提示に留める。
- **自動車税は連携対象外**（請求書払いで取込元に出ない）→ 手動入力。租税公課で計上し家事按分（事業分=租税公課／家事分=事業主貸。accounting §6・§7）。
- 店名（全角正規化後）を `mapping_history.pattern` のキーにし、確定実績から次回サジェスト。
- 取引日＝§1/§2/§3の `txn_date`、売上計上等は会計仕様に従う。

## 8. 汎用列マッピング（ユーザー定義フォーマット・C-11）

組込3形式（§1〜§3）はコードのパーサのまま残し、**1行=1取引型**の銀行/カードCSVを
列番号マッピング設定だけで取り込めるようにする（roadmap Phase3「対応フォーマット拡充」/
Exit基準5）。設定は `import_formats.config`（JSON）に保存し、検証して読み書きする。

### 8.1 source_type 表記と接続

- ユーザー定義フォーマットは `source_type` 文字列空間に **`format:{id}`**（`id` = `import_formats.id`）として表す。
- `import_batches.source_type` / `sub_accounts.import_source_type` は自由テキストなので組込3形式とそのまま共存し、**口座マスタ・dispatch は組込/ユーザー定義を1つの選択軸**で扱う（F-IMP-8 と一体）。
- 口座マスタ登録（`createImportAccount`）は `format:{id}` を取込形式として受理し、`id` の実在を検証する（存在しない id は拒否）。

### 8.2 設定（`ColumnMappingConfig`）

| フィールド | 必須 | 内容 |
|---|---|---|
| `encoding` | ○ | `shift_jis` / `utf8`（dispatch がデコードに使用。C-1） |
| `headerRows` | – | スキップする先頭行数（既定1） |
| `dateCol` | ○ | 取引日の列番号（0始まり。ISO化は C-3・複数形式吸収） |
| `descCols` | ○ | 摘要列（複数指定で半角正規化のうえ空白連結。空配列可） |
| `amount` | ○ | 金額マッピング（下記3モード） |
| `balanceCol` | – | 残高列（突合用・C-10。壊れていても取引行は失敗させず null 化） |
| `defaultAccountName` | – | 取込時の口座マスタ自動登録で用いる既定の親勘定科目名 |

**金額3モード（`amount.mode`）**:
| mode | 列 | 方向判定 |
|---|---|---|
| `split` | `paidCol` / `receivedCol` | 値ありの側（出金>0→out / 入金>0→in）。UFJ/新生型 |
| `signed` | `amountCol` | 符号付き1列。負=out / 0以上=in |
| `single` | `amountCol` / `directionCol` / `outValues[]` | 方向列が `outValues` のいずれか→out、他→in |

### 8.3 パース挙動（組込パーサと対称）

- 先頭 `headerRows` 行・全列空の行・金額セルが全て空の行は**取引行でない**としてスキップ（誤エラーにしない）。
- 取引行と判定したのに日付/金額が解釈不能なら **errors に退避**し正常行は取り込む（部分取込・C-9）。
- **負数（取消・組戻し等）も取りこぼさない（silent drop 禁止）**: 符号で方向を決める。split は出金列の負＝実質入金／入金列の負＝実質出金、signed は負=out、single は絶対値＋方向列。金額は常に円整数の絶対値で計上。
- `dedup_hash` は出現インデックス方式（C-6・`withDedupHashes`）。同日同額同摘要の別取引も全件保持し、再取込は冪等。

### 8.4 限界

- **1行=1取引型に限る**。複数行種別が混在するカード型（§2 の確定/未確定・注記行・登録番号行）は分類ロジックが要るため**組込 `card_mufg_visa` の担当**で、汎用設定では表現しない。
- 列の対応はヘッダ**名**でなく**列番号**で指定する（ヘッダ名マッチは将来拡張）。
- 金額の負数表記は `-`（半角/全角）を解する。`△`/`▲` 等の会計記号は将来対応。
- 設定の配列長は上限あり（`descCols` ≤ 64列・`single` の `outValues` ≤ 256件）。行ごとに反復されるため、巨大設定による取込時の CPU ブロックを防ぐ（列番号の値自体に上限は設けない＝範囲外は空セル扱い）。
