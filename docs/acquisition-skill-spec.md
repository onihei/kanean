# 取得スキル仕様 — Kanean

> 取込元データを取得し、**正規化ファイル**（[csv-format.md](./csv-format.md) §4.2 ほか）を出力する**外部スキル**の仕様。
> 本体には内蔵しない（[architecture.md](./architecture.md) §9, [PRD F-IMP-5/6]）。
> 第一の対象は **Amazon/楽天のスクレイピング**。取得の「型」は汎用で、将来 他サイトへ拡張可能。

---

## 0. 位置づけ — 全取込が「取得 → 正規化ファイル → import」に統一

| ソース | 取得（誰が） | importer に渡す形 |
|---|---|---|
| 三菱UFJ銀行 / 三菱UFJ-VISA / 新生銀行 | **人がサイトからCSVをDL**（既に出力可） | 各社ネイティブCSV（[csv-format §1〜§3]） |
| Amazon / 楽天 | **本スキルがスクレイプして正規化CSVを合成** | EC正規化フォーマット（[csv-format §4.2]） |

- 違いは「正規化ファイルを誰が作るか」だけ。銀行は既に存在、ECはスキルが生成。下流（import→仕訳→帳簿）は共通。
- **現在の実体**: Claude Code のスラッシュコマンド/スキル。**将来**: 他AI・ローカルLLM向けに**同じ出力契約で再実装**可（無料化）。
- 出力（中間フォーマット）が契約。取得方法・LLM・実装は差し替え可能。
- 本スキルは produce（取得・正規化）担当。本体の **importer は consume** 担当で別物（名前を混同しない）。

---

## 1. スキル構成 — オーケストレータ + 1サイト1スキル

```
acquisition（オーケストレータ / 全取り込みの親）
  ├ acquisition-amazon    … Amazon のログイン・巡回・抽出 → 正規化レコード
  ├ acquisition-rakuten   … 楽天 〃
  └ （将来）acquisition-<site>
共通処理（オーケストレータ or 共有）: 会計期間フィルタ(§5)・正規化契約検証・dedup・import投入・draft化
```

| 層 | 役割 |
|---|---|
| **`acquisition`（オーケストレータ）** | 全取り込みの親。サイトスキルのレジストリを持ち、**全実行 or 個別実行**を束ねる。共通処理（取得対象期間の決定[§5]・正規化契約の検証・import投入・dedup）を集約 |
| **`acquisition-<site>`（1サイト1スキル）** | そのサイトのログイン・巡回・抽出のみを担い、正規化レコードを返す。サイトの作法に専念 |

- **利点**: サイト改変の影響を**1スキルに局所化**（メンテしやすい）／**個別実行**できる（Amazonだけ再取得 等）／サイト追加＝スキル追加で済む。
- 銀行/カードは現状CSV手動DL→importなのでスクレイピングスキルは不要。将来DL自動化するなら同じ命名（`acquisition-<source>`）で足す。
- サイトスキルは「取得と正規化」だけに専念し、期間判定・import・承認といった横断処理はオーケストレータ側に置く。

## 2. 自動化レベル（human-in-the-loop の設計）

**無人の全自動（cron実行）はしない。** 理由:
- **2FA / CAPTCHA** は人の介在が必須。
- **認証情報をAI／スキルに保持させない**（設計原則）。

→ **役割分担**:

| 工程 | 担い手 | 備考 |
|---|---|---|
| 実行タイミングの通知 | **自動**（`/schedule` 月1のリマインド） | cron は「実行」でなく「思い出させる」ためだけに使う |
| スキル（コマンド）起動 | **人** | 前面の対話セッションで起動。無人ヘッドレス文脈では画面も2FAも出せない |
| ブラウザ | **ヘッドフル**（画面が見える） | 人が監視・介入できる |
| ログイン・2FA・CAPTCHA | **人** | 見えている実ブラウザに**人が直接入力**。AIはパスワードに触れない |
| 履歴の巡回・明細抽出 | **AI** | ログイン後のDOMを読むだけ |
| 取込結果の承認 | **人** | draft 仕訳を確認画面で承認（[csv-format §5]） |

- **2回目以降はほぼワンクリック**: 初回ログインのセッション（cookie = Playwright の `storageState` / 永続プロファイル）を保存・再利用。**期限切れ時のみ**再ログインを人に求める（グレースフルな分岐）。
- 保存セッションは**パスワード級の秘密**。ローカル限定・gitignore・同期しない（self-host = 本人の自分のセッションなので許容）。

## 2.5 取得経路 — 2つの実行殻（アプリ内 / スキル）＋ MCPフォールバック → 較正修復

AI（playwright MCP）の巡回はスナップショット往復のため**遅く・トークンを消費する**。通常運転は決定的な
固定スクリプトに寄せ、AIは「サイト改変時の保険＋修復役」に回す。

```
取込実行
  └ ① 固定 Playwright スクリプト（.claude/skills/acquisition/scripts/scrape.mjs <site>）
        成功 → 出力JSON → 分類（AI）→ POST（従来どおり）         ← 通常運転（速い・安い）
        失敗（サイト改変等）
          └ ② AI が playwright MCP で従来巡回 → 今回の取込を完遂   ← フォールバック（機能は止まらない）
              └ ③ AI が失敗アーティファクト＋②で観察した実構造でスクリプトを修正
                    → 再実行で検証（スクリプトは読むだけ＝安全） ← 自動修復（次回から①に復帰）
```

- **スクリプトの責務は「取得・正規化・自己検算」のみ**。分類（AI）・POST（curl）は従来どおりスキル側。
  読むだけなので再実行・修復検証が常に安全。
- **検算規約は経路によらず同一**（銀行=残高チェーン / カード=Σ利用＝新規ご利用額 / EC=Σline+shipping−points==total）。
  検算NGはスクリプトも投入させない（exit≠0・安全側）。
- **実装**: `playwright-core`（root devDependency）＋ Chrome チャンネル起動。**MCP と同じ永続プロファイル
  `./.kanean/pw-profile` を共有**（ログイン継続。同時起動は不可＝実行前に MCP ブラウザを閉じる）。
  ログイン/2FA はヘッドフル窓で**人**（スクリプトはログイン完了を検知するまで待機。§2 の原則は不変）。
- **失敗アーティファクト**: `.kanean/acquisition/fail/<source>/latest/` に `error.json`（step/message/url/hint）
  ＋ `page.html` ＋ `screenshot.png`。修復は `src/sites/<site>.mjs` 冒頭の宣言的な較正ポイント（`DEFAULT_SEL`）を直すのが基本。
- **終了コード契約**: `0`=成功 / `1`=失敗（フォールバックへ） / `2`=プロファイル使用中 / `4`=部分成功
  （EC: 突合OKの `orders`＋要補完の `failedOrders`。AIは failedOrders だけ MCP 補完）。
- 手順の詳細は `.claude/skills/acquisition/SKILL.md` 手順2a/2b。

### 2.5.1 巡回コアの一元化（`packages/acquisition`）

巡回手順の実体は **`packages/acquisition/src/sites/*.mjs` の1箇所だけ**にある。
実行殻（ブラウザの用意の仕方）だけが2つあり、同じサイトスクリプトを動かす。

```
packages/acquisition/
  src/sites/{ufjvisa,mufg,shinsei,amazon,rakuten}.mjs  ← 巡回手順（唯一の実体）
  src/core/                                            ← 殻に依らない部分（正規化・検算・較正・診断）
  src/runtime/playwright.mjs   ← 実行殻A: Claude Code スキル経路（Chrome + 永続プロファイル）
  src/runtime/electron.mjs     ← 実行殻B: アプリ内（Electron の BrowserWindow）
  bin/scrape.mjs               ← CLI。`.claude/skills/.../scripts/scrape.mjs` はこれを呼ぶだけ
```

**外部コマンドには依存しない**。適格請求書 PDF（Amazon の商品別純額の一次ソース）のテキスト化は
同梱の pdf.js で行う（`core/pdfText.mjs`）。以前は poppler の `pdftotext -layout` を子プロセスで
呼んでいたが、それだと DMG から入れた人に `brew install poppler` を強いることになり、配布形態と
噛み合わなかった。pdf.js が返すのは座標付き断片なので、`layoutFromItems`（純関数）で行を組み直す。

サイトスクリプトが使ってよい API は `src/core/page.mjs` の `BROWSER_API`（page 11 種・locator 13 種・
context 5 種）に固定してある。契約の外へ手を伸ばしていないことはテストで機械的に確かめる
（偽ブラウザが契約外のプロパティ参照で落ちる）。**殻を増やしても巡回手順は書き直さない**、が成立の条件。

| 共通 API | Playwright 殻 | Electron 殻 |
|---|---|---|
| `goto` | そのまま | `win.loadURL`（`ERR_ABORTED` は成功扱い） |
| `evaluate` | そのまま | `webContents.executeJavaScript` |
| `screenshot` | 全ページ | **表示領域のみ**（`capturePage` の制約。人に見えていた範囲で足りる） |
| `locator` / `getByRole` / `getByText` | そのまま | ページ内の解決器 + ポーリングで**自動待機の意味論を再現** |
| クリック | 実マウス入力 | `sendInputEvent`（当たり判定が取れなければページ内 `click()`） |
| 文字入力 | `fill` / `pressSequentially` | native setter + `input`/`change` ／ 実キー入力 |

Playwright の `count()` / `isVisible()` は待たず、`click()` / `fill()` / `innerText()` は待つ。
Electron 殻もこの区別をそのまま再現する（待つ側だけがポーリングする）。

**両殻が同じ明細を返すことの確かめ方**（実サイトでのみ確かめられる）。取込は取得結果を貯めない
（§2.5.3）ので、Electron 側は検証時だけ結果を落として突き合わせる。

```
# 殻A: スキル経路の CLI が --out に書く
node packages/acquisition/bin/scrape.mjs ufjvisa --since 2026-01-01 --until 2026-06-30 \
  --out /tmp/acq/pw-card_mufg_visa.json

# 殻B: KANEAN_ACQ_DUMP を立てて起動し、UI から取込む（既定では何も落とさない）
KANEAN_ACQ_DUMP=/tmp/acq/el pnpm dev:app

node packages/acquisition/bin/acq-diff.mjs \
  /tmp/acq/pw-card_mufg_visa.json /tmp/acq/el/card_mufg_visa.json
```

突き合わせでは `scrapedAt` と証跡パスの土台（殻ごとに違う）だけを均す。**較正・範囲・スクリプト版の
食い違いは明細の差と分けて報告する**（前提が違えば「殻の差」とは言えないため）。ダンプは品名・金額を
含む生の結果なので、確かめたら消す。

### 2.5.2 較正（`SEL`）はコードではなくデータ

各サイトの `SEL` は **`DEFAULT_SEL`（同梱・読み取り専用）** として持ち、
`$DATA_DIR/acquisition/selectors/<source>.json` があればそれを重ねる。

- 受け付けるのは**データだけ**。値は 文字列 / 数値 / 文字列配列 のみで、同梱に無いキーの追加・
  型の変更は拒否する。`page.goto` へ渡るキー（各サイトの `NAVIGABLE_KEYS`）は http/https に限る
  ＝ `javascript:` を通して**銀行のログイン済みセッションで任意コードを動かす形を作らない**。
- **上書きファイルを消す＝同梱較正へ戻る**（壊れた較正からの復帰手段）。
- 取得結果に `calibration: { origin, version, overridden }` を載せ、どの較正で取ったかを残す。

### 2.5.3 アプリ内取込のジョブと診断

アプリ内経路は人のログイン待ちを含むため、開始と結果取得を分けた**ジョブ**として進む。
**取込は分類を待たない**。取れたらそのまま importer へ流し、draft として帳簿に並べる。

```
 開始 ─▶ ログイン待ち ─▶ 取得中 ─▶ 完了（draft が帳簿に並ぶ）
            │              │
            └──────────────┴──▶ 失敗 / 中断
```

- ジョブが持つのは**進行の記録だけ**（`$DATA_DIR/acquisition/jobs/<jobId>.json`）。明細は持たない。
  この記録が全部消えても帳簿は完全に成立する。中断した巡回を再開する仕組みは持たない（取り直せばよい）。
- 科目が決まらなかった明細は**未確定勘定の draft**になり、`unresolved` として件数に出る。
  分類はその後、「未確定に科目を当てる」操作で行う（§2.5.4）。
- 分類のために外へ出るのは `{ id, text }`（品名・摘要）だけで、**金額・取引識別子・残高・日付は出ない**。
  同じ文字はまとめるので、会話の量は取込件数ではなく**品目の種類数**に比例する。
  確定履歴はアプリ側が引いて添える（外部クライアントに履歴を取りに行かせない）。
- 失敗診断は `$DATA_DIR/acquisition/diagnostics/<source>/latest/`。認証情報とセッション識別子は
  保存前に伏せる（入力欄の値・`csrf`/`token` の meta・URL のセッションパラメータ）。
- 診断には **「較正で直る見込みがあるか」の判定**を付ける。検算不一致・巡回の流れの変化・
  表示順の前提の変化は較正では直らないので、無駄な較正更新を繰り返させない。
- 巡回のログイン状態は Electron の専用セッション区画（`persist:kanean-acquisition`・`userData` 配下）に
  置き、`$DATA_DIR` の会計データとは物理的に分ける。**エクスポート・バックアップの対象外**で、
  設定画面から破棄できる。

### 2.5.4 分類は「未確定 draft に科目を当てる」

分類はジョブに属さない。**未確定勘定のまま残っている draft** に対する操作で、
人が画面で当てても Claude Desktop（MCP）が当てても同じものに効く。
巡回だけでなく **CSV 取込・手入力で生じた未確定にも同じ操作が効く**。

- 一覧（`GET /api/acquisition/unclassified`）は同じ文字をまとめて `{ id, text, count, sources }` を返す。
- 適用（`POST /api/acquisition/unclassified`）は `{ id, proposedAccount }` を受け、
  既存の `updateLineAccount` を通して科目を置き換える（draft 限定・税区分の再解決はそこに任せる）。
  **確定はしない。**
- `id` は `text` の短いダイジェスト。連番にすると「一覧の何番目か」に依存し、
  人が先に何件か片付けただけで番号がずれて**別の取引に当たる**。ダイジェストなら対応表が要らず、
  いつ返ってきても同じ文字に当たる。
- 既に人が片付けていた対象は「適用0件」として返し、失敗にしない。
  存在しない勘定科目を指された場合は**作らず**、その名前を返す。

## 3. 実行フロー

```
/schedule（月1）──▶ 通知「取込の時期です」              ← 自動はここだけ
                          │
              人が acquisition（または個別サイトスキル）起動
                          │
        ヘッドフルでブラウザ起動（保存セッションを復元）
                          │
        ┌── セッション有効？
        │        ├ 有効 → そのまま続行
        │        └ 無効 → ⏸ 一時停止「ログイン・2FAを済ませてEnter」
        │                        ↑ 人が実ブラウザに直接入力
        ▼
        開いている会計期間内(§5)の注文のみ巡回 → 明細抽出（AI）
                          │
        生証跡（HTML/スクショ）保存 ＋ 正規化CSV出力（§6）
                          │
        本体 importer へ投入 → draft 仕訳生成
                          │
                  人が確認画面で承認
```

## 5. 取得対象期間 — 開いている会計期間に限定

**翌期間の取引は取得しない（＝`raw_transactions` に入れない）。** 保留はしない、ただ無視する。

- 取得・取込の対象は **開いている会計期間（`fiscal_years.status='open'`）の `[start_date, end_date]`** の範囲のみ。
- 範囲判定は**実行日ではなく取引日（`order_date`/`txn_date`）**で行う。
  - 例: 1月に実行 → 前年12月分（まだ open 期間）は取得する／1月分（翌期）は取得しない。
- **年度繰越処理**で翌期が `open` になったら、次回実行でその期間分を取得する。
  - 前回無視した翌期注文は `raw_transactions` に**未登録（dedup記録なし）**なので、期間が開いた後の実行で普通に取得される（再取得の特別処理は不要）。
- **本体 importer も同じ期間ゲートを持つ**（権威）。銀行/カードの手動CSVに翌期行が混ざっていても、取込時に範囲外行は**入れない**。
- **黙って落とさない**: 範囲外で除外した件数（と open 期間の end_date）を実行ログ・取込結果に表示し、「繰越後に取り込まれる」ことが分かるようにする。

> 繰越処理そのもの（期末残高→翌期 元入金/開始残高）は会計仕様の範囲（[accounting-spec §1.3]）。本ゲートは「どの期間の取引を取り込むか」だけを規定する。

## 6. 出力（契約）= 正規化EC明細＋仕訳候補 [csv-format §4.2]

- 明細の必須項目: `source` / `order_id` / `order_date` / `order_total` / `line_no` / `item_name` / `quantity` / `line_amount` / `evidence_ref`、任意: `payment_hint` / `currency`（定義は [csv-format §4.2]）。
- **仕訳候補（旧 `category_hint` を格上げ）**: 行ごとに **AIが分類した科目提案**を付す。`proposed_account`（科目名/コード）/ `treatment`（`expense`=経費 / `owner_draw`=事業主貸 / `unresolved`=未確定）/ `reason`（分類理由＝承認UI表示＋監査）/ `confidence`（high/medium/low）/ `policy_ref`（適用したポリシー版・ルールID）。生成方法は **§7**。
  - これは**提案であって確定ではない**。本体は科目名→`account_id` を勘定科目マスタで検証し、未知/曖昧は **未確定勘定＋flag**（黙って確定しない）。借方＝この科目、貸方＝未払金（クリアリング）は [csv-format §4.3] で機械適用。
- **金額はLLM抽出を鵜呑みにしない**: 必ず `evidence_ref`（HTML/スクショ）を残し、取込は **draft** として人が承認。
- 出力先: **import API への POST**（認証なし・受け口は本体が zod 検証）。投入経路・レジストリは §7.4。

## 7. 仕訳化＝AI分類（2トラック・学習ループ・カスタマイズ）

> EC明細の科目分類は、本体のルールエンジンではなく**スキル（AI）が主担当**する。品名→科目は意味理解タスク（SDカード＝消耗品 / 漫画＝事業主貸 / 技術書＝新聞図書費）で、`contains` 型ルールでは列挙不能なため。
> **法的に決定的な項目（受取利息・利息の源泉・消費税納付）も AI対象外にしない**: 正しい処理を **md ポリシーに明記** し、AIは推測でなく適用して**確信して提案**する（受取利息→`事業主借` / 利息の源泉(国税・地方税)→`事業主貸` / 消費税納付→`租税公課`）。決定的＝当てずっぽうではないので確信提案でよく、全件 **draft＝人がUIで承認** するゲートが誤りの安全網。`unresolved` は「**本当に情報不足で決まらない**」時だけに戻す（「法的に微妙だから」では投げない）。
> → これは **銀行/カードをスキルトラックに寄せる**方向（§7.1 注）と整合。本体ルールエンジン（`auto_journal_rules`）は AI＋確定履歴が代替するので段階的に不要化（§12）。判別材料（新生「国税」は同日の税引前利息とペア＝消費税ではない 等）は [classification-policy.md] に置く。

### 7.1 役割分担 — 2トラック（競合させない）

| 取込トラック | 分類の主担当 | 関与しないもの |
|---|---|---|
| **UIトラック**（人が手動CSVをUIで取込） | 本体ルール: `auto_journal_rules` → `mapping_history` → institution → 未確定 | — |
| **スキルトラック**（連携サービス取込・本仕様） | **AI**: 確定履歴 ▶ md ポリシー ▶ 未確定（§7.2） | `auto_journal_rules` / institution は**関与しない** |

- 借方（科目）＝AIが決める／貸方（未払金=クリアリング）＝[csv-format §4.3] で機械的に決まる。1明細を2エンジンで二重分類しない。
- 対象はEC経費の「経費科目 vs 事業主貸」判定（誤りは承認時に回収可）。
- **方向性（移行中）**: 上表は現状（ECのみスキルトラック）。銀行/カードもスキルトラックへ移し、最終的に **UIトラックの本体ルールエンジン（`auto_journal_rules`）を廃止**する計画（§12）。その際、銀行の摘要→科目（報酬振込→売上回収 / 光熱費→水道光熱費 / カード引落→未払金決済）と法的パターン（利息/源泉/消費税）は **md ポリシーに明記してAIが提案**（決定的なので確信提案、`unresolved` は真の判別不能のみ）。**手動CSV取込は当面フォールバックとして残す**（銀行サイトは反自動化が強く、スキル取得の安定実証まで塞がない）。

### 7.2 学習ループ — 確定が次回の優先提案になる

```
EC巡回 → 品目抽出
  └ 各品目を AI が分類:  ① 確定履歴（最優先）▶ ② md ポリシー ▶ ③ 未確定
       │
   draft 投入 → 人がUIで承認・確定
       └─► 確定した品目→科目を履歴へ書き戻し ──┐
                                                ▼
              次回取込で AI が履歴を優先提案（収束・自己修復）
```

| 入力 | 性質 | 優先 |
|---|---|---|
| **確定履歴**（ユーザーがUIで確定した品目→科目の実績） | 動的・ユーザー固有の正解 | **最優先** |
| **md ポリシー**（科目定義＋判定＋例） | 静的・新規品目の初期判断 | 次点 |

- 履歴は**プロンプトに「過去の確定例」として投入**＝SQL完全一致では拾えない揺れ（`microSDXC 128GB` vs `256GB`）も**意味でマッチ**。md の例＝固定 few-shot、履歴＝実データで育つ few-shot。
- 自己修復: 履歴に無ければ md が初期判断 → 誤れば人が直す → 履歴へ入り次回から正しくなる。
- recency 重視は「昔は経費・今は私用」の方針変更にも追従（新しい確定が古いものに勝つ）。
- 格納は本体 `mapping_history` を転用（[data-model §2.9.2]）。EC経費も、決定的な金融取引（利息/源泉/消費税納付・摘要→科目）も、確定が次回提案を正す方向なので学習してよい。

### 7.3 履歴注入ポリシー — payload を履歴総量から切り離す

意味マッチ（プロンプト投入）の payload が履歴の蓄積で膨らまないよう、**注入する分だけ**絞る。**DB行は消さない**（監査・再学習用に残す。忘却＝削除ではなく注入ポリシー）。

| 機構 | 効果 |
|---|---|
| ① 重複排除済みペアを注入（生明細でなく `pattern→科目`） | `mapping_history` は `hit_count` で集約済み。「12回購入」→1行 |
| ② **関連プレフィルタ（主機構）** | 今回バッチの品名トークン（ブランド/キーワード）と語が重なる履歴のみ候補に。**payload ∝ 今回の取込件数**（月次で小）で履歴総量に非依存。語が重ならない新規品目→候補ゼロ→md 担当 |
| ③ 忘却窓（recency） | `last_used_at` が**直近12か月以内**のものだけ候補。1年使われていない確定は注入しない（行は残す） |
| ④ 上限K（バックストップ） | 候補多数でも `recency × hit_count` で上位K件（例 200）に丸め、payload に決定的な天井 |

- ②③④ は **`GET 分類履歴` API 側（SQL）**で適用。スキルは「今回の品名リスト」を渡し、**絞り込み済み候補だけ**受け取る（フィルタはデータの近くに置く）。

### 7.4 連携レジストリ・投入経路・API（認証なし・ローカル呼び出し）

- **連携サービスの一覧（Amazon/楽天/最終取得日）は本体 DB が正**（[data-model] 口座マスタ/F-IMP-8 を拡張）。スキルは状態を持たず、毎回 API で取得。
- スキルは本体を **`http://127.0.0.1:<PORT>` へ直接呼ぶ**（認証なし。本体はループバック限定バインド＝[architecture §5]）。以下 3 本を叩く：

| API | 用途 |
|---|---|
| `GET 連携サービス一覧` | 巡回対象＋最終取得日（差分の起点・§8） |
| `GET 分類履歴`（今回品名を渡す） | §7.3 で絞った確定履歴候補を取得 |
| `POST EC仕訳候補` | §6 契約の明細＋仕訳候補を draft 投入（本体 zod 検証＋期間ゲート） |

- 3本の req/res 契約は [ec-import-api.md](./ec-import-api.md)。

### 7.5 分類ポリシーのカスタマイズ（md ファイル）

- 分類方針は [classification-policy.md](./classification-policy.md) に外出しし、**ユーザーが md 編集でチューニング**（例を1行足す等）。
- **regex の羅列でなく「方針＋few-shot 例」**にする（AI を使う意義）。科目定義・判定順・代表例を記述。`policy_ref`（版/ルールID）を仕訳候補に刻み、改定の追跡を可能にする。
- 例（抜粋）: ストレージ/PC周辺/文具→消耗品費 ／ 漫画・娯楽書→事業主貸 ／ 技術書・専門書→新聞図書費 ／ 判別不能→未確定（理由添付）。

## 8. 差分取得・冪等性

- 取得範囲は **「§5 の open 期間 ∩ 前回取得以降」**。
- `dedup_hash = source + order_id + line_no`（[csv-format §4.2]）。再実行・重複投入に強い。
- 範囲外（翌期）は登録しない＝dedup記録も作らないので、期間が開いた後に自然と取得対象へ戻る。

---

## 9. スコープ最小化（負荷とリスクを下げる）

- item 明細が**必須なのは「経費品と私用品が混在する注文」だけ**。純注文（全部経費 or 全部私用）はカード明細の合計＋注文単位の分類で足りる（[csv-format §4]）。
- まずは混在注文に絞れば、抽出量・誤りリスク・実行時間を抑えられる。

---

## 10. セキュリティ

- **認証情報をスキル/AIに保持させない**（人が実ブラウザに入力）。本体側の import トークンは廃止されたため、AI の文脈に載る秘密情報はゼロになった（本体はループバック限定バインドで保護）。
- **セッション/プロファイルはローカルの秘密**（gitignore・非同期・必要なら暗号化）。
- 生証跡には個人情報が含まれる → 保存場所は本人ローカル。暗号化・保存期間を要検討。
- **規約**: 本人が自分のデータを個人利用の範囲で取得する前提。商用再配布・第三者の代行取得はしない。

---

## 11. 配布

- **Claude Code**: `.claude` のスキル/スラッシュコマンドとして配布（対象＝エンジニア）。オーケストレータ＋サイトスキルを単位に配れる。
- **他AI / ローカルLLM**: §6 の出力契約さえ満たせば実装自由。将来ローカルLLMで無料運用を想定。
- 本体リポジトリにスクレイパー実装は持たない（[architecture §9]）。
