# Kanean ロードマップ

個人事業主向け確定申告/会計システムを、実務で使える機能水準へ段階的に育てる
ための実装計画。**設計は他 docs を正とし**
（[architecture.md] / [accounting-spec.md] / [PRD.md] 等）、本書はその上で
「何を・どの順序で・誰が」実装するかを定める。

> 本書はコードベースを実地検証した上で、必要機能を洗い出した結論である。
> 法的リスク `high` の項目（確定申告書・消費税申告・源泉・控除判定・決算整理・
> 電子帳簿保存・e-Tax）は**税理士のサインオフを必須ゲート**とし、システムが
> 自動算出しても「提出可能」を AI/開発者が単独で宣言しない。

## 1. 結論サマリ（任せられる範囲）

洗い出したギャップ **82項目**を担当別に分類した結果：

| 担当区分 | 件数 | 割合 |
|---|---|---|
| AI が実装完結（`ai`） | 46 | 56% |
| AI 実装 + 人の判断/データ（`shared`） | 27 | 33% |
| 主に人間（契約・資格情報・税理士・NFC 等）（`human`） | 9 | 11% |

- 重要度: `must` 19 / `should` 36 / `nice` 27
- 法的リスク: `high` 18 / `medium` 18 / `low` 32 / `none` 14

**実装ドライバーとしては大半を委任可能**（過半が AI 完結、合算で約9割は AI が
手を動かせる）。一方で **`high` 18項目は税理士サインオフが律速**、最終局面の
**e-Tax 送信・自動口座アグリゲーション**は人間/外部依存が支配的。

## 2. 現状の急所（コード検証済み）

- ~~**`reports/`（試算表・PL・BS・総勘定元帳）は feat ブランチにのみ存在し `main` 未マージ。**~~ → **解消**: reports/ は `main` にマージ済み（CI は turbo `shared→core→server` を通すこと）。
- **schema 定義済みでコード参照ゼロ＝未配線テーブル**: `counterparties` / `sub_accounts`（補助元帳の軸として）/ `departments` / `items` / `tags`・`entry_tags` / `attachments` / `documents`・`document_lines`。
- **`opening_balances` は読取のみで書込み経路が皆無** → 青色決算書4ページ目（BS・元入金・資本連結）が常に擬似値になる。
- **`journalize` は借1:貸2 の2行固定。税区分は相手行に suggest 由来か `null`**（`accounts.default_tax_category_id` 未参照）。core の `assertBalanced` は任意N行対応済 → **複合仕訳・税区分自動付与は「配線するだけ」**。
- **`dedupHash` が脆い**: UFJ は残高列依存・カードは分割回数依存で、同日同額同摘要の衝突で片方が落ちる既知バグ。
- **core は完成度が高い**: `simplifiedTax`（税抜1000万→国390k/地方110k）・`depreciation`（マツダ2 = 439,919/219,960/残高1）ともゴールデン緑。**不足は server/UI 配線**。

## 3. 方針（基盤配線ファースト）

審査（3案比較・コード検証付き）で **「基盤配線 → 帳票 → 連携」** を最良と判定。
ユーザー最重点は連携・帳票の両翼だが、**税区分 `null`・補助科目未配線・元入金
未設定のまま帳票や連携を先に積むと決算書・消費税申告の入力源が壊れる**ため、
正しい入力源（Phase 1）を先に確立し、両翼（Phase 2 帳票 / Phase 3 連携）を連続
して出す。`must` を前方、`legalRisk:high` は人間ゲート化、AI 自走区間を前方に
最大化する。

> 連携を最優先に前倒しすることも可能（ユーザー判断で上書き可）。ただしその場合、
> 税区分・補助科目・名寄せの土台不足が後工程で二重計上・誤区分として顕在化する
> リスクを許容すること。

### Phase 3 — 銀行・カード連携の堅牢化【ユーザー最重点②】
> ✅ **完了**（2026-06-02 時点・`main` マージ済み）。重複検知の堅牢化(出現インデックス方式)・部分取込/エラーリカバリ(行単位 partial/failed)・口座残高同期/突合(残高チェーン)・口座マスタ選択UX(F-IMP-8)・**汎用列マッピング**(コード変更なしで新フォーマット追加)・**金融機関特有の既定自動仕訳**(受取利息→事業主借/源泉→事業主貸/消費税納付→租税公課)・取込明細の `ignored` 退避と状態フィルタUI・**口座間振替の名寄せ**(settlement リンク列＋同額逆方向日付近接の候補検知→1本の振替 draft 統合) まで実装。
> **残（Phase 5 へ）**: カード明細↔銀行引落の**合計突合**(1引落＝複数カード利用の合算)と EC↔カードの付替え連鎖は EC連携(Phase 5)と併せて実装する。本フェーズの名寄せは 1:1 の口座間振替に限定。
> **法的ゲート未充足**: 決済リンク/名寄せ(二重計上防止)・既定自動仕訳の会計的妥当性は **`legalRisk:high/medium`＝税理士サインオフ対象**。実装は候補提示＋ draft 起票に留め、「二重計上防止 完了／提出可能」は専門家確認を経るまで宣言しない（Exit基準2は口座間振替まで充足、カード合計突合は残）。

**目標**: 自動アグリゲーションは契約・資格情報・規約保守が重く `risk:medium/XL` の
ため Phase 5 へ回し、まず**手動CSV取込を「取りこぼさず・二重計上せず・残高が合い・
名寄せできる」業務水準**へ堅牢化。決済リンク名寄せは二重計上＝PL誤計上の重大リスク
のため専門家確認を伴う。

**AI 完結率**: 約80%（dedup・突合・残高同期・部分取込・列マッピング・口座マスタUIは AI。
名寄せロジックと特殊取引の会計区分の妥当性確認がゲート）

**法的ゲート**:
- 決済リンク/振替名寄せ（二重計上防止）の会計的妥当性 — 税理士（`high`）
- 金融機関特有の既定仕訳（受取利息源泉20.315%・税金引落区分）の妥当性 — 専門家（`medium`）

**主要項目**:
- 重複検知の堅牢化（`dedupHash` に行序数/明細位置、残高/分割依存の脆さ解消、重複候補レビューUI）— must/`high`
- 対応フォーマット拡充（`SourceType` 拡張・dispatch 分岐、**汎用列マッピング設定**＝ユーザー定義の列対応）— must
- 口座/カード登録UX（口座マスタ、`linked_account_ref` からの選択、`account_ref` 手入力廃止）— F-IMP-8
- 取込元をまたぐ決済リンク/名寄せ（settlement/clearing リンク列、カード↔銀行引落突合、口座間振替検知＝同額逆方向・日付近接）— must/`high`
- 口座残高同期・突合（残高列保存、累積残高と CSV 残高の突合・取りこぼし検知）
- 金融機関特有取引の既定自動仕訳（受取利息→事業主借/源泉、税金引落→租税公課、源泉20.315%の複合）
- 部分取込・エラーリカバリ（行単位 try-catch、`import_batches.status` partial/failed 発行、行単位エラー表示）

5. 新フォーマットを列マッピング設定で追加でき、口座マスタから選んで取込できる

  - ✅ **`restorable-export` で復元可能性が成立**（2026-08-12）: slice11 のエクスポートは zip に control plane を
    含まないため、書き出せても**取り込む経路が無く復元できなかった**（`books/` を置いてもレジストリに載らず不可視）。
    `POST /api/import`（設定→データ管理）を対にして追加し、sha256 突合 → `integrity_check` → migrate を
    **配置前**に済ませてから帳簿レジストリへ登録する。帳簿IDの衝突は 409 で中止し `mode=new`／`mode=replace` を
    利用者が選ぶ（黙って上書きも採番もしない）。zip リーダも自前（STORE＋DEFLATE・パス脱出/CRC/展開サイズを検証）。
    用途の違い（持ち出し ⇔ 巻き戻し）は [architecture.md] §11.1。**これで「解約＝データ人質にしない」が実際に機能する**。

**Exit**:
1. 仕訳/書類に領収書PDFを添付・閲覧でき、電帳法の保存要件を満たす
2. 口座連携で明細が定期自動取得され、未対応分は手動CSVで補完できる
3. 定率法・一括償却・少額特例・中古・除却・売却が計算・起票でき、翌年が前年残高起点で連続
4. 月次自動バックアップとアカウント削除/エクスポートが動作し、per-user DB が暗号化される

#### デスクトップ化（`electron-desktop-shell`・2026-08-12）

配布形態を **Electron** に確定して実装した（Tauri から変更。理由は当該 change の design.md）。
Phase 6 の帳簿受け渡しは「事務所側が普通に使えるアプリを持っている」ことが前提なので、その足場にあたる。

- Hono を Electron main プロセス内で動かし、UI は**カスタムプロトコル**で配る（**TCP を開かない**）。
  既存の 136 ルート・core・drizzle・pdf-lib は書き換えていない（`app.fetch` を直接呼ぶだけ）。
- ローカル連携（取込スキル・MCP サーバ）は `$DATA_DIR/kanean.sock`
  （unix socket・0600・**アプリ起動中のみ存在**）。**MCP はここに繋ぐ**。
- `better-sqlite3` を 13.x（Node-API）へ更新。Node と Electron で同一バイナリが動くためリビルド機構を持たない。
- 残: `Developer ID Application` 証明書と notarize（人の作業）、サンプル帳簿の要否判断。
- **派生**: エクスポート zip が復元できない既存欠陥を発見し、change `restorable-export` として切り出した
  （zip に control plane が無く、`books/` を置いても帳簿レジストリに載らない）→ **対応済み**（取り込み経路を追加。上記 slice11 の追記）。

#### MCP サーバ（`mcp-server`・2026-08-12）

Claude Desktop から会計データを問い合わせられるようにした（`packages/mcp`）。ソケットへ繋ぐ薄い
stdio ブリッジで、**会計ロジックは持たない**（検証・期間ゲート・冪等・帳簿解決の権威は本体側のまま）。

- 露出は読み取り中心の11本。128 ある HTTP ルートを機械的に写像せず、意味のある動詞に集約する
  （上限20をテストで固定）。**書き込みは連携サービスの登録だけ**で、仕訳の確定・承認と
  マスタ編集はツールとして持たない＝承認は UI に残る。
- 未起動なら**確認を得てから**起動して1回だけ再試行する。既定でソケットしか試さない
  （配布物が暗黙にポートを探すと、TCP を開かない設計と食い違い、誤接続もしうるため）。
- 配布は `.mcpb`（**104KB**）。Claude Desktop が Node を同梱するのでランタイムは持たない。
  設定画面の「Claude Desktop と連携」から書き出し、利用者は Dock の Claude アイコンへドラッグ1回で導入する。
- 手順知識は MCP prompts と返り値の `nextActions` に置く。**Claude Desktop のスキルは使えない**
  （スキルのコード実行は Anthropic 側のサンドボックスで走り、利用者のマシンのソケットに届かない）。
- 実機の Claude Desktop で疎通・会話とも確認済み。接頭辞を打たなくてもツールは選ばれる。

#### アプリ内取込（`acquisition-in-app`・2026-08-12）

取込の巡回を Electron の中へ移した。Claude Desktop には Bash が無く、これまでの
取込スキル（Bash から Playwright を起動する）が届かなかったため。

- **巡回手順の実体を1箇所に集約**（`packages/acquisition/src/sites/*.mjs`）。実行殻だけが2つあり
  （Playwright＝スキル経路 / Electron＝アプリ内）、同じサイトスクリプトを動かす。
  サイト側が使ってよい API は契約（`BROWSER_API`）に固定し、逸脱をテストで落とす。
- Playwright の locator の意味論（**見つかるまで待つ / count は待たない**）を Electron 側で再現した。
  ここが「巡回手順を書き直さずに殻を差し替える」の成立条件。
- **較正（`SEL`）をコードからデータへ**。`$DATA_DIR/acquisition/selectors/<source>.json` で
  アプリの更新なしに差し替えられる。受け付けるのはデータのみで、`javascript:` URL も型変更も
  未知キーも拒否する（銀行のログイン済みセッションで任意コードを動かす形を作らない）。
  上書きを消せば同梱較正へ戻る。
- **取込は分類を待たない。** 取れたらそのまま draft として帳簿に並び、科目が決まらなかったものは
  未確定勘定の draft になる。分類は後から「未確定に科目を当てる」操作で行い、人が画面で当てても
  Claude Desktop が当てても同じものに効く（CSV 取込・手入力の未確定にも効く）。
  当初は「分類が返ってから投入」にしていたが、取り込んでも画面に何も現れず、
  会計データを帳簿の外に TTL 付きで貯めることになっていたので捨てた。
- **分類のために外へ出るのは品名・摘要だけ**。金額・取引識別子・残高・日付はアプリ内に留まる。
  同じ文字はまとめるので、会話の量は取込件数ではなく品目の種類数に比例する。
  識別子は文字のダイジェスト＝一覧の並びに依存しないので、人が先に片付けても別の取引に当たらない。
- 取込は5状態のジョブとして進む。ジョブが持つのは進行の記録だけで、明細は持たない。
  中断した巡回の再開は持たない（取り直せばよい）。**範囲を限った取得では差分の起点を前進させない**
  ＝あいだに未取得の穴を残さない。
- 診断に「**較正で直る見込みがあるか**」の判定を付けた。検算不一致や巡回の流れの変化は較正では
  直らないので、無駄な更新を繰り返させない。
- 巡回のログイン状態は Electron の専用セッション区画に置き、エクスポート・バックアップの対象外。
  設定画面から破棄できる。
- 残: **実サイトでの通し実行**（人のログインが要る）。反自動化の当たり方、`locator` 再現の穴、
  Playwright 殻との出力一致は、実行して初めて分かる。

#### 帳簿受け渡しプロトコル（事務所⇔本人。チェックアウト／チェックイン）

本人が顧問を依頼するとき、帳簿を事務所へ「貸し出し」、修正済みを受け取って「返却」する流れ。
共有サーバを持たないまま2台のマシンをまたぐため、以下を1スライスずつ積む。

```
本人（personal）                          事務所（office）
編集可 ──コード入力してエクスポート──▶ 受入 → 預かり中（編集可）
ロック中（読み取り専用） ◀──返却封筒──   返却データを書き出し
  └ 取り込み＝丸ごと差し替え               └ 返却済 →（契約終了）アーカイブ
```

1. **顧問先コードの発行**（事務所側 UI）。コードは暗号鍵そのものではなく**事務所の公開鍵の指紋**として扱う
   （人が読み上げる媒体で運ぶため、漏洩しても復号に至らない設計にする）。
2. **暗号化封筒のフォーマットと鍵管理**。本人→事務所は事務所の公開鍵で暗号化し、封筒に本人の公開鍵を
   同梱して返却も暗号化できるようにする。封筒に `book_id`・預かり ID・貸出時点の世代を焼き込み、
   **取り違え（別の顧問先のデータで自分の帳簿を上書き）を構造的に防ぐ**。
3. **貸出中の読み取り専用ロック**。ロックは事故防止の合図であり、本人のマシン上の本人のファイルである以上
   セキュリティ境界ではない。§「解約＝データ人質にしない」原則に従い、**本人がロックを解除する道を必ず用意する**。
4. **返却の取り込み＝帳簿単位の丸ごと差し替え**。マージは行わない。restore（退避 → `integrity_check` → 配置）を
   再利用する。ロック中に手元が変更されていた場合（分岐）は、**自分のデータを使う／取り込んで上書きする**の
   2択を明示的に提示する（黙ってどちらかに倒さない）。
5. **事務所側の預かり管理 UI**（受入・預かり中・返却済のライフサイクル。アーカイブと接続する）。

**未確定**: 上記は `legalRisk` 未評価。帳簿の受け渡し中の記帳義務・保存義務の所在（電子帳簿保存法）は
人間/税理士の判断（`human`）。

| アカウント削除（per-user DB）とデータエクスポート | shared | 5 |
| e-Tax 電子提出（XML・XMLDSig・NFC・送信/受信） | human | 6 |

## 6. 横断リスク（順序に依らず注意）

- ~~`main` への `reports` マージ未完が最前段ブロッカー~~ → **解消済み**（Phase 1・2 とも `main` マージ済み。CI: turbo `shared→core→server` を通すこと）
- `opening_balances` の書込みUI/APIを起こさないと青色決算書4ページ目が常に擬似値
- 税区分自動付与の誤区分は消費税申告の誤りに直結（`high`）
- 名寄せの誤消し込みは PL/消費税を歪める（計上漏れ）
- 自動アグリゲーションは資格情報暗号保管・規約・契約で人間律速
- e-Tax 送信系仕様は外部入手前提（公式新Web-API は参照系中心で送信API非含）

## 7. 設計原則（各案からの移植）

- **confirmed 仕訳を唯一の真実源**とし、仕訳帳→元帳→試算表→PL/BS→決算書→申告書の集計連鎖を下流から固める。ゴールデン（マツダ2 / `simplifiedTax`）を各フェーズ CI の回帰固定に据え、配線で数値が崩れないことを保証。
- **連携は正規化中間レイヤ(`raw_transactions`)への後段として疎結合に設計**し、手動経路を捨てず併用。自動連携が来ても Phase 3 の dedup/名寄せがそのまま効く。
- **決済リンク/名寄せは多経路データ流入の前に必ず手当てする**（順序が逆だと二重計上が爆発）。
- **e-Tax は送信系仕様未入手なら feature-flag 隔離で保留**でき、他フェーズをブロックしない。
