# PRD: Kanean（ローカル単一ユーザー型 確定申告・会計システム）

> 商用クラウド会計サービスに相当する確定申告機能を、**誰でもセルフホストでき、かつ複数ユーザーで利用できる**形で実現する。
> まずは開発者本人が使うが、他者も使える設計とし、将来はデータ保全・上位機能を有料提供する余地を残す。
> 本書は要求仕様の確定版（v1）。設計・実装の上位文書として位置づける。

---

## 1. 背景・目的

### 1.1 背景
- 既存の商用クラウド会計サービスは月額課金・クラウド保管が前提で、データの主権・ランニングコスト・カスタマイズ性に制約がある。
- まず開発者本人の事業会計・確定申告を、**自分が管理できる環境（セルフホスト）**で完結させたい。
- 同じ仕組みを他者にも提供できるようにし、将来的には**データ保全や上位機能を有料**で提供する選択肢を持ちたい。

### 1.2 目的
- 銀行・カード・EC の取引データ取込から、仕訳・帳簿・固定資産・決算・確定申告書の作成、（将来的に）e-Tax 提出までを一気通貫で行う。
- 簿記・税務の正確性を担保し、青色申告（65万円控除）に耐える帳簿を生成する。
- **シングルユーザーのセルフホストでも、複数ユーザーのホスト運用でも、同一のコードベースで動く**構成とする。

### 1.3 提供形態
| 形態 | 説明 |
|---|---|
| セルフホスト（単独利用） | 個人が自分のマシンで起動し、本人のみ利用。データは手元に保管 |
| セルフホスト（少人数） | 1インスタンスを家族・知人など複数ユーザーで共有 |
| ホスト型サービス（将来） | 運営者がホストし、無料プラン＋有料プラン（データ保全・上位機能）を提供 |

### 1.4 成功の定義
- 1事業年度分の取引を取り込み、**青色申告決算書 + 確定申告書B + 消費税申告書（簡易課税）** を本システムだけで作成できる。
- 帳簿（仕訳帳・総勘定元帳）が複式簿記として整合し、貸借が一致する。
- 複数ユーザーが同一インスタンスを使っても、**各ユーザーの会計データが構造的に分離**されている。

## 2. ターゲット・前提

| 項目 | 内容 |
|---|---|
| 利用者 | **複数ユーザー対応**。当初は開発者本人のみだが、他者も利用可能な設計とする |
| 事業形態 | **個人事業主のみ**（法人は対象外） |
| 申告区分 | **青色申告**（複式簿記・65万円控除を前提） |
| 消費税 | **課税事業者・簡易課税**（インボイス対応。本則課税は対象外） |
| 固定資産 | **あり**（減価償却・少額特例・一括償却） |
| 家事按分 | **あり**（事業使用割合による経費按分） |
| 認証 | **持たない**。ローカルアプリとして `127.0.0.1` 限定で待ち受け、ネットワーク到達性を境界とする（[architecture.md] §5） |
| 課金 | **なし**（SaaS 化しない。自分専用のローカルアプリ） |
| 運用形態 | 自分のマシン上のローカルアプリ（Tauri デスクトップ化を予定）。サーバ運用・外部公開はしない |

### 2.1 明確な非スコープ（やらないこと）
- 法人会計・法人税申告
- 家計簿用途・資産管理（純粋な個人消費の可視化）
- 本則課税（消費税）方式
- 給与計算・年末調整・従業員管理
- きめ細かな権限管理 / 組織・チーム機能（1ユーザー=1事業主体を基本とする）
- マルチマシンでの水平スケール（当初は単一マシン前提）

## 3. 全体業務フロー

```
[取込] 銀行/カード CSV・EC履歴
   │
   ▼
[仕訳] 自動仕訳ルール → 手修正/手入力/振替 → 家事按分
   │
   ▼
[帳簿] 仕訳帳・総勘定元帳・補助元帳（自動生成）
   │
   ├──[固定資産] 資産登録 → 減価償却計算 → 期末に償却費を仕訳へ
   │
   ▼
[決算] 試算表 → 決算整理 → 青色申告決算書
   │
   ▼
[申告書] 確定申告書B / 消費税申告書（簡易課税）作成
   │
   ▼
[提出] （将来）e-Tax 用XML組成 → 電子署名 → 送信  ※当面はPDF出力→手動提出
```

## 4. 機能要求

優先度: **P0=MVP必須 / P1=本体機能 / P2=後フェーズ**

### 4.0 アクセス境界・アカウント（P0）

**認証機構は持たない**（ローカル単一ユーザーのデスクトップアプリ）。
アクセス制御はループバック限定バインドによるネットワーク境界で行う（[architecture.md] §5）。

| ID | 機能 | 優先 | 備考 |
|---|---|---|---|
| F-AUTH-1 | `127.0.0.1` 限定バインド | P0 | 唯一の防壁。設定で外部公開へ切り替えられない |
| F-AUTH-2 | 起動時の帳簿解決・専用DBの初期化 | P0 | 0冊なら1冊作成。複数帳簿を持てる（税理士が顧問先を N 冊） |
| F-AUTH-3 | ~~セッション管理・ログアウト~~ | — | 廃止（認証なし） |

| F-AUTH-5 | ~~認証方式の拡張余地~~ | — | 廃止 |
| F-AUTH-6 | データ一括エクスポート | P1 | per-user DB＋証憑の zip 書き出し |

## 5. 非機能要件

| 分類 | 要件 |
|---|---|
| データ保管 | **SQLite**。後述のとおり **1ユーザー=1DBファイル**（データプレーン）＋ 共通の **コントロールプレーンDB**（認証・課金）の2層構成 |
| データ分離 | 会計データは帳簿ごとに物理ファイルが分かれ、他帳簿への到達が構造的に起きない |
| バックアップ | **毎月メールで自動バックアップ送付**（ファイル単位）。将来の有料プランでは継続レプリ・世代管理。リストア手順を文書化 |
| アクセス境界 | `127.0.0.1` 限定バインド。認証・セッションは持たない |
| セキュリティ | 金融データ・（将来）マイナンバーを扱う。外部公開しないことを前提とし、保存データの暗号化（SQLCipher）は将来課題 |
| 可用性 | 当面は単一マシン運用で高可用性は不要。将来のホスト型でSLAを検討 |
| 同時実行 | per-user DBにより各ユーザーは実質シングルライター。**SQLiteはWALモードで運用** |
| 監査性 | 仕訳の追加・修正履歴を追える（青色申告の帳簿要件） |
| 性能 | 1ユーザーあたり年間数千〜1万件規模の取引を想定。応答性は最低限で可 |
| 保守性 | 税制改正（税率・耐用年数・様式）に追従できるようルールを外部データ化。**N個の帳簿DBに走るマイグレーション機構**を用意 |
| スケール | 単一マシン前提。マルチマシン化する場合は LiteFS / Turso 等の共有ストレージ層が必要（将来検討） |

### 5.1 データアーキテクチャ（方針確定）
```
control plane（共通1DB）          data plane（帳簿ごと）
  control.sqlite                   books/{book_id}.sqlite
   ├ books（帳簿レジストリ）          ├ accounts（勘定科目）
   └ backup_status                   ├ journal_entries（仕訳）
                                     ├ ledgers / 補助元帳
                                     ├ fixed_assets（固定資産）
                                     ├ invoices（請求書）
                                     └ … 会計データ一式
```
- **ユーザー横断で集計・参照が要るもの**（認証・課金・バックアップ状態）はコントロールプレーンに集約。
- **会計データ**はユーザー専用ファイルに隔離。
- アプリは「対象帳簿の解決 → book_id から該当DBファイルを開く」ルーティング層を1枚挟む。
- リポジトリ層を抽象化し、将来コントロールプレーンのみ別DBMS（例: PostgreSQL）へ移行できる逃げ道を残す。

## 6. 開発フェーズ（段階計画）

| フェーズ | 範囲 | 着地点 |
|---|---|---|
| **Phase 0** | アクセス境界・データ2層構成（F-AUTH） | ローカルで起動し、オーナーのDBが作られる |
| **Phase 1** | 取込→仕訳→帳簿出力（F-IMP/JNL/BOK） | 複式簿記の帳簿がCSVで出る |
| **Phase 2** | 固定資産（F-FA） | 減価償却が仕訳に反映される |
| **Phase 3** | 決算書・申告書PDF（F-FIN） | 青色決算書・申告書がPDFで出る＝**手動提出可能** |
| **Phase 4** | 請求書（F-INV） | 請求〜売掛仕訳の自動化 |
| **Phase 5** | e-Tax 電子提出（F-SUB） | 電子申告完結 |
| ~~**Phase 6**~~ | ~~プラン・課金（F-PLAN）~~ | **撤回**（SaaS化しない） |

> ※ データ2層構成（Phase 0）を先に据えたことで、将来の複数帳簿（税理士が顧問先を N 冊持つ）への拡張余地が残っている。
> ※ e-Tax提出（Phase 5）は難易度・法的確認が大きいため、Phase 3 のPDF手動提出を実用上のゴールとして先に確保する。

## 7. 主要リスク・要検討事項

| # | リスク | 内容 | 対応方針 |
|---|---|---|---|
| R-1 | EC 明細取得 | Amazon/楽天は規約・2FA・DOM変更で壊れやすく、本体にスクレイパーを内蔵すると保守負債＋配布不可 | **取得を本体から切り離す**：外部AIスキル（Claude Code→将来ローカルLLM）がLLMで意味抽出（DOM変更に強い）。月1の低頻度。本体は中間フォーマット受け口のみ（F-IMP-6）。**金額はLLM鵜呑みにせず生証跡保存＋draft承認**で担保。製品配布もスキル配布で対応（対象＝エンジニア）。手動入力を常時フォールバック |
| R-2 | e-Tax連携 | XMLスキーマ・電子署名・NFCの実装難度が高い | Phase 5に分離。PDF手動提出を先行 |
| R-3 | 税制改正追従 | 税率・耐用年数・申告様式は年次で変わる | 税率/科目/様式をコードから分離しデータ化 |
| R-4 | 簿記の正確性 | 計算誤りは申告ミスに直結 | 会計計算は期待値テスト必須（テスト計画で担保） |
| R-5 | インボイス | 適格請求書の保存・記載要件 | 請求書・仕入の区分を仕様化 |
| R-6 | per-user DBのマイグレーション | スキーマ変更を全ユーザーDBに整合的に適用する必要 | 全DB走査のマイグレーションランナーを基盤として用意 |
| R-7 | 単一マシンのスケール限界 | SQLiteはローカルディスク前提でアプリ複数台に弱い | 単一マシンを前提に据え、必要時のみLiteFS/Turso等を検討 |
| R-8 | データ保全（有料）の責務 | 他者の資産データを預かる法的・運用責任 | 暗号化・バックアップ・復元・退会時削除を仕様化 |

## 8. 用語集（抜粋）

| 用語 | 意味 |
|---|---|
| 青色申告 | 複式簿記による記帳で最大65万円の特別控除が受けられる申告制度 |
| 簡易課税 | 売上にみなし仕入率を掛けて消費税を計算する方式（事業区分ごとに率が異なる） |
| 家事按分 | 事業と私用が混在する支出を事業使用割合で経費に按分すること |
| 一括償却資産 | 取得価額10万円以上20万円未満を3年均等で償却する制度 |
| 少額減価償却資産特例 | 青色申告者が30万円未満の資産を一時に経費算入できる特例 |
