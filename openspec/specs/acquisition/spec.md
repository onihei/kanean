# acquisition Specification

## Purpose

連携サービス（EC・銀行・カード）の明細をアプリ自身が巡回して取得する振る舞い。人が見える状態での
ログイン、長時間ジョブとしての進行、取得結果の自己検算、分類のために外へ出す情報の範囲、
サイト改変への較正、失敗時の診断を定める。取得したものを仕訳にする契約は [[skill-import]] が持つ。
（[docs/acquisition-skill-spec.md]・[docs/csv-format.md] §4）

## Requirements

### Requirement: 人が見える巡回と人への委譲

システムは巡回を**人が見えるブラウザ画面**で行い、ログイン・2要素認証・CAPTCHA は人に委ねる SHALL。
認証情報をアプリまたは外部のクライアントに保持させてはならない。人の介在なしに巡回を開始してはならない。

#### Scenario: 画面が見える状態で巡回する

- **WHEN** 取込を開始する
- **THEN** 巡回の様子が見えるウィンドウが開き、人が監視・介入できる状態になる

#### Scenario: ログインを人に委ねる

- **WHEN** 巡回中にログインまたは2要素認証が要求される
- **THEN** 巡回を一時停止して人の入力を待ち、認証情報をアプリが受け取ることはない

#### Scenario: 無人では始まらない

- **WHEN** 人が起動していない契機（時刻到来など）で取込が始まろうとする
- **THEN** 取込は開始されない

#### Scenario: 人が中断できる

- **WHEN** 進行中の取込を人が中断する
- **THEN** 巡回を止め、そこまでに取得した分を投入せずに終える

### Requirement: 長時間ジョブとしての進行

システムは取込を**開始と結果取得が分かれた進行**として扱い、進行中の状態を問い合わせられるようにする SHALL。
人のログイン待ちを含むため、単一の同期的な応答で完結させてはならない。
取込は UI からも [[mcp-server]] からも開始でき、どちらから開始しても同じ進行を辿る。

**取込は分類を待たずに完了する。** 科目が決まっていない明細も未確定として投入され、
分類は取込の後工程として別に行う（下記「未確定の分類」）。

**部分成功を成功と見分けられるようにする。** 巡回で一部の明細（注文）が取得できないまま投入を
終えた場合も取込は完了として扱うが、取得できなかった件数と各失敗の識別情報・理由を結果に示す SHALL。
黙って完了扱いにして失敗を隠してはならない。

**部分成功が起きうるかはサイトごとの失敗粒度の宣言に従う SHALL。** 明細単位（EC＝注文ごとに独立して
取得できるサイト）だけが部分成功をとりうる。全体単位（銀行・カード＝残高チェーン/請求額の自己検算が
全明細にまたがるサイト）に部分成功は存在せず、検算が崩れれば取込全体を失敗にする（部分投入をしない）。

#### Scenario: 開始してすぐ進行を返す

- **WHEN** 取込の開始を要求する
- **THEN** 巡回の完了を待たずに、その取込を識別できる情報と現在の状態を返す

#### Scenario: 進行状態を問い合わせられる

- **WHEN** 進行中の取込の状態を問い合わせる
- **THEN** 「ログイン待ち」「取得中」「完了」「失敗」「中断」のいずれかと、進捗が分かる情報を返す

#### Scenario: 分類を待たずに完了する

- **WHEN** 巡回で得た明細を投入し終える
- **THEN** 科目が決まっていない明細があっても取込は完了し、その件数を未確定として示す

#### Scenario: どちらの入口でも同じ進行になる

- **WHEN** 同じ連携サービスの取込を UI から開始した場合と外部クライアントから開始した場合を比べる
- **THEN** 辿る状態と最終結果は一致する

#### Scenario: 同じ対象を二重に走らせない

- **WHEN** 同一の連携サービスの取込が既に進行している状態で、もう一度開始を要求する
- **THEN** 新しい巡回を始めず、進行中の取込を示す

#### Scenario: 取得できなかった明細を件数と理由で示す

- **WHEN** 巡回で一部の明細（注文）が取得できないまま投入を終える
- **THEN** 取込は完了として扱いつつ、結果に「取得できなかった件数」を示し、
  完了メッセージに再実行で再取得を試みられる旨を含める
- **AND** 各失敗について識別情報（注文ID・日付）と理由を警告として残し、UI で一覧できる

#### Scenario: 銀行・カードは部分成功にしない

- **WHEN** 失敗粒度を「全体」と宣言したサイト（銀行・カード）の巡回で一部の明細が取得できない
- **THEN** 取込全体を失敗として扱い、部分的な投入は行わない（検算を満たさない明細を帳簿へ入れない）

#### Scenario: 全件取得できた場合は失敗表示を出さない

- **WHEN** 巡回対象のすべての明細を取得して投入を終える
- **THEN** 取得できなかった件数や失敗の警告は表示しない

### Requirement: 取得結果の自己検算

システムは取得した明細を投入前に自己検算し、**合わなければ投入しない** SHALL。
検算の規約は取得経路によらず同一とする。

#### Scenario: 銀行は残高チェーンで検算する

- **WHEN** 銀行口座の入出金明細を取得する
- **THEN** 差引残高の連鎖が整合することを確認し、崩れていれば投入せず人へ報告する

#### Scenario: カードは請求額との一致で検算する

- **WHEN** カードの利用明細を取得する
- **THEN** 利用額の合計が請求額と一致することを確認し、合わなければ投入せず人へ報告する

#### Scenario: EC は注文合計との一致で検算する

- **WHEN** EC の注文明細を取得する
- **THEN** 明細の合計に送料とポイント利用を加減した額が注文合計と一致することを確認する
- **AND** 一致しない場合も取込は継続しつつ、不一致を警告として残す

#### Scenario: 抽出に確信が持てない場合は中断する

- **WHEN** 想定外の画面に遭遇する、または金額や品名を取り出せない
- **THEN** 推測で値を作らず、そこで中断して人へ報告する

### Requirement: 取得範囲と取りこぼしの防止

システムは取得対象を**開いている会計期間と前回取得以降の範囲の重なり**に限り、その範囲を
**古い方から連続して**取得する SHALL。範囲外は登録せず、除外したことを件数として示す。

**差分の起点は「連続して取得できた終端」を正確に指す SHALL。** 部分成功（一部の明細が取得できない
まま完了）のときは、最初に取得できなかった明細の日付の**前日**まで起点を前進させ、それより先へは
進めない。これにより、失敗した明細は必ず次回の既定の取得範囲に含まれ、取りこぼしが恒久化しない。

#### Scenario: 開いている期間だけを取得する

- **WHEN** 取引日が開いている会計期間の外にある明細を取得する
- **THEN** 登録せず、除外した件数を結果に示す

#### Scenario: 古い方から連続して取得する

- **WHEN** 前回取得以降に複数の明細が増えている
- **THEN** 古い方から連続して取得し、新しいものだけを先に取り込んで途中を飛ばすことはない

#### Scenario: 範囲を限った取得では前進させない

- **WHEN** 人が範囲を限って一部だけを取得する
- **THEN** 差分の起点を取得できていない範囲より先へ進めず、残りが次回の対象として残る

#### Scenario: 部分成功では連続して取得できた終端まで前進する

- **WHEN** 一部の明細（注文）が取得できないまま取込を終える
- **THEN** 差分の起点を「最初に取得できなかった明細の日付の前日」まで前進させ、それより先へは進めない
- **AND** 次回の既定の取得範囲に、取得できなかった明細の日付が含まれる

#### Scenario: 初回取込の部分失敗でも取りこぼしを恒久化しない

- **WHEN** 差分の起点が未記録（その連携サービスの初回取込）の状態で部分成功に終わる
- **THEN** 次回の既定の取得範囲は取得できなかった明細の日付を含み、
  取込済みのより新しい明細の日付まで起点が飛ぶことはない

#### Scenario: 前進の余地が無い部分成功では前進させない

- **WHEN** 取得できた明細が 1 件も無い、または最初の失敗が取得範囲の先頭にある状態で部分成功に終わる
- **THEN** 差分の起点を変えない

### Requirement: 未確定の分類

システムは科目が決まっていない draft を**未確定として一覧でき、後から科目を当てられる** SHALL。
分類は人が画面で行っても外部のクライアントが行っても、同じ draft に対する同じ操作とする。
取込の経路（巡回・CSV・手入力）によらず同じ操作が効かなければならない。

#### Scenario: 未確定を一覧できる

- **WHEN** 未確定の分類対象を求める
- **THEN** 科目が決まっていない draft の分類対象の文字（品名・摘要）を、重複をまとめて返す

#### Scenario: 科目を当てる

- **WHEN** 分類対象に科目を指定する
- **THEN** 対応する未確定の draft の科目が置き換わり、確定はされない

#### Scenario: 判断の根拠を残す

- **WHEN** 科目とともに判断の理由・確信度が与えられる
- **THEN** それを draft の由来として記録し、確定する人が読める形にする（[[web-app]]）
- **AND** 根拠が無くても科目は当たる（そのぶん確信度による絞り込みは効かない）

#### Scenario: 人が先に片付けていても壊れない

- **WHEN** 分類を受け取った時点で、その対象が既に人の操作で解消されている
- **THEN** 何も変更せず、適用が0件だったことを示す（失敗としない）

#### Scenario: 確定済みには当てない

- **WHEN** 既に確定された仕訳に対して分類を当てようとする
- **THEN** 変更せず、確定済みである旨を示す

### Requirement: 分類方針の提示と編集

システムは科目の当て方の方針を**利用者が編集できるデータ**として保持し、分類を委ねる際に渡す SHALL。
外部のクライアントは利用者のファイルを読めないため、渡さなければ方針は判断に反映されない。
方針が指示できるのは分類の判断のみであり、期間ゲート・冪等・科目検証といった
システムの権威（[[skill-import]]）を変えてはならない。

#### Scenario: 方針を添えて分類を委ねる

- **WHEN** 未確定の分類対象を求める
- **THEN** その帳簿の分類方針を一緒に返す

#### Scenario: 方針を編集する

- **WHEN** 利用者が分類方針を書き換える
- **THEN** 以後の分類ではその方針が渡る

#### Scenario: 既定へ戻せる

- **WHEN** 編集した方針を取り消す
- **THEN** 同梱の既定の方針へ戻る

#### Scenario: 方針で権威は変わらない

- **WHEN** 方針に、期間外の取込や重複の許容を求める記述が含まれる
- **THEN** システムの検証は変わらず、期間ゲート・冪等はそのまま働く

### Requirement: 分類のために外へ出す情報の最小化

システムは科目分類を外部のクライアントに委ねる際、**判断に必要な文字情報のみ**を渡す SHALL。
金額・取引識別子・残高・証憑参照をアプリの外へ出してはならない。分類の結果は
アプリが保持している draft へ突き合わせて適用する。

#### Scenario: 品名・摘要だけを渡す

- **WHEN** 未確定の分類を外部クライアントへ委ねる
- **THEN** 渡すのは分類対象の文字（品名・摘要）とその識別子のみで、金額や残高は含まれない

#### Scenario: 参考にする確定履歴は絞って渡す

- **WHEN** 確定履歴を添える
- **THEN** 今回の分類対象に関連するものだけを、直近の実績を優先して上限件数まで渡す
- **AND** 複数の連携サービスが混ざる場合は、それぞれの由来について引き、どの由来かを示す

#### Scenario: 識別子から取引を辿れない

- **WHEN** 分類対象に付す識別子を決める
- **THEN** 識別子は分類対象の文字から決まり、単体では取引を特定できない

#### Scenario: 分類結果を突き合わせて適用する

- **WHEN** 外部クライアントから分類結果を受け取る
- **THEN** アプリが保持している draft に識別子で突き合わせて適用する
- **AND** 対応しない識別子は適用せず、その件数を示す

#### Scenario: 分類が返らなくても取得は無駄にならない

- **WHEN** 分類を受け取る前に会話が途切れる
- **THEN** 取り込んだ draft は帳簿に残り、人が画面で分類・確定できる

### Requirement: サイト較正の外出しと更新

システムはサイトごとの較正（画面上の要素の同定に用いる値）を**プログラムから分離したデータ**として保持し、
アプリの更新なしに差し替えられるようにする SHALL。較正の更新として**データのみを受け付け**、
実行されるプログラムを受け付けてはならない。

#### Scenario: 較正を更新して再試行できる

- **WHEN** サイトの変更で巡回が失敗し、較正の更新が与えられる
- **THEN** アプリを更新することなく、更新後の較正で巡回を再試行できる

#### Scenario: プログラムを受け付けない

- **WHEN** 較正の更新としてプログラムに相当するものが与えられる
- **THEN** 受け付けず、拒否したことを示す

#### Scenario: 壊れた較正から復帰できる

- **WHEN** 更新した較正で巡回が失敗し続ける
- **THEN** 配布時の較正へ戻す手段があり、以前動いていた状態に復帰できる

### Requirement: 失敗時の診断

システムは巡回の失敗時に、**どこで・何が起きたか**を後から調べられる形で残す SHALL。
失敗を汎用のエラーとして片付けてはならない。

#### Scenario: 失敗の手掛かりを残す

- **WHEN** 巡回が失敗する
- **THEN** 失敗した手順・そのときの所在・画面の状態を、後から参照できる形で残す

#### Scenario: 診断を取り出せる

- **WHEN** 直近の失敗の診断を要求する
- **THEN** 較正の見直しに足る情報（どの要素が見つからなかったか、そのとき画面に何があったか）を返す

#### Scenario: 認証情報を診断に残さない

- **WHEN** 失敗の手掛かりを残す
- **THEN** 入力された認証情報やセッションの識別子は含めない

### Requirement: 投入は既存の取込契約を通る

システムは巡回で得た明細を、**取得経路によらず同一の権威**（期間ゲート・冪等・科目検証）を通して
投入する SHALL（[[skill-import]]）。投入結果はすべて draft とし、確定は人が UI で行う。
**投入は分類の有無を待たない。**

#### Scenario: すべて draft として投入する

- **WHEN** 巡回で得た明細を投入する
- **THEN** 生成される仕訳はすべて draft であり、確定されない

#### Scenario: 科目が決まっていなくても投入する

- **WHEN** 科目が決まっていない明細を投入する
- **THEN** 未確定勘定の draft として帳簿に並び、未確定の件数として示される

#### Scenario: 手動取込と二重計上しない

- **WHEN** 同一の口座について、巡回による取込と手動の取込を併用する
- **THEN** 同じ取引が二重に登録されない

#### Scenario: 経路が違っても結果が同じになる

- **WHEN** 同じ期間の同じ連携サービスを、アプリ内の巡回と外部のスキル経路のそれぞれで取り込む
- **THEN** 生成される仕訳は一致する

#### Scenario: 件数を黙って落とさない

- **WHEN** 投入が完了する
- **THEN** 受理・重複・期間外除外・未確定・警告の件数をそれぞれ示す

### Requirement: 巡回セッションの秘密としての扱い

システムは巡回で保持するログイン状態を**パスワードに準じる秘密**として扱う SHALL。
外部への同期・エクスポート・バックアップの対象に含めてはならない。

#### Scenario: エクスポートに含めない

- **WHEN** 帳簿のエクスポートを行う
- **THEN** 巡回のログイン状態は含まれない

#### Scenario: 終了後に待ち受けを残さない

- **WHEN** 巡回の途中でアプリを終了する
- **THEN** 巡回のウィンドウとプロセスは終了し、会計データへ到達しうる待ち受けは残らない（[[desktop-app]]）

#### Scenario: ログイン状態を破棄できる

- **WHEN** 人が連携のログイン状態の破棄を求める
- **THEN** 保持していたログイン状態を消去し、次回は再ログインが必要になる
