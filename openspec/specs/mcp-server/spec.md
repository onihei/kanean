# mcp-server Specification

## Purpose

MCP クライアント（Claude Desktop 等）から Kanean の会計データを扱えるようにする窓口。
露出する動詞の範囲・帳簿の解決・前提不足時の誘導・アプリ未起動時の扱い・1クリックで導入できる
配布形態を定める。到達性の境界は [[local-access]]、アプリの起動終了は [[desktop-app]] が持つ。

## Requirements

### Requirement: ローカルアプリへの MCP 接続

システムは MCP クライアントからの接続を受け、同一マシンで動作するアプリの API へ中継する SHALL。
中継のために新たな待ち受け（TCP ポート等）を作ってはならない。到達性の境界は [[local-access]] に従う。

#### Scenario: 起動中のアプリへ接続する

- **WHEN** アプリが起動している状態で MCP クライアントが接続する
- **THEN** ツールの一覧が取得でき、会計データを問い合わせられる

#### Scenario: 新しい到達経路を作らない

- **WHEN** MCP 接続が確立している
- **THEN** アプリの既存のローカル経路以外に、会計データへ到達できる待ち受けは増えていない

#### Scenario: 既定ではローカルソケットしか試さない

- **WHEN** 接続先が明示されていない状態でツールが呼ばれる
- **THEN** ローカルソケットのみを試し、TCP ポートへの接続を試みない
- **AND** ソケットが無ければ「アプリが起動していない」と判別する（別経路を探さない）

#### Scenario: 明示された開発用の経路でも同じツールが動く

- **WHEN** 開発用の接続先が明示的に指定されている
- **THEN** 同じツール群が同じ結果を返す

### Requirement: アプリ未起動の検知と確認付き起動

システムはアプリが起動していないことを判別し、**利用者の確認を得てから**起動して処理を再試行する SHALL。
確認なしにアプリを起動してはならず、判別できない失敗を汎用エラーとして返してもならない。

#### Scenario: 未起動を判別して伝える

- **WHEN** アプリが起動していない状態でツールが呼ばれる
- **THEN** 「Kanean が起動していない」と判別できる結果を返す
- **AND** 起動してよいかの確認を求める

#### Scenario: 確認を得て起動し再試行する

- **WHEN** 利用者が起動を承諾する
- **THEN** アプリを起動し、到達可能になってから元の処理を1回だけ再試行する

#### Scenario: 断られたら起動しない

- **WHEN** 利用者が起動を承諾しない
- **THEN** アプリを起動せず、処理を行わずに終える

#### Scenario: 起動を待ちきれない場合を報告する

- **WHEN** 起動を試みたが所定時間内に到達可能にならない
- **THEN** 待機を打ち切り、起動できなかったことを報告する（別経路を探して代替しない）

#### Scenario: 途中でアプリが終了した場合を報告する

- **WHEN** 処理の途中でアプリが終了し到達できなくなる
- **THEN** 黙って再試行せず、アプリが終了したことを報告する

### Requirement: 露出する動詞の範囲

システムは MCP ツールとして露出する動詞を、**会計データの読み取りを中心とした限られた集合**に保つ SHALL。
アプリの HTTP ルートを機械的に写像してはならない。読み取りは [[reports]] の規約に従い、
確定済み（`confirmed`）の仕訳のみを集計に用いる。

#### Scenario: 会計データを問い合わせられる

- **WHEN** 期間・科目を指定して残高や帳票を問い合わせる
- **THEN** 試算表・損益計算書・貸借対照表・元帳/補助元帳・仕訳の検索・科目残高・納税予測の結果を返す

#### Scenario: 申告の準備を問い合わせられる

- **WHEN** 申告前チェックまたは入力指示書を問い合わせる
- **THEN** [[filing]] の規約に従い、precheck の判定結果と作成コーナー向け入力指示書を返す

#### Scenario: 集計に未確定を混ぜない

- **WHEN** 承認待ちの draft 仕訳が存在する状態で帳票を問い合わせる
- **THEN** 集計には `confirmed` の仕訳のみを用いる
- **AND** 未確定が存在することは件数として別に示す

#### Scenario: ルートの総数に比例して増えない

- **WHEN** アプリが多数の HTTP ルートを持つ
- **THEN** 露出するツールはそれに比例せず、意味のある動詞の単位に集約されている

### Requirement: 書き込みの限定と承認の非委譲

システムが書き込みとして露出してよい操作は、**連携サービスの登録・取込の進行・サイト較正の更新・
レシートの取込・申告の完了記録に限る** SHALL。
仕訳の確定・取消・削除、マスタ・期首残高・税区分の編集、draft の承認を行うツールを露出してはならない。
承認は [[skill-import]] の原則どおり利用者が UI で行う。

取込に関して露出してよいのは、開始・状態の問い合わせ・**未確定 draft の分類**・失敗の診断・較正の更新であり、
いずれも [[acquisition]] の規約に従う。分類のために受け取れる情報は品名・摘要とその識別子に限られ、
較正の更新として受け付けるのはデータのみでプログラムを受け付けない。
分類は科目を**提案として置き換える**にとどまり、確定はしない。

レシートに関して露出してよい書き込みは、[[receipt-inbox]] の規約に従う **現金レシートの draft 起票と
証憑の添付**に限る。カード払いのレシートは突合候補の提示のみで、起票する経路を持たない。
いずれも draft に留まり、確定はしない。

申告に関して露出してよい書き込みは、[[filing]] の完了記録の作成と控えの添付に限る。
記録の削除は UI で行う。

#### Scenario: 連携サービスを追加できる

- **WHEN** 追加したい連携サービスを指定する
- **THEN** 登録に必要な選択肢（勘定科目・補助科目など）を提示して確認を得たうえで登録する

#### Scenario: 取込を開始して進行を追える

- **WHEN** 連携サービスを指定して取込の開始を要求する
- **THEN** 巡回の完了を待たずに識別子と状態を返し、以後その状態を問い合わせられる

#### Scenario: 取込は分類を待たずに終わる

- **WHEN** 取込の完了を確かめる
- **THEN** 受理・重複・期間外・未確定の件数が返り、未確定があっても取込は完了している

#### Scenario: 未確定に科目を当てる

- **WHEN** 未確定の分類対象を求め、識別子ごとの科目を返す
- **THEN** アプリ側で draft に突き合わせて科目を置き換え、適用件数と対応しなかった件数を返す
- **AND** 確定はされず、利用者の確認へ誘導される

#### Scenario: 判断の材料が渡される

- **WHEN** 未確定の分類対象を求める
- **THEN** 分類方針と、関連する確定履歴が一緒に返る（利用者のファイルを読みに行かせない）

#### Scenario: 判断の根拠を返させる

- **WHEN** 科目を当てる
- **THEN** 理由と確信度を添えることが求められ、利用者の画面でそれが読める

#### Scenario: 失敗を診断して較正を直せる

- **WHEN** 巡回が失敗した取込の診断を要求する
- **THEN** 失敗した手順と画面の状態を返し、較正の更新を受け付ける

#### Scenario: 較正の更新でプログラムを受け付けない

- **WHEN** 較正の更新としてプログラムに相当するものを渡す
- **THEN** 受け付けず、拒否したことを返す

#### Scenario: 現金レシートを起票できる

- **WHEN** 現金のレシートを画像と撮影時の文脈とともに渡す
- **THEN** [[skill-import]] の規約で draft 仕訳が作られ、当該画像が証憑として添付される
- **AND** 同じ画像を再び渡しても仕訳と添付は増えない

#### Scenario: カードのレシートを起票するツールが存在しない

- **WHEN** カード払いのレシートを渡す
- **THEN** 返るのは既存明細の突合候補のみで、それを起票するツールは存在しない

#### Scenario: 申告の完了を記録できる

- **WHEN** 転記手順の完遂後に、年分・税目・提出日・受付番号と控え PDF を渡して完了記録を要求する
- **THEN** [[filing]] の完了記録として保存され、帳簿の仕訳・設定は変更されない

#### Scenario: 完了記録を削除するツールが存在しない

- **WHEN** 完了記録を削除しようとする
- **THEN** それを行うツールは存在せず、UI での操作へ誘導される

#### Scenario: draft を確定するツールが存在しない

- **WHEN** 承認待ちの draft 仕訳を確定しようとする
- **THEN** それを行うツールは存在せず、UI での承認へ誘導される

#### Scenario: 設定を書き換えるツールが存在しない

- **WHEN** 期首残高・勘定科目・税区分を変更しようとする
- **THEN** それを行うツールは存在せず、UI での操作へ誘導される

### Requirement: 対象帳簿の解決と曖昧さの提示

システムは対象帳簿を [[books]] の規約に従って解決し、決まらないときは**推測せず選択肢を返す** SHALL。

#### Scenario: 帳簿が1冊なら指定を求めない

- **WHEN** アクティブな帳簿が1冊しかない状態でツールを呼ぶ
- **THEN** 帳簿の指定を求めずにその帳簿を対象とする

#### Scenario: 2冊以上なら選択肢を返す

- **WHEN** アクティブな帳簿が2冊以上ある状態で帳簿を指定せずにツールを呼ぶ
- **THEN** 処理を行わず、選択可能な帳簿の識別子と名称を返して確認を促す

### Requirement: 次の一手の提示

システムはツールの結果に、**次に何をすべきか**を含める SHALL。前提が満たされないときは、
何が足りないかと選べる選択肢を返す。承認・編集が必要なときはアプリの該当画面を開くリンクを添える。
黙って空の結果を返してはならない。

#### Scenario: 前提不足を選択肢付きで返す

- **WHEN** 会計年度が存在しない状態で帳票を問い合わせる
- **THEN** 会計年度が無いことと、作成のための導線を返す（空の帳票を返さない）

#### Scenario: 承認へ戻す導線を返す

- **WHEN** 承認待ちの draft がある状態でその件数を問い合わせる
- **THEN** 件数とともに、アプリの該当画面を開くリンクを返す

#### Scenario: リンクからアプリの該当画面が開く

- **WHEN** 返されたリンクを開く
- **THEN** Kanean が前面に出て該当画面が表示される

#### Scenario: 除外や重複を黙って落とさない

- **WHEN** 問い合わせや登録の結果に除外・重複・未確定が含まれる
- **THEN** それぞれの件数を結果に明示する

### Requirement: 定型手順の配布

システムは典型的な作業の入口を MCP クライアント側へ提供する SHALL。
利用者に Kanean 用のスキルその他の追加物を導入させてはならない。

#### Scenario: 手順が入口として現れる

- **WHEN** 利用者が MCP クライアントで Kanean の定型作業を探す
- **THEN** 「今月の状況」「決算前チェック」「確定申告の転記」「レシートの取込」等の入口が提示され、そこから会話を始められる

#### Scenario: 確定申告の転記手順が規約を運ぶ

- **WHEN** 利用者が「確定申告の転記」の入口から会話を始める
- **THEN** 提示される手順は [[filing]] の転記手順の規約（転記値は入力指示書のみ・認証と送信は利用者・
  検算一致の確認）を含んでいる

#### Scenario: レシートの取込手順が規約を運ぶ

- **WHEN** 利用者が「レシートの取込」の入口から会話を始める
- **THEN** 提示される手順は [[receipt-inbox]] の規約（画像とメタの対が揃った件のみ扱う・現金は起票しカードは
  突合のみ・登録と証憑保存の完了を確認してから中継コピーを削除する・未登録のものを消さない）を含んでいる

#### Scenario: 追加の導入物を要求しない

- **WHEN** 利用者が Kanean を MCP クライアントで使い始める
- **THEN** 導入するものは Kanean 本体と MCP バンドルのみで、別途スキルを入れる必要がない

### Requirement: 1クリックで導入できる配布形態

システムは MCP サーバを、対応クライアントへ**ドラッグ＆ドロップ相当の操作で導入できる単一ファイル**として
提供する SHALL。利用者にもアプリにも、クライアントの設定ファイルを手で書き換えさせてはならない。

#### Scenario: バンドルを書き出して提示する

- **WHEN** 利用者が設定画面から連携の導線を実行する（[[web-app]]）
- **THEN** 導入用のバンドルファイルが書き出され、その場所と導入手順が提示される

#### Scenario: 設定ファイルを手書きしない

- **WHEN** 利用者がバンドルを MCP クライアントへ導入する
- **THEN** クライアントの設定ファイルを開くことも編集することもなく接続が成立する

#### Scenario: 追加のランタイムを要求しない

- **WHEN** Node.js も pnpm も導入していないマシンでバンドルを導入する
- **THEN** そのまま接続でき、会計データを問い合わせられる

### Requirement: クライアントの版の表明と一致の要求

システムは MCP クライアントに自身の版を表明させ、**アプリに同梱された版と一致する場合にのみ**
会計データの要求を処理する SHALL。一致しない要求は処理してはならず、入れ直しの手順を伴う拒否として返す。
版を表明しない要求も「一致しない」として扱う（判別できない要求を通してはならない）。

**到達確認の経路はこの拒否の対象外とする。** 到達確認まで拒否すると、クライアントからは
アプリが起動していない状態と区別できなくなり、利用者へ誤った次の一手を案内してしまう。

#### Scenario: 一致する版のクライアントは通常どおり扱う

- **WHEN** 同梱された版と一致する版を表明したクライアントが会計データを要求する
- **THEN** これまでどおり結果を返す

#### Scenario: 一致しない版を拒否する

- **WHEN** 同梱された版と一致しない版を表明したクライアントが会計データを要求する
- **THEN** 要求を処理せず、使用中の版と同梱の版を示した拒否を返す
- **AND** 設定画面から書き出して入れ直す手順を次の一手として伴う

#### Scenario: 版を表明しないクライアントを拒否する

- **WHEN** 版を表明しないクライアントが会計データを要求する
- **THEN** 一致しない版と同じ拒否を返す（別の扱いをしない）

#### Scenario: 到達確認は拒否しない

- **WHEN** 一致しない版のクライアントが到達確認を行う
- **THEN** 到達できると応答する（アプリが起動していないかのように振る舞わない）

#### Scenario: 拒否の理由が利用者へ届く

- **WHEN** 版が一致せず拒否されたクライアントが、その結果を利用者へ提示する
- **THEN** クライアント側を更新していなくても、入れ直しが必要である旨と手順が利用者に読める形で提示される

#### Scenario: 拒否された要求は会計データを変えない

- **WHEN** 版が一致しないクライアントが書き込みを伴う操作を要求する
- **THEN** 帳簿は変更されない

### Requirement: 連携の到達の記録

システムは MCP クライアントが到達した事実と、そのとき表明された版を記録する SHALL。
記録は特定の帳簿ではなくアプリ全体に属する。**一度も到達していない状態を区別できなければならない。**

拒否した要求も到達として記録する。拒否こそが「古い版が使われている」ことの観測だからである。

#### Scenario: 到達を記録する

- **WHEN** MCP クライアントが会計データを要求する
- **THEN** 到達した時刻と表明された版を記録する

#### Scenario: 拒否した要求も記録する

- **WHEN** 版が一致しないクライアントの要求を拒否する
- **THEN** その到達と版を記録する（一致しない版が使われていることが後から分かる）

#### Scenario: 一度も到達していない状態を区別する

- **WHEN** MCP クライアントが一度も到達していない
- **THEN** 記録が無いことをもって「到達を観測していない」と判別できる
- **AND** それを「クライアントが導入されていない」とは扱わない（アプリからは判別できないため）

#### Scenario: 帳簿を切り替えても記録は変わらない

- **WHEN** 対象の帳簿を切り替える
- **THEN** 到達の記録は同じものが参照される
