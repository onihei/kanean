## Context

見るべき前提は [proposal.md](./proposal.md) の Why と Issue #112。ここでは設計に効く制約だけを挙げる。

- **本体は TCP を開かない**（[[local-access]]）。端末→本体の直接通信は選択肢に無い
- **利用者に追加の導入物を要求できない**（[[mcp-server]]「追加の導入物を要求しない」）。
  Mac 側の処理を Claude Code スキルとして別配布する案は**この規約と衝突する**
- 受け皿は既にある。[[skill-import]] は取得手段に依存しない中間契約で、[[attachments]] は
  HEIC を受理し SHA-256 を記録済み
- リポジトリは TS モノレポ（pnpm workspace = `packages/*`）。Dart/Flutter は別エコシステム

## Goals / Non-Goals

**Goals:**

- 自前のサーバ・アカウント・鍵管理を一切増やさずに双方向を成立させる
- 端末側と Mac 側が守る契約を**1 つの定義から**導き、片側だけ直して壊れる状態を作らない
- Android を後から足すときに、契約とアプリのコードを書き直さないで済む形にする

**Non-Goals:**

- 撮影品質の作り込み（長レシート・自動シャッター等）。v1 は簡易検査までとし、Tier ① の残りは後続
- 走行距離ログ・固定資産の現物写真（Issue #112 の Tier ④）
- Mac 側の突合ロジックの高度化。v1 は日付近接と金額一致による候補提示に留める

## Decisions

### D1. Flutter + Riverpod + drift（端末内 SQLite）

**なぜ**: 本アプリは「UI ＋ プラットフォーム API 呼び出し」だけで共有ビジネスロジックが無い。
スマホ側は会計計算をしない（[[receipt-capture]]「端末は会計データを持たない」）ので、
Expo/RN の「TS 資産を共有できる」利点がほぼ効かない。共有したい型は**メタと status の契約だけ**で、
それは D4 の方法で言語をまたげる。

一方 Android は段階案に入っている。SwiftUI 単独はアプリを二重化する。
さらにスキャン UI は iOS=VisionKit / Android=ML Kit Document Scanner を**統一 API で出すプラグインが既にあり**、
本 change が求めている抽象化がプラグイン側で済んでいる。

**代替案**: Expo/RN（TS 継続。ただし pnpm workspace への同居は地雷が多く、共有できる資産も実質無い）、
SwiftUI + 後日 Kotlin（iOS 品質は最良だが v4 で丸ごと二重化）。

Riverpod は送信キューという非同期状態を持つため。drift は型安全で Drizzle と思想が近く、
キューと履歴の 2 つのテーブルに対して十分。

### D2. リポジトリはモノレポのルート直下 `mobile/`

**なぜ**: レシート取込は「モバイルで撮る」＋「Mac 側で登録する」で 1 つの機能であり、
Mac 側は必ずこのリポジトリに入る。割ると 1 機能が 2 リポジトリ 2 PR に割れる。
加えて spec が正という運用なので、[[receipt-capture]] / [[receipt-inbox]] と実装を分離したくない。

`mobile/kanean/` と入れ子にはしない。2 つ目のモバイルアプリを作る予定が無く、
店頭名が未決である以上**ディレクトリ名に製品名を焼き付けない**方が安全。

干渉しないことは確認済み: `pnpm-workspace.yaml` は `packages/*` のみなので pnpm・turbo からは不可視。
`.gitignore` は `flutter create` が `mobile/.gitignore` を置くのでルートは触らない。
eslint の `ignores` にだけ `mobile/**` を足す。CI は Flutter SDK + Xcode の別ワークフローに分ける。

将来切り出したくなれば `git subtree split` で履歴ごと抜ける。**先に分けて後で統合する方が高い**。

### D3. Mac 側は MCP の定型手順。スキルの別配布はしない

Issue #112 の探索時は「`acquisition-receipts` スキルを新設する」と書いたが、
[[mcp-server]]「利用者に追加物を導入させてはならない」と衝突する。**定型手順「レシートの取込」**として
配ることで、利用者が導入するものは本体と MCP バンドルのみのまま保てる。

手順が [[receipt-inbox]] の規約（対が揃った件のみ扱う・現金は起票しカードは突合のみ・
削除は登録完了の確認後）を運ぶことは spec に落とした。

### D4. 契約は zod を正とし、JSON Schema を生成して Dart へ渡す

既存の投入 API は zod で検証している（[[skill-import]]「投入時の検証と権威」）。
契約の正を JSON Schema 側に置くと zod と二重管理になるため、**zod を正**とし、
そこから JSON Schema を生成して `packages/shared` に成果物として置く。Dart 側はその JSON Schema から
モデルを起こし、同じスキーマで検証する。

**ドリフト対策**: メタと status のゴールデンフィクスチャ（正常系・欠損・不正）を
リポジトリに 1 セット置き、**TS 側と Dart 側の両方のテストが同じファイルを読む**。
片側だけ解釈を変えるとどちらかのテストが落ちる。

**代替案**: 手で両方書く（必ずドリフトする）、Protobuf 等の IDL を導入する（ファイル 1 個の
往復に対して重い）。

### D5. 削除するのは Mac 側

登録と証憑保存の完了を知っているのは Mac 側なので、**確認と削除を同じ主体が行う**。
端末は status を読んで履歴の表示を更新するだけで、削除には関与しない。

**代替案**: 端末が status を見て自分の書いたものを消す。端末がオフラインのまま放置されると
inbox が溜まり続けるため採らない。

### D6. 1 件の単位と識別子

件の識別子は ULID（既存の id 生成と揃える）。inbox には `{ulid}` を共有する画像とメタを対で置き、
status も同じ `{ulid}` を鍵にする。**画像だけ／メタだけの状態は同期の途中**として持ち越す
（iCloud は 2 ファイルを同時に運ばない）。

### D7. 冪等性は画像の SHA-256 で取る

端末が撮影時に SHA-256 を計算してメタに書く。Mac 側は [[attachments]] が既に記録している
`sha256` と突き合わせ、既出なら起票も添付もしない。銀行明細の「出現インデックス方式」と違い、
レシートは画像そのものが一意の鍵になるため単純なハッシュ照合で足りる。

副次的に、撮影日時とハッシュが揃うことは真実性確保の材料にもなる（ただし
[[attachments]] と同じく**電帳法準拠はシステムが宣言しない**）。

### D8. オンデバイス OCR は「目視確認の補助」に留める

端末側は ML Kit の日本語テキスト認識を使い、読めた日付と金額を撮影直後に提示する。
装飾の多い紙面では精度が落ちるが、**読み取りの正は Mac 側**（Claude が画像を読む）なので許容できる。
読めなくても撮影は成立させる（spec 化済み）。iOS の品質が問題になった場合のみ、
platform channel で Vision を呼ぶ余地を残す。

## Risks / Trade-offs

- **iCloud の同期遅延・片側だけ先に届く** → 対が揃わない件は処理せず次の機会に持ち越す（spec 化済み）。
  status も同じ経路なので「送信済み（未登録）」の状態が一定時間続くことを UI で正常として扱う
- **契約のドリフト** → D4 のゴールデンフィクスチャ両側テスト。これが唯一の防壁なので、
  契約を変えるときはフィクスチャを先に足す
- **画像が Anthropic へ渡る** → 本体自身は送らず、渡すのは利用者の AI クライアント。
  利用者への明示を spec 化した（[[receipt-inbox]]「外部へ渡る情報の明示」）
- **App Store の Minimum Functionality（4.2）** → エクスポートを持たないため単体機能が薄い。
  撮影と読み取り履歴が単体で成立することが審査上の最低線になる
- **カード突合の誤り** → 自動選択せず候補提示に留め、選択を人に残す（spec 化済み）。
  二重計上は `legalRisk:high` の領域なので、迷ったら起票しない側に倒す
- **iCloud 実装だけはテストで守れない** → 搬送を1枚のインタフェースにしたおかげで、テストは
  `DirectoryTransport`（素のファイル I/O）で全部通る。だが**実機の iCloud は別の作法を要求する**:
  コンテナへの書き込みは `NSFileCoordinator` を通さないと同期デーモンが気づかず、
  アプリは成功したつもりで「送信済み」にしたまま黙って止まる。読み取り側も、実体が降りるまで
  `.名前.icloud` のプレースホルダしか見えない。**ここは実機で踏むしかない領域**として、
  搬送を触ったら必ず実機で1往復させる
- **Flutter の依存プラグインの保守** → スキャンと iCloud はプラグイン依存。
  差し替え可能なよう、搬送とスキャンはアプリ内で 1 枚のインタフェース越しに使う（Android 対応の下準備も兼ねる）

## Migration Plan

新規機能なので既存データの移行は無い。順序だけ 2 点。

1. 識別子は `com.susipero.kanean.mobile` で確定済みなので、**#292 の改名完了を待たずに着手できる**
2. ただし `packages/shared` に置く契約の成果物は改名の一括置換の対象に入る。
   #292 と本 change を同時に走らせる場合は、改名を先に通してから契約を足す方が衝突が少ない
