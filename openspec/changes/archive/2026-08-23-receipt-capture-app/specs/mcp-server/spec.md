## MODIFIED Requirements

### Requirement: 定型手順の配布

システムは典型的な作業の入口を MCP クライアント側へ提供する SHALL。
利用者に Kanean 用のスキルその他の追加物を導入させてはならない。

#### Scenario: 手順が入口として現れる

- **WHEN** 利用者が MCP クライアントで Kanean の定型作業を探す
- **THEN** 「今月の状況」「決算前チェック」「確定申告の転記」「レシートの取込」等の入口が提示され、そこから会話を始められる

#### Scenario: 確定申告の転記手順が規約を運ぶ

- **WHEN** 利用者が「確定申告の転記」の入口から会話を始める
- **THEN** 提示される手順は [[filing]] の転記手順の規約（転記値は入力指示書のみ・認証と送信は利用者・
  検算一致の確認）を含んでいる

#### Scenario: レシートの取込手順が規約を運ぶ

- **WHEN** 利用者が「レシートの取込」の入口から会話を始める
- **THEN** 提示される手順は [[receipt-inbox]] の規約（画像とメタの対が揃った件のみ扱う・現金は起票しカードは
  突合のみ・登録と証憑保存の完了を確認してから中継コピーを削除する・未登録のものを消さない）を含んでいる

#### Scenario: 追加の導入物を要求しない

- **WHEN** 利用者が Kanean を MCP クライアントで使い始める
- **THEN** 導入するものは Kanean 本体と MCP バンドルのみで、別途スキルを入れる必要がない

### Requirement: 書き込みの限定と承認の非委譲

システムが書き込みとして露出してよい操作は、**連携サービスの登録・取込の進行・サイト較正の更新・
レシートの取込・申告の完了記録に限る** SHALL。
仕訳の確定・取消・削除、マスタ・期首残高・税区分の編集、draft の承認を行うツールを露出してはならない。
承認は [[skill-import]] の原則どおり利用者が UI で行う。

取込に関して露出してよいのは、開始・状態の問い合わせ・**未確定 draft の分類**・失敗の診断・較正の更新であり、
いずれも [[acquisition]] の規約に従う。分類のために受け取れる情報は品名・摘要とその識別子に限られ、
較正の更新として受け付けるのはデータのみでプログラムを受け付けない。
分類は科目を**提案として置き換える**にとどまり、確定はしない。

レシートに関して露出してよい書き込みは、[[receipt-inbox]] の規約に従う **現金レシートの draft 起票と
証憑の添付**に限る。カード払いのレシートは突合候補の提示のみで、起票する経路を持たない。
いずれも draft に留まり、確定はしない。

申告に関して露出してよい書き込みは、[[filing]] の完了記録の作成と控えの添付に限る。
記録の削除は UI で行う。

#### Scenario: 連携サービスを追加できる

- **WHEN** 追加したい連携サービスを指定する
- **THEN** 登録に必要な選択肢（勘定科目・補助科目など）を提示して確認を得たうえで登録する

#### Scenario: 取込を開始して進行を追える

- **WHEN** 連携サービスを指定して取込の開始を要求する
- **THEN** 巡回の完了を待たずに識別子と状態を返し、以後その状態を問い合わせられる

#### Scenario: 取込は分類を待たずに終わる

- **WHEN** 取込の完了を確かめる
- **THEN** 受理・重複・期間外・未確定の件数が返り、未確定があっても取込は完了している

#### Scenario: 未確定に科目を当てる

- **WHEN** 未確定の分類対象を求め、識別子ごとの科目を返す
- **THEN** アプリ側で draft に突き合わせて科目を置き換え、適用件数と対応しなかった件数を返す
- **AND** 確定はされず、利用者の確認へ誘導される

#### Scenario: 判断の材料が渡される

- **WHEN** 未確定の分類対象を求める
- **THEN** 分類方針と、関連する確定履歴が一緒に返る（利用者のファイルを読みに行かせない）

#### Scenario: 判断の根拠を返させる

- **WHEN** 科目を当てる
- **THEN** 理由と確信度を添えることが求められ、利用者の画面でそれが読める

#### Scenario: 失敗を診断して較正を直せる

- **WHEN** 巡回が失敗した取込の診断を要求する
- **THEN** 失敗した手順と画面の状態を返し、較正の更新を受け付ける

#### Scenario: 較正の更新でプログラムを受け付けない

- **WHEN** 較正の更新としてプログラムに相当するものを渡す
- **THEN** 受け付けず、拒否したことを返す

#### Scenario: 現金レシートを起票できる

- **WHEN** 現金のレシートを画像と撮影時の文脈とともに渡す
- **THEN** [[skill-import]] の規約で draft 仕訳が作られ、当該画像が証憑として添付される
- **AND** 同じ画像を再び渡しても仕訳と添付は増えない

#### Scenario: カードのレシートを起票するツールが存在しない

- **WHEN** カード払いのレシートを渡す
- **THEN** 返るのは既存明細の突合候補のみで、それを起票するツールは存在しない

#### Scenario: 申告の完了を記録できる

- **WHEN** 転記手順の完遂後に、年分・税目・提出日・受付番号と控え PDF を渡して完了記録を要求する
- **THEN** [[filing]] の完了記録として保存され、帳簿の仕訳・設定は変更されない

#### Scenario: 完了記録を削除するツールが存在しない

- **WHEN** 完了記録を削除しようとする
- **THEN** それを行うツールは存在せず、UI での操作へ誘導される

#### Scenario: draft を確定するツールが存在しない

- **WHEN** 承認待ちの draft 仕訳を確定しようとする
- **THEN** それを行うツールは存在せず、UI での承認へ誘導される

#### Scenario: 設定を書き換えるツールが存在しない

- **WHEN** 期首残高・勘定科目・税区分を変更しようとする
- **THEN** それを行うツールは存在せず、UI での操作へ誘導される
