## Context

`electron-desktop-shell` §7.5 の回帰確認で、エクスポート zip が復元できないことを実測した。
本 change はその1点に絞る。Electron 化とは独立で、どちらの配布形態でも成り立つ問題である。

**実測した挙動**（`electron-desktop-shell` の作業中）:

```
GET /api/export                → 226,007 B の zip
zip の中身                      → manifest.json / books/01KZTBGRE….sqlite（2ファイル）
解凍して books/ を別 $DATA_DIR へ
その環境で server を起動        → 別 ULID(01KZTBN6V…) の空帳簿「マイ帳簿」が生成される
GET /api/fixed-assets          → []   ← 元環境で登録したマツダ2 が見えない
```

原因は単純で、**control plane（帳簿レジストリ）が zip に入っていない**こと。
`ensureAtLeastOneBook` は control の `books` テーブルだけを見るので、
data plane のファイルがそこに在っても「0冊」と判断する。

## 3層の設計判断

### 1. control.sqlite ごと zip に入れるか

**入れない。** control plane は**その環境の**帳簿レジストリであり、
複数帳簿・アプリモード・バックアップ記録といった**持ち出し対象でない情報**を含む。
これを持ち込むと、取り込み先の他の帳簿を壊しうる（事務所モードで顧問先を複数持つ環境が典型）。

エクスポートは「帳簿1冊の持ち出し」という単位を保ち、**取り込み側が自分のレジストリへ登録する**のが正しい。
`manifest.json` は既に `bookId` / `bookName` / `sha256` / `byteSize` を持っており、登録に必要な情報は揃っている。

### 2. 起動時に孤児ファイルを自動登録するか

**しない。** `books/*.sqlite` を見つけたら自動でレジストリに載せる案は一見単純だが、

- **意図しないファイルを帳簿として取り込む**（退避目的で置いたコピー、restore の `pre-restore-*` 退避物など）
- 「黙って落とさない・黙って確定しない」の裏返しで、**黙って増やす**ことになる
- 取り込み時の検証（sha256・衝突確認）を通らない経路ができてしまう

明示的な取り込み操作にする。**ファイルの存在は意図ではない。**

### 3. `restore` CLI との関係

用途が違うので**統合しない**。

| | 対象 | 含むもの | 用途 |
|---|---|---|---|
| `restore` CLI | バックアップ世代 | control ＋ 全帳簿 | **同一環境**の巻き戻し |
| 取り込み（本 change） | エクスポート zip | 帳簿1冊 ＋ 証憑 | **別環境**への持ち出し |

`restore` は現状で機能している（control 込みのスナップショットなので、この不具合は起きない）。
両者を混同させないよう、UI とドキュメントで用途を書き分ける。

### 4. 取り込みの入口

**API＋UI のみ。CLI は作らない。**

取り込みは「別環境へ持ち出した zip を開けるようにする」操作であり、その局面で**アプリは正常に起動する**
（起動できるが、空の帳簿しか無い）。`restore` CLI がサーバ停止中の運用作業なのと対照的に、
取り込みは**アプリを開いたまま**できる。CLI を足す動機になるのは「アプリが起動しないほど壊れた状態」だが、
それは取り込みではなく `restore` の領分である。

エクスポートが UI（設定→データ管理）にある以上、対になる取り込みも同じ場所に置く。

### 5. `bookId` 衝突時の既定

**`bookId` は原則そのまま保持し、衝突したときだけ 409 で中止して利用者に選ばせる。**

```
POST /api/import  (zip)
  bookId 未登録  → その bookId のまま登録して配置
  bookId 登録済み → 409（既存には一切触れない）
POST /api/import?mode=new     → 別 ULID を採番して新規帳簿として取り込む
POST /api/import?mode=replace → 既存を退避してから明示的に置換する
```

ID を保持するのは、[docs/roadmap.md] の**帳簿受け渡しプロトコル**が下流にあるため。あの設計は
封筒に `book_id` を焼き込んで「取り違え（別の顧問先のデータで自分の帳簿を上書き）」を構造的に防ぎ、
返却の取り込みを**帳簿単位の丸ごと差し替え**として扱う。取り込みのたびに ID を振り直すと、
同じ帳簿が別マシンで別 ID になり、この同一性判定が成立しなくなる。

一方で衝突を黙って別 ULID に倒すのも採らない。「置換のつもりが2冊に増えていた」に気づけないためで、
[[data-ops]] の「黙って落とさない・黙って確定しない」と同じ理由である。**衝突は利用者の判断を要する事象**
として扱い、409 に `bookId` / zip 側の `bookName` / 既存側の名前を載せて選択の材料にする。
