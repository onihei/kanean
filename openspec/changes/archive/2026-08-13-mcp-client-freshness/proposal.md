## Why

取込の分類は Claude Desktop に委ねる設計になっており、アプリ自身が画面で
「科目の分類は Claude Desktop に任せられます」「Claude Desktop で『仕訳して』と頼むと候補が入ります」
と案内している。ところが**連携が成立しているのか、成立していても古いバンドルなのかを、
利用者もアプリも確かめる手段が無い**。取込の導線が分類の手前で切れている。

古いバンドルは黙って動き続ける。ツールの形が変わっても、利用者には「なぜか結果がおかしい」
としか見えない。バンドルは配布物に同梱されているので、アプリを更新するたびに版がずれうる。

## What Changes

- MCP クライアントが**自分の版を名乗る**。バンドルからの呼び出しにクライアント識別ヘッダを付ける。
- 同梱版と**一致しないクライアントからの `/api/*` を拒否する**（**BREAKING**: 古いバンドルは
  版を入れ直すまで会計データを読めなくなる）。拒否応答のメッセージは既存の翻訳経路を通って
  Claude Desktop 側にそのまま表示されるので、**古いバンドル自身に手を入れずに**入れ直しを案内できる。
- `/health` は拒否の対象外に保つ。ここを塞ぐと未起動と区別できなくなり、
  「アプリが起動していません」という**誤った案内**を古いバンドルに言わせてしまう。
- **接続の観測を記録する**（最後に到達したクライアントの版と時刻）。control plane に置く。
- ホーム画面のセットアップ案内に**連携の状態を1行**出す。接続の記録が無ければ
  「連携がまだ確認できていません」、版が一致しなければ「古い版が使われています」。

「MCP が入っていない」とは書かない。アプリはサーバ側にいるので**入っていないことを証明できない**。
書けるのは観測できた事実だけ＝「まだ一度も到達していない」。導入したが一度も使っていない状態は、
連携が働くと確かめられていないという意味で、実際にセットアップが完了していない。

## Capabilities

### New Capabilities

なし。既存の capability の要求を変える。

### Modified Capabilities

- `mcp-server`: クライアントの版の表明と、同梱版と一致しないクライアントの拒否を追加する。
  拒否は会計データの経路（`/api/*`）に限り、到達確認（`/health`）には及ばない。
- `web-app`: セットアップ案内が扱う対象に、AI 連携の疎通状態を追加する。断定できない導入の有無ではなく、
  観測できた到達の有無と版の一致で書く。

## Impact

- `packages/mcp` — 呼び出しにクライアント識別ヘッダを付ける（`connection.ts`）。
  バンドル生成が同梱版を書き出す（`scripts/bundle.mjs`）。拒否応答の翻訳は
  既存の `fromAppResponse` がそのまま担うので追加不要。
- `packages/server` — `/api/*` の前段でクライアントの版を検査し、記録する。
- `packages/desktop` — 同梱版を配布物へ載せ（`electron-builder.yml` の `extraResources`）、
  サーバへ渡す。
- `packages/web` — ホームのセットアップ案内に1行追加する。
- control plane（`app_settings`）— 観測の記録先。既存の key/value なのでマイグレーションは要らない。
- 帳簿データ（data plane）には触れない。会計計算・帳票・確定の規約は変わらない。
