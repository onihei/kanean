## Context

MCP バンドルは配布物に同梱され、利用者が Claude Desktop へドラッグして導入する。
導入後のバンドルは Claude Desktop が起動したときだけ動くプロセスで、アプリへは
`$DATA_DIR/kanean.sock` 経由で HTTP を投げる。**アプリはサーバ側にいる**ので、
クライアントの状態はリクエストが来たときにしか観測できない。

取込の巡回が Electron 側へ移った結果、このソケットへ繋ぐのは MCP クライアントだけになった。
ソケットに届いた要求＝ MCP からの要求、と読んでよい。

動機は proposal.md「Why」を参照。

## Goals / Non-Goals

**Goals:**

- 一致しないバンドルが黙って動き続ける状態を無くす
- **古いバンドル自身を改修せずに**、利用者へ入れ直しを案内する
- 誤った次の一手（「アプリが起動していません」）を言わせない
- 疎通の状態をホーム画面から確かめられるようにする

**Non-Goals:**

- Claude Desktop の設定ファイルやインストール状態を読むこと（design D3 の線を越えない）
- クライアントが導入済みかを判別すること（原理的に不可能。specs で「断定しない」と固定した）
- 自動更新。書き出しと導入は利用者の操作のまま
- 版の互換範囲を持つこと（後述 D1）

## Decisions

### D1. 一致しなければ拒否する（新旧を区別しない）

同梱版と**厳密に一致**しないクライアントを拒否する。古いか新しいかで分岐しない。

- 版を名乗らないクライアントも、この一本の規則で自然に拒否側へ落ちる。移行期のための特別扱いが要らない。
- 案内文「設定画面から書き出して入れ直してください」は**両方向で正しい**。
  このアプリから書き出せば必ず一致するため、クライアントが古くても新しくても解決する。

*代替案*: semver で比較し「古いときだけ」拒否する。却下 — 同梱版より新しいクライアント
（＝別の新しいアプリから書き出したもの）が素通りする。それは実際に壊れうる組み合わせで、
しかも利用者からは最も分かりにくい。

### D2. 拒否は会計データの経路だけ。到達確認は開けたままにする

拒否は `/api/*` に限る。`/health` は誰でも通す。

クライアントの到達確認は例外を握り潰して真偽だけを返すので、`/health` を拒否すると
**到達不能と区別できない**。その結果クライアントは「Kanean が起動していません」と案内し、
利用者はアプリを起動し直して、何も直らない。塞いではいけない理由がここにある。

サーバ側は `/health` が最上位、`/api` がマウントという構造なので、境界はそのまま引ける。
クライアントの起動待ちも `/health` のポーリングなので巻き込まれない。

### D3. 拒否応答の本文で案内する（成功応答では届かない）

拒否は `{ error: { code, message } }` で返す。ステータスは `426 Upgrade Required`。

これは既存の翻訳経路に乗せるための形である。クライアントはアプリのエラー本文の
`error.message` をそのまま利用者向けの結果へ通すので、**バンドルを更新しなくても**
入れ直しの案内が Claude Desktop の画面に出る。

逆に**成功応答に注記を混ぜても届かない**。ツールはアプリの応答を分配束縛で受け取り、
必要なフィールドだけを取り出して結果を組み立てるため、知らないフィールドはそこで捨てられる。
「動かしたまま警告する」経路は存在しない ── これが「全部拒否」を選んだ理由そのものである。

*代替案*: 成功応答に警告フィールドを足し、クライアント側で読む。却下 —
読む側の改修が要るので、**まさに古いバンドルには届かない**。解きたい問題に効かない。

### D4. クライアントはヘッダで名乗り、検査の対象は**入口**で決める

要求ヘッダにクライアントの名前と版を載せる。名乗りは呼び出しの共通経路1箇所に置く
（ツールごとに載せると、足し忘れた経路だけが拒否される部分的な不通になる）。

ただし**「名乗らない要求を拒否」では足りない**。UI も同じ Hono を通るので、名乗りの有無だけを
見ると UI まで巻き込む。そして名乗る前の版のバンドルこそ、名乗らないまま来る。

そこで検査の対象は入口で決める:

```
  kanean://（プロトコルハンドラ）→ 印なし → 検査しない ＝ UI
  unix socket（ローカル連携）      → 印あり → 検査する ＝ MCP クライアント
```

印はソケットの入口が付ける。クライアントが同名のヘッダを送ってきても上書きするので、
自分から名乗れる類のものではない。取込の巡回が Electron 側へ移った結果、このソケットへ
繋ぐのは MCP クライアントだけなので、この対応づけが成り立つ。

名乗りがあれば入口の印が無くても検査する。開発用の TCP 経路でも同じ判定を通すため
（mcp-server spec「明示された開発用の経路でも同じツールが動く」）。

### D5. 同梱版は版ファイルとして配る

バンドル生成が `.mcpb` と並べて版だけを書いたファイルを出力し、配布物へ同梱する。

`.mcpb` は zip なので、実行時に中の `manifest.json` を読むには展開が要る。
版のためだけに zip を扱いたくない。版の出所は `manifest.json` のままで、
既存の一致検査（`package.json` と食い違ったらビルドを止める）がそのまま効く。

*代替案*: デスクトップが MCP パッケージを依存に取る。却下 — 配布物に MCP サーバの実装が
二重に入る。zip を実行時に読む。却下 — 版1つのために依存と失敗経路が増える。

### D6. 観測は control plane に記録する

最後に到達した版と時刻を `app_settings`（既存の key/value）に置く。

帳簿ではなくアプリに属する情報なので data plane ではない。既存テーブルなので
マイグレーションも要らない。

### D7. 同梱版が判明しないときは検査しない

開発時（サーバ単体起動・同梱物が無い）は同梱版が分からない。このとき検査は行わず、
ホームの案内も出さない。

比較対象を持たないまま拒否すると開発中に MCP を検証できなくなる。
「分からないから拒否」ではなく「分からないから何も言わない」に倒す。

なお `pnpm dev:app`（デスクトップの開発起動）では、リポジトリ内にバンドルを作ってあれば
同梱版が判明する＝検査が働く。パッケージまで作らなくても実機で確かめられる。

## Risks / Trade-offs

- **動いていた連携が止まる（BREAKING）** → 止まった瞬間に、理由と手順が Claude Desktop の
  画面に出る。利用者が詰まる時間は「一度質問して、書き出して、入れ直す」まで。
  D2（`/health` を開ける）が守られていることが前提で、破ると誤った案内に化ける。

- **記録は常に過去形で、現在の状態ではない** → Claude Desktop が起動していなければ観測は増えない。
  入れ直した直後もホームの表示は古いままになる。断定を避け、観測時点を必ず添える形で
  spec に固定した（「一致しない版が使われていることを案内する」シナリオ）。

- **疎通未確認の行が、導入済みだが未使用の人にも出る** → 一度使えば消える自己解決の行。
  導入しただけで一度も通していない状態は、連携が働くと確かめられていないという意味で
  実際に完了していない。文言を「確認できていません」に保つ限り偽りにならない。

- **版を上げ忘れると拒否が起きない** → バンドル生成が `package.json` と `manifest.json` の
  食い違いで止まる仕組みは既にある。版を上げる操作自体は人の手に残る。

## Migration Plan

1. クライアントが版を名乗るようにし、バンドルを作り直す。
2. サーバの検査と記録、ホームの案内を入れる。
3. 利用者は設定画面から書き出して入れ直す。**この作業は避けられない** ── 現在配布済みの
   バンドルは版を名乗らないため、更新後は拒否される。それが分かる形で拒否が出るのが本変更の目的。

ロールバック: 検査を無効化すれば従来どおり動く。記録とホームの案内は残っても害が無い
（案内は観測の有無で書かれており、拒否の有無に依存しない）。
