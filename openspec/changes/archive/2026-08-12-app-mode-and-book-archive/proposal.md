## Why

複数帳簿の土台（`books`）が入ったことで、1インスタンスが「自分の帳簿1冊」と「顧問先 N 冊」という
性質の異なる2つの使われ方を持つようになった。いまの Web は起動時に前回の帳簿を黙って復元して業務画面へ入るため、
顧問先を N 冊持つ使い方では**別の顧問先の帳簿に気づかず書き込む**事故が起こりうる。
逆に自分1冊しか持たない使い方では、帳簿切替や帳簿作成の導線が常時ノイズになる。

同時に、顧問契約が終わった帳簿・使わなくなった帳簿を一覧から下げる手段が無い。
`books` は「削除は提供しない」（税務データの消失は不可逆）を要件として持つため、
一覧が増える一方になる構造的な行き止まりがある。

## What Changes

- **アプリモードを導入する**。`じぶんの帳簿` / `事務所` の2値を control plane に保持し、初回起動時に選択させる。
  設定画面からいつでも変更できる（初回の選択ミスの救済とデバッグ用途）。
- **起動後の導線をモードで分岐させる**。
  - `事務所`: 起動時に必ず帳簿（顧問先）を選ぶ画面から始める。**BREAKING**: 既存の
    「選択を次回起動時に復元する」をやめ、前回の帳簿はハイライト表示に留める（黙って開かない）。
  - `じぶんの帳簿`: 唯一のアクティブ帳簿へ直行する。帳簿の切替・作成・顧問先向けの導線を露出しない。
- **帳簿のアーカイブを導入する**。削除は導入しない（既存要件を維持）。control plane の
  `books.archived_at` のみで表現し、data plane のファイルには一切触れない。
  顧問契約の終了・使わなくなった帳簿の整理に使う。
- **アーカイブに伴い帳簿解決の「1冊」の意味を確定する**。暗黙解決の判定を**アクティブ帳簿の冊数**に基づかせる。
  アーカイブ済み帳簿は明示指定でのみ到達でき、読めるが書けない（復帰は可能）。
- **モード切替は破壊的副作用を持たない**。`事務所` → `じぶんの帳簿` はアクティブが2冊以上なら切替できず、
  帳簿管理でアーカイブしてから切り替える。設定変更のついでにデータが消えることは無い。
- **バックアップ・マイグレーションはアーカイブ済み帳簿も対象に含める**ことを要件として固定する
  （将来「アクティブのみ」に絞られて、数年後に開けない帳簿が生まれるのを防ぐ）。

## Capabilities

### New Capabilities

- `app-mode`: アプリモード（`じぶんの帳簿` / `事務所`）の選択・保持・変更と、モードが決める起動導線・
  UI 露出範囲・不変条件。モードは表示と導線のみを決め、会計データの意味・計算・帳簿解決の可否は変えない。

### Modified Capabilities

- `books`: 帳簿のアーカイブと復帰を追加。一覧の既定をアクティブのみに変更（`?includeArchived=true` で全件）。
  対象帳簿の解決における「1冊しか無ければ省略できる」をアクティブ冊数基準に確定。
  アーカイブ済み帳簿への書き込み拒否と、アクティブ1冊のときのアーカイブ拒否を追加。
  「削除は提供しない」は維持（変更しない）。
- `web-app`: 起動導線をモード分岐に変更。**BREAKING**: 帳簿選択の自動復元をやめる（`事務所` の場合）。
  設定画面にモード変更を追加し、帳簿管理にアーカイブ／復帰を追加。
- `data-ops`: バックアップとマイグレーションの対象にアーカイブ済み帳簿を含めることを明示。

## Impact

- **control plane スキーマ**: `books.archived_at` 追加、アプリ設定の保存先（`app_settings` 相当）追加。
  data plane のスキーマ変更は無い。
- **API**: `GET /api/books`（既定の絞り込み変更 = 破壊的）、帳簿のアーカイブ／復帰、アプリモードの取得・更新。
  帳簿解決ミドルウェアの暗黙解決条件。
- **packages/web**: `App.tsx` の起動シーケンス（帳簿の自動選択をモード分岐へ）、`nav/Sidebar.tsx`（帳簿切替の露出）、
  `SettingsTab`（モード・帳簿管理）。新規に帳簿選択画面。
- **packages/server**: `migrate.js`・バックアップスクリプトの対象範囲（ファイル走査ベースのため実質維持、要件として固定）。
- **docs**: `docs/architecture.md` §4/§5（帳簿解決）、`docs/data-model.md`（control plane）、`docs/roadmap.md`（後述の非スコープ）。

## 非スコープ（ロードマップへ残すもの）

本 change は**モードと帳簿の整理**までとし、以下は扱わない。これらは `docs/roadmap.md` が
非スコープとして保留していた「税理士・第三者とのデータ共有（[PRD.md] §54 要再定義）」に対応する将来スライス群であり、
本 change の完了時点でロードマップへ追記する。

事務所⇔本人の**帳簿受け渡しプロトコル**（チェックアウト／チェックイン）:

1. **顧問先コードの発行**（事務所側 UI）。コードは暗号鍵そのものではなく、事務所の公開鍵の指紋として扱う
   （人が読み上げる媒体で運ぶため、漏洩しても復号に至らない設計にする）。
2. **暗号化封筒のフォーマットと鍵管理**。本人 → 事務所は事務所の公開鍵で暗号化し、封筒に本人の公開鍵を同梱して
   返却も暗号化できるようにする。封筒には `book_id`・預かり ID・貸出時点の世代を焼き込み、取り違えを構造的に防ぐ。
3. **貸出中の読み取り専用ロック**。ロックは事故防止の合図であり、本人のマシン上の本人のファイルである以上
   セキュリティ境界ではない。`data-ops` の「解約＝データ人質にしない」原則に従い、**本人がロックを解除する道を必ず用意する**。
4. **返却の取り込み＝帳簿単位の丸ごと差し替え**。マージは行わない。`data-ops` の restore（退避 → `integrity_check` → 配置）を再利用する。
   ロック中に手元が変更されていた場合（分岐）は、**自分のデータを使う／取り込んで上書きする**の2択を明示的に提示する。
5. **事務所側の預かり管理 UI**（受入・預かり中・返却済のライフサイクル。アーカイブと接続する）。
