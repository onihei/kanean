## Context

現状の起動シーケンスは `packages/web/src/App.tsx` にあり、`GET /api/books` の結果から
`localStorage` の保存値（無ければ `list[0]`）を**黙って選んで** `Workbench` へ入る。
サーバ側は `books` の帳簿解決規約（ヘッダ → クエリ → 1冊なら暗黙 → 曖昧なら 400）を持ち、
control plane（`control.sqlite`）に帳簿レジストリ、data plane（`books/{id}.sqlite`）に会計データを置く。

制約:

- 認証は無く、`127.0.0.1` バインドが唯一の境界。ユーザーは自分のマシンの自分のファイルを触っている。
  したがって**サーバが人に対して強制できることは無い**。仕様上の不変条件はアプリの導線が守るものであって、
  ファイルシステムに対する保証ではない。
- `books` は「帳簿の削除は提供しない」を要件として持つ。本 change はこれを維持する。
- data plane のスキーマは触らない（帳簿ファイルは会計データだけを持ち、アプリの都合を持ち込まない）。

動機は proposal.md の Why を参照。

## Goals / Non-Goals

**Goals:**

- 起動直後に「どの帳簿を触っているか」が曖昧なまま業務操作へ入れない状態にする。
- 帳簿を一覧から下げる手段を、データを失わずに提供する。
- モードの導入が既存の帳簿解決規約を**上書きしない**こと。規約はひとつのまま、UI がそれに従う。

**Non-Goals:**

- 事務所⇔本人の帳簿受け渡しプロトコル（proposal.md の非スコープを参照）。
  本 change ではその状態（貸出中・預かり中）を `books` に持ち込まない。
- モードによる会計ロジック・帳票・税計算の差異。モードは表示と導線のみ。
- 帳簿の削除・物理的な移動。

## Decisions

### モードは control plane の汎用 key-value に置く

`control.sqlite` に `app_settings(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL)` を追加し、
`app_mode` を1行として持つ。

- **なぜ localStorage ではないか**: Tauri の webview とブラウザ開発で別々の答えになる。
  また `office → personal` の切替可否判定はアクティブ冊数を見るサーバ側の判断であり、
  クライアントの記憶に置くと判定と保存が分かれる。
- **なぜ帳簿（data plane）ではないか**: 帳簿を跨ぐ設定であり、帳簿ファイルは可搬（エクスポート・受け渡し）である。
  アプリの都合を持ち出させない。
- **なぜ専用テーブルでなく KV か**: 今後のアプリ全体設定（表示の好みなど）を受けられる。
  型の緩さはサーバ側の検証で吸収し、**未知の値・壊れた値は「未設定」として扱う**（勝手に既定へ倒さない）。

### アーカイブは `books.archived_at` の1列で表す

`archived_at TEXT NULL`（ISO8601）。`NULL` = アクティブ。時刻表現は隣接する `created_at` / `updated_at`（ISO 文字列）に揃える。

- **なぜ boolean でないか**: 「いつ下げたか」が顧問契約終了の記録として意味を持つ。
- **なぜ `status TEXT` の状態機械にしないか**: 将来の受け渡しプロトコルは「貸出中」「預かり中」といった
  別種の状態を必要とするが、それは**アーカイブと直交する**（預かり中の帳簿もアーカイブし得ない、
  アーカイブ済みは貸し出さない、という関係は後から述べればよい）。いま単一の `status` に畳むと、
  将来その列の意味を作り直すことになる。`archived_at` は「アーカイブされた事実」だけを表す。
- data plane には一切触れない。ファイル・証憑ディレクトリはそのまま残る。

### アーカイブ済みへの書き込み拒否は帳簿解決ミドルウェアの一点で行う

解決した帳簿が `archived` かつリクエストが更新系（`POST`/`PUT`/`PATCH`/`DELETE`）なら 409 を返す。

- **なぜ一点集約か**: ルートごとに書くと必ず漏れる。漏れた1本が「アーカイブしたはずの帳簿が書き換わる」を生む。
- **例外の切り分け**: `POST /api/books/:id/unarchive` は control plane に対する操作であり、
  帳簿解決ミドルウェア（data plane を開く経路）を通さない。パスで分離する。

### 暗黙解決の「1冊」はアクティブ冊数で判定する

`books` spec の「1冊しか無ければ指定を省略できる」を、アーカイブ済みを数えない判定に変更する。

- 要件の趣旨は「対象が曖昧でないこと」であり、アーカイブ済みは選択候補ではない。
- **後方互換**: アーカイブが1件も無い既存環境では挙動が一致する。
- 逆にアーカイブ済みを数えると、帳簿を1冊に整理したのに 400 が返り続ける、という不合理が起きる。

### 起動シーケンス

```
起動
 └ GET /api/app-mode
    ├ 未設定 ────────▶ ModeSetup（選ぶまで進まない）
    │
    ├ personal ──▶ GET /api/books（アクティブのみ）
    │               ├ 1冊 ──▶ Workbench（年度ゲート）
    │               └ 0/2冊+ ─▶ 不整合の修復導線（後述）
    │
    └ office ────▶ BookPicker（必ず選ぶ・前回はハイライトのみ）
                    └ 選択 ──▶ Workbench（key=bookId・年度ゲート）
                                 └「帳簿を閉じる」で BookPicker へ戻る
```

`Workbench` を `key={bookId}` で作り直して画面状態を持ち越さない既存の作りはそのまま使う。

### `localStorage` の役割を降格させる

`kanean.bookId` は「次回自動で開くための記憶」から「帳簿選択画面でハイライトするための記憶」へ変える。
自動選択には使わない。既存の保存値が残っていても、意味が変わるだけで害は無い。

- これが `web-app` spec の「選択を次回起動時に復元する」を変更する実体であり、本 change の
  **BREAKING** の中身。復元をやめること自体が安全性の本体（前回の顧問先が黙って開いていて、そのまま仕訳を打つのが最悪の事故）。

### `personal` で不変条件が壊れている場合は、黙って選ばない

`personal` なのにアクティブが2冊以上（外部でファイルを足した、バックアップから復元した等）のとき、
`list[0]` を選んで進むのは「黙ってどれかの帳簿に書き込む」そのものなので行わない。
帳簿を1つ選ばせ、残りをアーカイブして 1冊にする修復導線を出す。アクティブ0冊はサーバ起動時の自動作成で解消される。

- サーバは不変条件を**強制しない**（ファイルシステムは人のもの）。アプリは検出して直す導線を出すに留める。

### 既存インストールのモードは推測しない

マイグレーションでモードを自動設定せず「未設定」のままにし、初回起動でユーザーに選ばせる。

- 冊数から推測すると「たまたま今1冊だから personal」を恒久的な選択として固定してしまう。
- 対象は自分のローカルアプリ1インスタンスであり、一度きりの選択画面のコストは無視できる。

## Risks / Trade-offs

- **アーカイブ済みへの書き込み拒否が漏れる** → ミドルウェア一点集約 ＋ 「アーカイブ済み帳簿に更新系を投げると 409」を
  代表的な更新系ルート（起票・確定・取込・マスタ更新）について明示的にテストする。
- **`GET /api/books` の既定変更が呼び出し側を壊す** → 破壊的変更。web 以外（skill/MCP 経路）での帳簿列挙箇所を
  洗い出し、全件が必要な箇所は `?includeArchived=true` に切り替える。tasks に洗い出しを含める。
- **アクティブ0冊にできてしまうと空帳簿が生える** → 「最後のアクティブ帳簿はアーカイブできない」を
  サーバ側で 409 として強制する（UI の制御だけに頼らない）。
- **モードが表示の話に留まらず、機能を隠す方向へ育つ** → `personal` で隠すのは帳簿の切替・作成・
  事務所固有の導線のみと定め、会計機能は隠さない。「モードで機能が消える」を仕様として広げない。
- **KV テーブルの型が緩い** → 値はサーバで検証し、不正値・未知の値は未設定として扱う（既定へ倒さない）。
- **`archived_at` を将来の状態機械と混ぜたくなる** → 受け渡しプロトコルの状態は別の列/テーブルで持つ、を
  この design の決定として残す。

## Migration Plan

control plane に対する冪等なマイグレーション2本（data plane は変更なし）:

1. `app_settings` テーブルの追加
2. `books.archived_at` 列の追加（`NULL` 既定 = 既存の全帳簿はアクティブ）

適用は既存の `migrate.js`（deploy 時）と起動時の追いつきに乗る。

**ロールバック**: 追加した列・テーブルは旧コードから無視できる（旧コードは `archived_at` を見ないため、
アーカイブ済み帳簿も一覧に出るだけで壊れない）。前方互換なので列を落とす必要は無い。

## Open Questions

- 帳簿選択画面（`office`）に、帳簿名以外にどこまで出すか（未確定 draft 件数・open 年度・最終更新日など）。
  仕様・approach・タスク分割を変えずに後から足せる。
- `personal` モードで「今やること」の内容を変えるか（帳簿横断の概念が無いので現状のままで足りる想定）。
