# Design — rename-users-to-books

## Context

動機は proposal.md「Why」を参照。設計に効く現状は次の4点。

- **HTTP の入口はすでに1箇所に寄っている**。`packages/web` の `fetch(` は全 77 箇所が `api.ts` 内にあり、
  他ファイルからの直 fetch はゼロ。全リクエストに帳簿を載せるフックを1つ作れば全経路を覆える。
  しかも 77 箇所すべてが `credentials: 'include'`（Cookie 廃止済みで**現在は無意味**）を付けており、
  同じ機械的置換で除去できる。
- **ただしブラウザネイティブの取得が2箇所ある**。`SettingsTab.tsx` の `<a href="/api/export">`
  （zip をメモリに載せないため意図的）と `api.ts` の `attachmentUrl()`（証憑を `src`/`href` で開く）。
  これらは `fetch` を通らないので**カスタムヘッダを載せられない**。
- **rename の物理的な規模**: `userDb(` 93 箇所、config のパス関数 36 箇所、`c.get('userId')` 14 箇所、
  `userId` に言及するファイル 29 個。ただしいずれも型で追える。
- **ULID ガードが2箇所ある**（`attachments/storage.ts`・`ops/exportUser.ts`）。
  過去に非 ULID の id で証憑・エクスポートが 500 になった実績があり、bookId へ確実に移す必要がある。

## Goals / Non-Goals

**Goals**

- `users` → `books` の概念・スキーマ・ディレクトリ・API を一度に改める
- 帳簿を N 冊持てる状態にし、「どの帳簿に対する操作か」が曖昧なまま処理されないことを保証する
- 税理士側インスタンス（顧問先 N 冊）を後から足せる形にする

**Non-Goals**

- 帳簿の削除 API（D4）
- 帳簿の受け渡し（エクスポート → 相手のインスタンスへ取込 → 編集中ロック）
- 帳簿ごとのアクセス制御・暗号化

## Decisions

### D1. 対象帳簿の指定は「ヘッダ → クエリ → 1冊なら暗黙 → 400」の4段

**採用**: 解決順を次の1本に決める。

```
1. X-Book-Id ヘッダ            … 通常の API 呼び出し（api.ts の共通ラッパが付与）
2. ?bookId= クエリパラメータ    … ブラウザネイティブの GET（/api/export・証憑ダウンロード）
3. 帳簿が1冊だけなら、その帳簿  … 単一帳簿運用・curl・既存の取込スキルが無改造で動く
4. いずれも無く2冊以上 → 400   … どの帳簿か推測しない
```

3 段目があることで、**1冊しか持たない利用者と既存の取込スキルは何も変わらない**。
4 段目は「黙って確定しない・黙って落とさない」と同じ思想で、**曖昧なら止める**。
存在しない bookId を指定した場合は 404（他人の帳簿を探る文脈がないため情報隠蔽はしない）。

**却下した案**:

- *サーバがプロセスグローバルに「選択中の帳簿」を保持し、`POST /api/books/:id/select` で切替*
  → プロセス全体の可変状態になる。タブを2枚開いた場合・MCP クライアント・取込スキルが
  同時に別の帳簿を触ると壊れる。特に**長時間の取込中に切替が起きると別の帳簿に書き込む**。
- *パスに埋める（`/api/books/{id}/entries` …）*
  → 93 箇所のルートすべてに波及し、`/skill` 側の契約も変わる。得るものが D1 と同じで代償が大きい。
- *選択中帳簿を Cookie に持つ*
  → ネイティブ GET も解決できて魅力的だが、認証を消したばかりの設計に「サーバが覚えている
  暗黙の状態」を再導入することになる。クエリで足りる。

### D2. `books` テーブルは最小限にする

```
books: id (ULID, PK) / name (notNull) / createdAt / updatedAt
```

`users` の `displayName`・`email`・`status` は引き継がない。帳簿に停止状態はなく、
事業者名・氏名は data plane の `business_settings` が正（control plane に二重に持たない）。

自動作成される最初の帳簿の名前は `マイ帳簿`。改名できる。

`backup_status.user_id` → `book_id`（外部キーを張り替え）。列の入替を伴うため
SQLite では新テーブル作成＋コピー＋差し替えになる。

### D3. `src/auth/` を廃止して `src/books/` にする

```
src/auth/provision.ts   → src/books/resolve.ts     帳簿の解決・初回作成
src/auth/middleware.ts  → src/books/middleware.ts  D1 の解決順を実装
                        + src/http/books.ts        一覧・作成・改名
```

認証が無くなった以上 `auth/` という名前は嘘なので、rename と同時に畳む。

### D4. 帳簿の削除 API は提供しない

削除は**不可逆で、消えるのは税務データ**である。UI に置くと誤操作の余地が生まれる一方、
必要な場面（顧問契約の終了など）は年に数回で、`$DATA_DIR/books/{id}.sqlite` と
`books/{id}/` を手で消せば済む。[[local-access]] で引いた「取り消せない操作は委任しない」
と同じ線引きをここにも適用する。

### D5. 既存の開発データは移行せず破棄する

実運用データが存在しないため、移行スクリプトを書かない。`$DATA_DIR` を作り直す。
破棄前に中身（帳簿数・仕訳件数）を提示してから消す。

**代償**: 既存のエクスポート zip は新レイアウトへそのままリストアできない。実データが無いので許容する。

### D6. rename は「境界から型で押し出す」

`config.ts`（パス）→ `db/router.ts`（`bookDb`）→ `books/middleware.ts`（`c.set('bookId')`）
の順に改名し、あとは `tsc` が壊れた箇所を全部指してくれる状態にする。
server の 511 テストが安全網になる。1コミットで完結させる（中途半端な状態を残さない）。

`AuthVariables { userId }` → `BookVariables { bookId }` も同時に行う。変数名だけ `userId` で
残すと、次に読む人が「ユーザーとは？」を再発見することになる。

## Risks / Trade-offs

- **[ULID ガードを bookId へ移し忘れる]** → 証憑アップロードとエクスポートが 500 になる。
  過去に踏んだ罠。`attachments/storage.ts` と `ops/export*.ts` を明示的にタスク化し、
  非 ULID の bookId を弾くテストを残す。
- **[`X-Book-Id` を付け忘れた経路が 1冊のうちは動いてしまい、2冊目で初めて壊れる]**
  → D1 の 3 段目が両刃。`api.ts` の全 77 箇所を共通ラッパへ寄せ、生 `fetch(` が
  api.ts に残っていないことを検査する（`credentials: 'include'` の除去と同じ置換で行う）。
  さらに **2冊ある状態での E2E** を仕上げに入れ、暗黙解決に隠れたままにしない。
- **[ネイティブ GET の 2 箇所で `?bookId=` を付け忘れる]** → 2冊以上のとき 400 になる。
  エクスポートと証憑表示は仕上げの手動確認に含める。
- **[取込スキルが 2 冊環境で 400 になる]** → 仕様どおりだが、スキル側のエラーメッセージが
  不親切だと詰まる。400 のボディに「利用可能な帳簿の id と name」を含め、
  スキルが人へ提示できるようにする。
- **[backup/restore が旧 `users/` ディレクトリを見に行ったまま静かに 0 件成功する]**
  → data-ops には「DATA_DIR 誤設定（control.sqlite 不在）は非0終了」がすでにある。
  加えて**帳簿0冊のバックアップも失敗として扱う**（偽の成功を作らない）。

## Migration Plan

1. `books` テーブルと `backup_status.book_id` のマイグレーションを生成
2. `config.ts` → `db/router.ts` → `books/` の順に改名し、`tsc` が黙るまで追従
3. `http/books.ts`（一覧・作成・改名）と D1 のミドルウェアを実装
4. web: 共通ラッパ導入（`credentials: 'include'` 除去と同時）→ 帳簿切替 UI → 設定画面の作成・改名
5. `$DATA_DIR` を作り直し、起動 → 1冊目自動作成 を確認
6. **2冊目を作って**切替・暗黙解決の失効（400）・エクスポート・証憑を確認
7. docs（architecture §4/§5/§12.1・data-model §1・PRD・CLAUDE.md・openspec config）

**ロールバック**: 実データが無いため、revert してもう一度 `$DATA_DIR` を作り直せばよい。

## Open Questions

- **帳簿を切り替えたとき web の画面状態をどこまでリセットするか**（選択中の会計年度・開いている元帳・
  絞り込み条件）。全リセットで始めて、煩わしければ後から緩める。実装時に決める。
- **MCP サーバ（後続 change）がどう帳簿を指定するか**。D1 のヘッダをそのまま使えるはずだが、
  MCP のツール引数として `bookId` を明示的に取る方が LLM には扱いやすいかもしれない。④ で決める。
