## Context

動機と選択肢の比較は proposal.md を参照。設計を決めている現状は次の4つ。

- **`lib.mjs`（302行）が既に接合面になっている。** サイトスクリプト5本（1166行）が使う巡回 API は
  `goto` / `evaluate` / `locator` / `getByRole` / `getByText` / `screenshot` / `waitForTimeout` / `url` /
  `content` など **14種**しかない。巡回手順そのものを書き直す必要はない。
- **`SEL` は既に宣言的な較正ポイントとして各スクリプト冒頭に分離されている。** データへの外出しは
  構造の変更ではなく、置き場所の変更で足りる。
- **失敗アーティファクト**（どの手順で・どの URL で・画面がどうだったか）を残す仕組みが既にある。
  診断の材料は揃っていて、置き場所と取り出し口だけが足りない。
- **巡回スクリプトはリポジトリの中にある。** アプリからも使うようになるため、**同じ手順を2箇所に
  持たない構成**が要る。

## Goals / Non-Goals

**Goals:**

- サイト固有の巡回手順を**書き直さずに**アプリへ載せる。
- 較正（サイト改変への追随）を**アプリの更新なしに**回せる状態を保つ。
- Claude Code + スキルの経路を残す（開発時の較正と、較正では直らない深い修復に要る）。
- 明細の本体をアプリの外へ出さない。

**Non-Goals:**

- Playwright 互換の完全な再現。使われている14種が動けばよい。
- 5サイト同時の移行。殻を1サイトで実証してから広げる。
- 手動 CSV 取込の廃止。反自動化に対するフォールバックとして残す（既存方針）。

## Decisions

### D1. 巡回コアを `packages/acquisition` へ切り出し、実行殻を2つ持つ

**採用**: サイトスクリプトと `lib` をパッケージ化し、アプリとスキルの**両方がそこを参照する**。

```
packages/acquisition/
  sites/{amazon,rakuten,mufg,shinsei,ufjvisa}.mjs   ← 巡回手順（サイト固有）※唯一の実体
  runtime/playwright.mjs   ← 実行殻A: 開発・スキル経路（現状の lib.mjs 相当）
  runtime/electron.mjs     ← 実行殻B: アプリ内（新規・200〜400行）
  bin/scrape.mjs           ← CLI（スキルが叩く薄いラッパ）
```

`.claude/skills/acquisition/scripts/scrape-<site>.mjs` は CLI を呼ぶだけにする。
**巡回手順の実体が1つしかない**ので、較正やページ構造の知見が片方に取り残されない。

**代替案**: アプリ側に巡回手順を複製する。→ 却下。サイト改変のたびに2箇所を直すことになり、
必ず片方が腐る。

### D2. 実行殻の対応関係

| 共通 API | Electron 実装 |
|---|---|
| `goto` | `webContents.loadURL` |
| `evaluate` | `webContents.executeJavaScript` |
| `url` / `content` | `getURL` / 同上を経由して取得 |
| `screenshot` | `capturePage` |
| `waitForTimeout` | タイマ |
| `locator` / `getByRole` / `getByText` | **ページ内で解決する式へ変換し、ポーリングで待つ** |

厄介なのは最後の1行だけ。Playwright の locator は「見つかるまで待つ」意味論を持つので、
**同じ意味論をポーリングで再現する**（見つかる／可視になる／クリックできるまで有限時間待ち、
尽きたら失敗として診断を残す）。ここが再現の要で、最初の1サイトで実証する対象でもある。

### D3. 較正データは「同梱を既定・`$DATA_DIR` で上書き」

```
配布時の較正（アプリ同梱・読み取り専用）
        ▲ 復帰できる
$DATA_DIR/acquisition/selectors/<source>.json  ← あれば優先。更新はここへ書く
```

- 更新は**データのみ**を受け付ける（文字列・正規表現の文字列表現・列名など）。zod で形を検証し、
  関数・コード片に相当するものは弾く。**銀行のログイン済みセッションを持つブラウザで
  任意コードが動く形は作らない。**
- 壊れた較正から戻せるように、上書きの削除＝同梱較正への復帰とする。
- 較正には版を持たせ、投入した仕訳の `policyRef` と同じ発想で「どの較正で取ったか」を残す。

### D4. 取込は分類を待たない（draft を先に並べる）

```
 開始 ─▶ ログイン待ち ─▶ 取得中 ─▶ 完了（draft が帳簿に並ぶ）
            │              │
            └──────────────┴──▶ 失敗 / 中断
```

**取り込んだ時点で draft として帳簿へ並べる。** 科目が決まっていない明細は未確定勘定の draft になり、
分類は後から当てる（D5）。ジョブが持つのは進行の記録だけで、明細は持たない。

- 進行中の巡回はアプリのプロセスに紐づく（アプリ終了で消える）。中断した巡回を再開する仕組みは
  持たない（取り直せばよい。冪等なので二重計上しない）。
- 同一連携サービスの二重起動は拒否する（進行中のジョブを返す）。

> **方針転換（実装後）**: 当初は「分類が返ってから importer へ流す」設計にし、分類待ちの明細を
> `$DATA_DIR/acquisition/jobs/*.json` に貯めていた。実際に動かして2つの問題が出た。
>
> 1. **取り込んでも帳簿に何も現れない。** 分類が返るまで人にできることが無く、
>    「取り込めたのか」を画面から判断できない。
> 2. **会計データを帳簿の外に置くことになる。** 取得済み明細は仕訳の材料そのものなのに、
>    data plane の外の JSON に、7日で黙って捨てる TTL 付きで置かれていた。
>    エクスポートにもバックアップにも入らない場所に、消えたら取り直しになるものを置いていた。
>
> importer は元々「科目未指定 → 未確定勘定の draft ＋ unresolved 件数」を持っている。
> 先に投入すれば、この2つは同時に消える。**既にあった仕組みを使わずに、外側に似た仕組みを
> 作りかけていた**のが誤りだった。分類待ちの置き場所ごと廃止する。

### D5. 分類は「未確定 draft に科目を当てる」操作

分類はジョブに属さない。**未確定勘定の draft** に対する操作にする。これにより:

- 人が UI で当てても、[[mcp-server]] 経由で AI が当てても、**同じ draft に対する同じ操作**になる。
- CSV 取込・手入力で生じた未確定にも同じ操作が効く（巡回だけの仕組みにしない）。
- 分類が返らなくても取込は完結している。会話が途切れても失うものが無い。

外へ出すのは `{ id, text }` の配列だけ（`text` は品名または摘要）。同じ文字はまとめるので、
会話が消費する量が**取込件数ではなく品目の種類数**に比例する。

`id` は **`text` から決まる短いダイジェスト**にする。連番にすると「何番目か」が一覧の中身に依存し、
人が先に何件か片付けただけで番号がずれて**別の取引に当たる**（会計データを壊す）。
ダイジェストなら、アプリ側に対応表を持たずに、いつ返ってきても同じ文字に当たる。
`text` から決まる値なので、クライアントが既に持っている情報以上のものを渡すことにもならない
（＝単体では取引を特定できない、を満たす）。

適用は既存の `updateLineAccount` を通す（draft 限定・科目変更時の税区分再解決の権威はそこにある）。
確定済みには当たらない。既に人が片付けていた対象は「適用0件」として返し、失敗にしない。

確定履歴の参照（`/skill/classification-history/lookup`）は**アプリ側で引いて添える**。
外部クライアントに履歴を取りに行かせない（往復が減り、履歴が外へ出る範囲も絞れる）。

### D6. 投入は既存 importer をそのまま通す

期間ゲート・冪等（出現インデックス方式）・科目検証・クリアリング連鎖は**一切書き直さない**。
アプリ内巡回は同一プロセスなので HTTP を経由せず importer を直接呼べるが、**通る検証は同じもの**とする
（`/skill/*` のハンドラと同じ入力検証・同じ importer 関数を共有する）。
「経路が違っても結果が同じ」を保つのはここ。

### D7. 巡回セッションは会計データと分けて置く

Electron の永続セッション区画（`userData` 配下）に置き、`$DATA_DIR` の会計データとは物理的に分ける。
エクスポート・バックアップの対象に含めない。破棄の導線を用意する。
これは既存方針（`architecture.md` §12.0「会計データは必ず `data/` に隔離する」）の裏返しで、
**秘密は会計データ側に持ち込まない**。

### D8. サイトの載せ順

1. **`card_mufg_visa`** — 最も単純（残高列なし・Σ利用＝請求額）。**殻の実証に最短**。
2. **`bank_ufj`** — Angular SPA で最も壊れやすい。**較正の外出しと診断ループの実証**になる。
3. `bank_shinsei` / `amazon` / `rakuten` — 同じ殻に載せる作業。

## Risks / Trade-offs

- **`locator` の自動待機を忠実に再現できない** → 1サイト目で実証し、再現できない意味論が見つかったら
  そのサイトスクリプト側を明示的な待機へ書き換える（殻の抽象を歪めない）。
- **反自動化に弾かれる** → **実サイトで確認済み（2026-08-13・5サイト）**。想定していた「自動化ツールだから
  弾かれる」形（captcha・拒否ページ）は**どのサイトでも起きなかった**。弾かれた場合に手動 CSV 取込が
  残るという退路も変えていない。

  ただし**予期しない形の妨げが1つあった**。Amazon の適格請求書リンクだけが Electron 殻で配られず、
  captcha も拒否ページも出ないまま**中身だけ静かに欠ける**（最悪 0/22 注文）。原因は Electron の
  既知バグ（[electron#34762](https://github.com/electron/electron/issues/34762) /
  [#30201](https://github.com/electron/electron/issues/30201)・2022年から open）で、
  `setUserAgent()` が **UA 文字列しか変えず** User-Agent Client Hints を更新しないこと。
  「UA は `Chrome/150` と名乗るが `userAgentData.brands` に `Google Chrome` が無い」という
  不整合が残り、機微な書類の配信で見られていた。CDP `Emulation.setUserAgentOverride` に
  `userAgentMetadata` を添えて UA と辻褄を合わせ、20/22 まで回復（`applyClientHints`）。

  **学び**: 反自動化は「弾かれる／通る」の二値ではなく、**静かに一部だけ欠ける**形を取りうる。
  自己検算（Σ・残高チェーン・突合）が無ければ、欠けたことに気づかないまま帳簿へ入っていた。
  検算を必須にしている設計がここで効いた。
- **較正では直らない改変（巡回手順そのものの変化）** → アプリの更新が要る。これは受け入れる。
  診断に「較正では直らない」と判別できる情報を含め、無駄な較正更新を繰り返させない。
- **巡回ウィンドウが会計データを扱うウィンドウと同居する** → 巡回ウィンドウは外部サイトを開くので、
  アプリの内部 API に到達できない隔離設定にする（同一オリジンにしない）。
- **ジョブ状態が増えて複雑になる** → 状態を5つに固定し、増やさない。中断した巡回の再開は持たない。
- **切り出しでスキル経路が壊れる** → D1 の切り出しを最初のタスクにし、**巡回の挙動を変えない状態で**
  現行スキルが従来どおり動くことを確認してから殻を足す。

## Migration Plan

1. `packages/acquisition` へ切り出す。**この時点では挙動を変えない**。既存スキルが従来どおり動くことを確認。
2. 較正データを `$DATA_DIR` 側で上書きできるようにする（Playwright 殻のまま検証できる）。
3. Electron 殻を実装し、`card_mufg_visa` を載せて Playwright 殻と同じ結果になることを突き合わせる。
4. ジョブモデル（進行の記録のみ）、UI の進行表示、MCP ツールを足す。
5. `bank_ufj` を載せ、較正の更新と診断のループを実サイトで一周させる。
6. 残る3サイトを載せる。

ロールバックは各段階で可能。3以降が失敗しても、スキル経路（Playwright 殻）は動き続ける。
