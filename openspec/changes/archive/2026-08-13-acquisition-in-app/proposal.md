## Why

連携サービスの取込は今、`.claude/skills/acquisition/scripts/scrape-*.mjs` を **Bash から実行する**ことで
成り立っている。Claude Desktop には Bash もファイルシステムもないため、[[mcp-server]] を入れても
**取込だけは動かない**。取込は本アプリの中心価値なので、ここが欠けたままでは人に配れない。

置き場所の選択肢は実質2つしかなく、どちらも巡回コードをアプリ側へ寄せる方向を指す。

- `.mcpb` に同梱する → Chromium を二重に持つ（アプリは既に Electron）か、Chrome のインストールを要求する。
- **Electron に内蔵する** → Chromium は既にある。Chrome 非導入のマシンでも動く。

さらに副次的な効果として、**明細データが会話のコンテキストを往復しなくなる**。
今は数百明細ぶんの金額・注文ID・証憑参照まで AI が持ち運んでいるが、分類に本当に必要なのは品名だけ。

失うものが1つある。**サイト改変時の自己修復ループ**（AI が `SEL` 較正ポイントを直す）は、
コードがアプリのバイナリに入ると成立しない。これは `SEL` を**コードからデータへ外出しする**ことで取り戻す。

## What Changes

- **巡回を Electron 内に実装する**。`BrowserWindow` を人が見える状態で開き、ログイン・2FA は従来どおり人が入力する。
  自動化レベルの原則（無人実行しない・認証情報を AI に持たせない）は変えない。
- **既存のサイトスクリプトを活かす**。`lib.mjs` が既に接合面になっており、サイト側が使う API は
  `goto` / `evaluate` / `locator` / `getByRole` / `getByText` / `screenshot` / `url` / `content` など**14種**しかない。
  ここに Electron 実装を1本足す形にし、サイト固有の巡回手順は書き直さない。
- **`SEL`（サイト較正ポイント）をコードからデータへ外出しする**。アプリは `$DATA_DIR` 側の較正データを読み、
  コードは固定。セレクタの修復が**アプリの更新なしに**行える状態にする。
- **非同期の取込ジョブとして扱う**。ログイン待ちを含むと数分かかるため、開始と状態問い合わせを
  分けた進行モデルにする。UI からも [[mcp-server]] からも同じジョブを起動できる。
- **取り込んだ時点で draft として帳簿へ並べる**。科目が決まっていない明細は未確定勘定の draft になり、
  分類は**後から当てる**。分類を待たせない＝取込と分類を切り離す。
- **分類は「未確定の draft に科目を当てる」操作**にする。人が UI で当てても、[[mcp-server]] 経由で
  AI が当てても同じ draft に効く。CSV 取込・手入力で生じた未確定にも同じ操作が効く。
- **分類のために外へ出すのは品名・摘要だけ**にする。金額・注文ID・残高・証憑参照はアプリ内に留める。
- **失敗診断と較正の更新をツールとして露出する**。失敗時の手掛かり（どの手順で・どの URL で・
  ページがどうなっていたか）を返し、較正データの更新を受け付ける。**受け取るのはデータのみで、
  実行されるコードは受け取らない**。
- **1サイトずつ載せる**。まず `card_mufg_visa` で殻を実証し、次に `bank_ufj`（SPA で最も壊れやすい＝
  修復ループの実証になる）、残る `amazon` / `rakuten` / `bank_shinsei` を同じ殻に載せる。
- **Claude Code + 既存スキルの経路は残す**。開発時の較正と、較正データでは直らない深い修復に要る。

### Non-goals

- **無人・全自動の実行**（cron 等）。2FA と CAPTCHA に人が要る前提を変えない。
- **draft の自動確定**。取込結果は従来どおりすべて draft で、承認は人が UI で行う。
- **AI にコードを書かせて実行すること**。較正はデータの更新に限る。銀行のログイン済みセッションを
  持つブラウザで任意コードが動く形は作らない。
- 認証情報をアプリや AI に保持させること（人が実ブラウザに入力する原則は不変）。
- 検算規約・冪等・期間ゲートの変更（取得経路が変わっても契約は同一）。

## Capabilities

### New Capabilities

- `acquisition`: アプリ内で行う連携サービスの巡回。取込ジョブの進行と中断、人のログインを待つ扱い、
  取得結果の自己検算、外へ出す情報の範囲、較正データの外出しと更新、失敗時の診断。

### Modified Capabilities

- `mcp-server`: 書き込みの範囲を拡張し、取込ジョブの開始・状態問い合わせ・**未確定 draft の分類**・
  較正データの更新を露出する。draft を確定しない原則は維持する。
- `web-app`: 設定・連携サービスの画面から取込を開始でき、進行状況と結果（受理・重複・期間外・未確定）を
  提示する。取り込んだ draft はそのまま確認待ちの一覧に並ぶ。

> `mcp-server` は先行する change で導入される。本 change はその後に適用する。

## Impact

- **変更**: `packages/desktop`（巡回用ウィンドウとセッション、Electron 版の巡回ランタイム）、
  `packages/server`（取込ジョブの状態管理・較正データの読み書き・既存 importer への接続）、
  `packages/mcp`（取込ツールの追加）、`packages/web`（取込の開始と進行表示）
- **移設**: `.claude/skills/acquisition/scripts/*.mjs` の巡回手順をアプリ側から利用できる形へ。
  スキル側の経路は残すため、**同じ手順を2箇所に持たない**構成にする（design で扱う）
- **新規データ**: `$DATA_DIR/acquisition/`（較正データ・失敗時の手掛かり・巡回セッション）。
  巡回セッションはパスワード級の秘密で、同期・バックアップの対象にしない
- **既存契約は変更しない**: `/skill/*` の req/res（[docs/ec-import-api.md]・[docs/bank-import-api.md]）、
  検算規約、冪等（出現インデックス方式）、期間ゲート
- **docs**: `acquisition-skill-spec.md` §2.5（取得経路）に Electron 経路を追記、`architecture.md` §9
- **未検証**: Electron の `BrowserWindow` が銀行サイトの反自動化に対してどう振る舞うか（Playwright の
  CDP 経由より有利な可能性があるが確証はない）、`locator` 相当の自動待機をどこまで忠実に再現できるか
