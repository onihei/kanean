## Context

動機は proposal.md「Why」を参照。設計上効く現状は次の4つ。

- **ソケットは実装済み**（`packages/desktop/src/socket.ts`）。`honoApp.fetch(request)` をそのまま流すので、
  UI が使う `/api/*` も `/skill/*` も同じ経路で届く。**接続の土台は既にある。**
- **`/skill/*` は既に「AI エージェント向けの中間契約」として設計されている**（zod 検証・期間ゲート・冪等・
  科目解決の権威がサーバ側）。ブリッジがその権威を持ち直す必要はない。
- **HTTP ルートは 128 本ある。** 機械的に写像するとツール定義がコンテキストを圧迫し、モデルの選択精度が落ちる。
- **Claude Desktop のスキルは使えない。** スキルのコード実行は Anthropic 側のサンドボックスで行われ、
  利用者のマシンの `kanean.sock` に到達できない。ローカルで動くのは MCP サーバプロセスだけ。

## Goals / Non-Goals

**Goals:**

- ブリッジに**会計ロジックを一切置かない**（既存 API の合成に徹する）。`packages/server` は原則無変更。
- **利用者が導入するものを2つに抑える**（Kanean.app と MCP バンドル）。設定ファイルの手書きをゼロにする。
- 「何ができるか」だけでなく**「次に何をすべきか」を返り値で伝える**。
- Claude Code + 既存スキルの経路を壊さない（併存）。

**Non-Goals:**

- ツールの網羅性。読み取りの主要動線が通ればよく、あとから足す。
- MCP クライアント非依存の抽象化。当面 Claude Desktop に合わせ、必要になってから一般化する。
- 取込の実行（次 change）。本 change は連携サービスの**登録**まで。

## Decisions

### D1. 手順知識も MCP 側に畳み、スキルは併用しない

**採用**: MCP バンドル1つに、ツール・prompts・返り値の誘導をすべて含める。

Claude Desktop のスキルは ①ローカルソケットに到達できない ②Pro 以上＋コード実行の有効化が要る
③導入物が2つになる、の3点で不利。手順知識は「prompts」と「返り値の `nextActions`」で運べるので、
スキルに依存する理由がない。

**代替案**: スキル（手順）＋ MCP（道具）の2枚構成。→ ①の到達性で成立しない。

### D2. 新パッケージ `packages/mcp` = stdio ⇄ unix socket の薄いブリッジ

**採用**: `@modelcontextprotocol/sdk` の stdio サーバ。ツール呼び出しを既存 HTTP へ変換して返すだけ。
DB にも `packages/core` にも触れない。

理由: 権威（検証・期間ゲート・冪等・帳簿解決）は既にサーバ側にある。ブリッジが状態や判断を持つと
**同じ規則が2箇所に分かれて必ずずれる**。会計の正しさに関わる分岐はブリッジに書かない。

**接続先は既定でローカルソケットのみ**とする（`KANEAN_SOCKET` → 既定パス）。ソケットが無ければ
「アプリ未起動」と判別し、**TCP ポートを探しに行かない**。

既存スキル（`SKILL.md`）は socket が無ければ `127.0.0.1:10140` へ落ちるが、あれは開発リポジトリの中で
動く前提の規約である。利用者へ配るバンドルが暗黙にポートを探すと、①デスクトップ版は TCP を開かない
という設計と食い違って見え、②別プロセスがそのポートを掴んでいた場合に誤接続しうる。
開発時は `KANEAN_BASE_URL` を**明示したときだけ** TCP 経路を使う（`localhost` は `::1` に
解決され得るので `127.0.0.1` を使う）。

補足として、`127.0.0.1:10140` は `packages/server/src/index.ts` の `serve()` ＝
`pnpm --filter @kanean/server dev` の入口にのみ存在する。デスクトップ版（`packages/desktop`）は
`serve()` を呼ばず、`protocol.handle` とソケットに `honoApp.fetch` を流すだけなので TCP を開かない。

### D3. 配布は `.mcpb`（MCP Bundle）単一ファイル

**採用**: `mcpb` CLI で `manifest.json` ＋ サーバ実装を1ファイルに固め、配布物に同梱する。
設定画面の導線は**それを書き出して Finder で見せるだけ**。

**代替案**: アプリが `claude_desktop_config.json` を直接書き換える。
→ 却下。他アプリの設定ファイルを勝手に編集するのは行儀が悪く、フォーマット変更に追従し続ける必要があり、
既存のエントリを壊すリスクを負う。**利用者のドラッグ1回で済むなら、そちらが安全。**

### D4. アプリ未起動 = 確認してから起動（探索の案C）

**採用**: ソケットの不在で「未起動」と判別 → 起動してよいか確認 → `open -a` 相当で起動 →
到達可能になるまで待つ → 元の呼び出しを**1回だけ**再試行。

- 黙って起動しない: 会話の副作用で GUI が立ち上がるのは驚きになる。
- 待ちは有限で打ち切る。**別ポートを探して代替しない**（既存スキルの原則と同じ）。
- 常駐化はしない。[[desktop-app]]「自動起動しない」は**ログイン時の自動起動**の禁止であり、
  利用者が承諾した起動はこれに当たらない。

### D5. ツールは「意味のある動詞」12本前後。ルートを写像しない

**採用**: 読み取り10本 + 書き込み1本 + 現在地1本を目安に始める。

| 区分 | ツール（目安） |
|---|---|
| 現在地 | 帳簿・会計年度・アプリモード・承認待ち件数をまとめて返す1本 |
| 読み取り | 試算表 / PL / BS / 元帳 / 補助元帳 / 仕訳検索 / 科目残高 / 納税予測 / 連携サービス一覧 |
| 書き込み | 連携サービスの登録のみ |

- 「7月末の売掛金」は `/reports/trial-balance?from&to` の合成で出せる。**サーバに新エンドポイントを足さない。**
- 「現在地」はサーバ側の複数 API をブリッジが束ねる（`books` + `fiscal-years` + `app-mode` + draft 件数）。
  これは会計判断を含まない単純な合成なので D2 に反しない。
- **ツール名には `kanean_` 接頭辞を付ける。** クライアントは複数の MCP サーバを繋ぐため、
  名前空間の衝突を避ける必要がある。なお利用者が発話で「kanean」と言う必要はない
  （モデルがツール一覧から選ぶ）。
- **露出範囲と到達性境界は別問題**。ソケットは `/api/*` 全体を通す（[[local-access]]）が、
  ツールとして露出する動詞は絞る。前者は防壁、後者は使いやすさと事故防止の問題。

### D6. 手順知識は prompts と `nextActions` に置く

ツールの説明文は「何ができるか」しか伝えない。順序・前提・禁止事項は伝わらない。効く順に：

1. **返り値の `nextActions`** — 最も効く。前提不足なら選択肢を返す（`book_required` が既にこの形）。
2. **prompts** — 「今月の状況」「決算前チェック」を入口として配る。スキルと違い**アプリと一緒に配布できる**。
3. **ツール説明** — 最小限。「これは `get_context` の後に呼ぶ」程度に留める。

### D7. 承認は UI に残し、深いリンクで戻す

ツールは draft を確定しない（[[skill-import]]「黙って確定しない」）。代わりに `kanean://` のリンクを返し、
アプリを前面に出して該当画面を開く（`app.setAsDefaultProtocolClient`）。**リンクは画面遷移のみを担い、
変更操作を実行しない**（リンクを開くだけでデータが変わる状態を作らない）。

なお `protocol.handle('kanean', …)` は既にあるが、あれは**アプリ内配信**の仕組みで、OS レベルの
リンク受理とは別。両者が同じスキームを共有する点は実装で切り分ける。

### D8. ランタイムは同梱しない（ホストが供給する）— 実装で確定

**採用**: `server.type: "node"` として **Node ランタイムは同梱しない**。依存だけを esbuild で
1ファイルに畳む（**実測 104KB**）。

当初は「まず同梱で作り、サイズが問題になったら見直す」としていたが、実装時に確認したところ
**Claude Desktop が macOS / Windows 向けに Node ランタイムを同梱しており、利用者側に Node は要らない**
（[MCPB のドキュメント]）。同梱すべきランタイムは最初から無かった。
これで mcp-server spec「追加のランタイムを要求しない」はホスト側で満たされる。

`node_modules` を丸ごと同梱する案は採らない。pnpm の symlink を実ファイルへ展開する手間がかかり、
成果物も桁違いに大きくなる。ブリッジは HTTP と JSON しか触らないので、静的に畳んで困らない。

**プラットフォームは `darwin` のみ宣言する。** 起動が `open -a`（macOS）に依存しており、
Windows では未起動時に起動できないため。動く範囲だけを名乗る。

### D9. バンドルの書き出しは desktop 専用の HTTP ルートで行う

**採用**: `packages/desktop` が `createApp()` の Hono に `/api/desktop/*` を追加登録し、
設定画面はそこを叩く。書き出し（`resources` → 利用者に見える場所へコピー）と
Finder での提示（`shell.showItemInFolder`）は Electron 側にしか無いため。

**代替案**: preload + IPC を足す。→ 却下。アプリは現在 preload を持たず、UI との通信は
すべて HTTP に一本化されている。ここだけ別の通信面を増やすと、web が「どちらの経路か」を
意識することになる。

副次的な利点として、**開発時（Vite + server 単体）には自然に 404 になる**。
設定画面はそれを見て「デスクトップ版で操作してください」と案内でき、
「押せるのに何も起きない」状態を作らずに済む。

## Risks / Trade-offs

- **ツールが増え続けてコンテキストを食う** → 上限（目安12本、多くても20本）を design の約束として置き、
  増やすときは「既存を統合できないか」を先に検討する。
- **`.mcpb` / prompts の仕様がクライアント側で変わる** → ブリッジ本体（ツール実装）とパッケージングを
  分けておき、フォーマット変更がツール実装に波及しないようにする。
- **ソケット経由では `/api/*` 全体に到達できる** → ツールを絞っても、ソケットを直接叩けば何でもできる。
  ただしこれは**既存の到達性境界のままであり、本 change で緩めていない**。防壁は「同一マシンで
  アプリが起動していること」であって、ルート単位の制限ではない（[[local-access]]）。
- **深いリンクが外部から開かれうる** → 画面遷移のみに限定し、未知の経路は初期画面へフォールバック。
- **Claude Desktop のプラン要件** → Pro 以上を前提とすることは合意済み。配布時の案内に明記する。
- **利用者が「AI が勝手に会計処理をした」と感じる** → 書き込みを連携サービス登録に限り、
  結果には必ず件数と次の一手を添える。

## Migration Plan

1. `packages/mcp` を追加し、開発時の `127.0.0.1` 経路で動作確認（アプリのビルドを待たずに始められる）。
2. デスクトップ経路（ソケット）へ切り替えて同値であることを確認（[[local-access]]「経路によらず同一」）。
3. プロトコルハンドラ登録と設定画面の導線を足す。
4. `.mcpb` を作り、配布物へ同梱。素の Claude Desktop に導入して疎通を確認する。

ロールバックは**バンドルを削除するだけ**。アプリ本体は MCP なしで従来どおり動き、
Claude Code + 既存スキルの経路にも影響しない。

## 実機で確かめたこと

- **発話に「kanean」は要らない。**「7月末の売掛金は？」（サーバ名を含まない）でツールが選ばれ、
  正しい数字が返った。探索段階で懸念していた「毎回 kanean と打つ必要があるか」は**杞憂**で、
  ツール名の `kanean_` 接頭辞は名前空間の衝突回避としてだけ働く（利用者は打たない）。
- 導入時にクライアント側の権限確認が出るが、「常に許可」を選べば以降は継続する。
  配布時の案内にこの一手を含めると迷わせずに済む。

## Open Questions

- MCP prompts が Claude Desktop の UI 上でどう見えるか（入口としてどれだけ発見されやすいか）。
  露出が弱ければ、D6 の重心を `nextActions` 側へ寄せる。
- 「現在地」ツールが返すべき情報の粒度。実際に会話させてみて、足りない/多すぎるを調整する。
- 承認待ちの件数を返す際、帳簿が複数あるときに全帳簿を横断して返すか、対象帳簿だけに絞るか。
- 開発時の TCP 経路（`KANEAN_BASE_URL` 明示時）は実 DB での同値確認をしていない。
  配布物が通らない経路なので優先度は低いが、開発でツールを使うようになったら確かめる。
