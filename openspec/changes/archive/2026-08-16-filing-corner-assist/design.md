# filing-corner-assist — 設計

## Context

動機は proposal.md（Why）を参照。前提となる現状:

- 申告値の組成は実装済み（[[tax-return]]）: `/api/tax-return/blue-statement`・`income-tax`・
  `consumption` が様式ボックス（[docs/form-mapping.md]）に対応づいた JSON を返し、PDF と同一の
  組成関数を共有している。filing はこの出力の**射影**であり、新しい計算を持たない。
- MCP ブリッジ（packages/mcp・.mcpb）は unix socket 経由で server API を呼ぶ。露出動詞の限定・
  版一致・定型手順の配布という規約が既にある（[[mcp-server]]）。
- AI 機能は「利用者の Claude サブスク側で動かし、アプリは API キーを持たない」方針。
  ブラウザ操作の能力（Claude in Chrome 等）もクライアント側にある。
- 証憑保存の機構（帳簿ごとのディレクトリ・メタ＋SHA-256）は [[attachments]] にあるが、
  仕訳（entries）紐付け前提。

## Goals / Non-Goals

**Goals**

- 転記値の「唯一の実体」を server が返す入力指示書に置き、AI・人のどちらが転記しても同じ源を使う。
- AI の関与を「写字」に限定する構造（指示書のみ・検算ゲート・認証と送信は人）をデータと手順の両面で強制する。
- アプリ単体（Claude なし）でもチェック → 手動転記 → 完了記録が完結する。

**Non-Goals**

- 作成コーナーの画面遷移をアプリが自動実行すること（実行殻・Playwright スクリプトは持たない）。
- e-Tax フル API・xtx・eLTAX・マイナポータル連携（将来 change）。
- 提出の有効性判定。「提出可能」の宣言はどの層でも行わない。

## Decisions

### D1. 転記手順は MCP の定型手順（prompt）として配布し、アプリは自動化エンジンを持たない

- 理由: 作成コーナーは毎年1月に作り直され、実行頻度は年1回。決定的スクリプト
  （acquisition の sites/ 方式）は「年1回しか動かないのに毎年壊れる」最悪の保守比率になる。
  画面を読んで適応するのはクライアント側モデルの仕事とし、アプリは正しい転記値と規約だけを供給する。
- 代替案: acquisition の実行殻に載せる（却下: 上記）。Claude 用スキルを別途配布
  （却下: [[mcp-server]] が追加導入物を禁じている）。
- 手順本文は packages/mcp 内のテンプレートとして持ち、内容に [[filing]] の転記手順の規約
  （指示書のみ・認証と送信は人・検算一致・不一致時は停止して差分報告）を織り込む。

### D2. 入力指示書は「画面グループ → 項目」のフラットな射影。欄対応は docs が正

- 形: `{ year, groups: [{ screen, items: [{ field, value, format?, note? }] }], checksum: {...} }`。
  `value` は円整数（Yen）または選択肢の文字列。`checksum` は所得税の申告納税額/還付額と
  消費税の国・地方・合計。
- 射影は `packages/core` の純関数（既存 organ の出力 → 指示書構造）。server は既存 organ を
  呼んで渡すだけ。これで「PDF・画面プレビュー・指示書の金額一致」がテストで固定できる。
- 様式ボックス → 作成コーナー欄の対応表は `docs/filing-corner-mapping.md` を新設して正とする。
  作成コーナーは年分でラベルが揺れるため、mapping には対象年分を明記し、乖離の吸収は
  手順側（画面を読む側）の責務とする。乖離が大きい場合は止まって報告（黙って推測しない）。

### D3. precheck は server 内の決定的チェッカー。判定は既存 organ の再利用で行う

- 貸借一致は試算表、青色控除・事業区分・控除入力は設定と `tax_return_inputs`、
  未確定 draft は件数クエリ。それぞれ blocking / warning と該当画面への deep link
  （既存のアプリリンク機構）を返す。
- 「提出可能」フラグは応答の語彙に存在させない（`issues: []` が最良の状態）。

### D4. 完了記録は data plane の新テーブル。添付は保存機構を共通化し、紐付けは別テーブル

- `filing_records`: 年分・税目（income_tax / consumption）・提出方法（corner_etax / paper / other）・
  提出日・受付番号・メモ。同一年分複数可（再提出・税目違い）。
- 添付は既存 attachments テーブルが**最初から polymorphic**（target_type / target_id）だったため、
  `target_type='filing_record'` で同テーブルに保持する（実装時に確認して当初案の別テーブルから変更）。
  ファイル保存・制約・ハッシュのロジックは `addAttachmentTo` としてサービス共通化し、
  対象行の存在検証だけ各ドメインが行う。ダウンロード・削除は既存 `/attachments/:id` ルートがそのまま効く。

### D5. MCP は読み取り2＋書き込み1＋prompt 1

- `filing_precheck`（読み）・`filing_instruction_sheet`（読み）・`filing_record_submission`
  （書き: 記録作成＋控え添付。ローカルファイルパスを受け取りブリッジが読んで送る）。
- 既存の版一致・帳簿解決・次の一手の規約に自動で乗る。削除ツールは作らない（UI のみ）。

### D6. 65万円控除への接続は「案内」まで

- e-Tax 提出（corner_etax）の完了記録が作られたら、web の確定申告画面で
  `qualifiesFor65` の設定確認への導線を出す。自動では変更しない（設定書き込みの非委譲と、
  年をまたぐ適用判定を機械が断定しないため）。

## Risks / Trade-offs

- [作成コーナーの年次改組で mapping が陳腐化] → mapping に年分を明記し、手順に「ラベル乖離時は
  停止して報告」を規約化。修正は docs と射影関数の小改修で済む構造にする。
- [AI の誤入力] → 転記値は指示書のみ＋送信前の検算一致ゲート（不一致なら送信に進まない・
  完了記録も作らない）。
- [控え PDF の取り違え・改変] → システムは事実の記録に徹し SHA-256 とメタを残す。内容の真正性は
  判定しない（[[attachments]] と同じ立場）。
- [クライアントにブラウザ操作能力が無い] → 指示書の手動転記（web 画面のコピー付き一覧）が
  常にフォールバックとして成立する。
- [長丁場のセッション切れ] → 手順に作成コーナーの途中保存（.data ファイル）での再開を織り込む。

## Migration Plan

- data plane マイグレーション追加（`filing_records`・`filing_record_attachments`）。既存テーブル変更なし。
- MCP バンドルは版一致規約により、アプリ更新後に設定画面から書き出し直す既存フローで配布される。
- ロールバック: 新テーブル・新ルート・新画面のみのため、変更の取り消しで既存機能に影響しない。

## Open Questions

- 対象年分（令和8年分）の作成コーナーの実画面確認は公開後（例年1月）にしかできない。
  mapping の初版は現行年分の画面と公開情報で書き、実地確認タスクを申告期に残す。
- 控え PDF をブラウザのダウンロードからどう受け渡すか（自動でパスを拾えるか、手動添付に倒すか）は
  クライアント能力依存。手動添付フォールバックがあるため実装時に決めてよい。
