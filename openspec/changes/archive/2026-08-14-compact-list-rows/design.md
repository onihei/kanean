## Context

動機と計測値は [proposal.md](./proposal.md) を参照。ここでは実装上の制約と選択だけを書く。

**幅の制約は Electron の既定ウィンドウが決めている。** `packages/desktop/src/main.ts:91` の
`width: 1280` から、`ServicesTab` の詳細ペインは 740px。`App.tsx:211` の `maxWidth: 1120` は
main の実幅 1060 より大きく、既定サイズでは発動しない。**幅を増やす方向の対策は既定サイズに効かない**
ため、行の中身を減らす以外に受入基準を満たす道はない。

**一覧はサーバ側で会計年度に閉じている。** `listDrafts(db, fiscalYearId, …)` /
`listEntries(db, fiscalYearId, …)` は `withOpenYear` 経由（`http/api.ts:324, 518`）で、
開いている会計年度1つに限定される。日付から年を省ける根拠はこの構造にある。

**ただし取込明細だけは閉じていない。** `listRawTransactions(db, status?)`
（`import/rawStatus.ts:48`）に年の条件は無く、`raw_transactions` に `fiscal_year_id` 列も無い
（`db/data/schema.ts:345`）。`executeRollover` は `fiscal_years` と `opening_balances` しか
触らない（`closing/rollover.ts:83`）ため、繰越後は過年度の行が残る。年を一律に省くと嘘になる。

## Goals / Non-Goals

**Goals:**

- 既定ウィンドウ 1280×860 で、対象2画面のどの行も意図しない折り返しを起こさない
- 折り返しを消す過程で情報を失わない（配置を変え、重複を消すだけ）
- 日付の年に関する規則を1つに統一し、会計年度に閉じている画面とそうでない画面の両方で正しく振る舞う

**Non-Goals:**

- 表示密度の一般解（デザイントークン化・全画面のテーブル正規化）。
  `docs/refactor-backlog.md` C3 の色トークン化と隣接するが、本 change では触らない
- 帳票系タブ（試算表・推移表・部門別）。既に `STICKY_TH` / 横スクロールで別の解を持つ
- 摘要が長い場合の一覧性の作り込み（省略記号＋`title` で一旦様子を見る）

## Decisions

### D1. 日付は「開いている会計年度と異なるときだけ年を出す」

年の省略を画面ごとに決めるのではなく、**行の日付と開いている会計年度を比較して決める**。

- 会計年度に閉じている画面（draft 一覧）では、結果的に常に `MM-DD` になる
- 閉じていない画面（取込明細）では、当年度は `MM-DD`、過年度だけ `YYYY-MM-DD` になる

**代案（採らない）**: 画面ごとに年の要否を固定する。実装は単純だが、取込明細で過年度の行が
`MM-DD` で当年度の行に紛れる。年を消した結果として過年度の行が**目立つ**ことは、
この規則の副産物ではなく採用理由の一つである。

整形関数は開いている会計年度を引数に取り、`packages/web/src/lib/format.ts` に置く。
会計年度は `Workbench` が既に保持している（`App.tsx:185` の `years` / `openFy`）ため、
新たな API 呼び出しは要らない。props で渡すか、既存の取得を各タブで再利用するかは実装時に決める。

### D2. `DraftRow` は grid ではなく「1行＋従属行」を保つ

現状の `flexWrap: 'wrap'` をやめ、主行は折り返さない構成にする。従属行（根拠行）は既存の
`origin.reason` 行を拡張し、税区分 select と税額をそこへ移す。

**代案（採らない）**: CSS Grid で常時2行の固定テンプレートにする。折り返し位置は揃うが、
情報量を減らさないため縦に伸びる。「例外ベースの取込レビュー」（[[web-app]]）は high を
一括確定して medium/low だけ精査する流れなので、**high の行に根拠も税区分も要らない**。
従属行を条件付きにできる前者の方が、仕様の意図に合う。

従属行を出す条件は `origin.reason` の有無を引き継ぐ（現行と同じ）。税区分を触りたいだけの行で
従属行が無いケースが出るため、そこは実装時に「reason が無くても税区分は出す」か
「従属行の開閉を行単位で持つ」かを選ぶ。**前者を既定とする**（開閉状態を持つと選択状態と
合わせて2つの行内状態を管理することになり、一括確定の選択と混乱する）。

### D3. `<select>` は幅を固定し、入力方式は変えない

`<select>` の閉状態は最長 option の幅になるため、勘定科目マスタが増えると行が広がる。
固定幅を与えれば、科目数と行の幅が切り離される。開いたドロップダウンは全文のまま。

**代案（採らない）**: コンボボックス化・検索付きピッカー。科目数が多いこと自体は
一般的な会計ソフトと同様で問題ではなく、幅は固定幅で解ける。入力方式の変更は別の判断。

### D4. 取込明細は `table-layout: fixed` にする

現状は `table-layout: auto` で幅指定も無いため、セル内で摘要が折り返して行高が可変になる。
`<colgroup>` で列幅を宣言し、摘要セルを `nowrap` + `ellipsis` + `title` にする。

口座/形式列（`accountRef / sourceType`）は行ごとにほぼ同じ値が並ぶが、**この画面には
サービスの絞り込みが無い**ため、見出しへ移す先が無い。列としては残し、幅だけ抑える。
（絞り込みを足すのは取込明細の会計年度スコープ化と同じ層の話なので、別 change に送る。）

### D5. `maxWidth` は上げるが、受入基準には含めない

既定サイズでは不活性なので、上げても受入基準の達成には寄与しない。ウィンドウを広げて使う場合に
のみ効く。1行の変更なので同梱するが、**これが効かないと収まらない実装は不可**とする。

## Risks / Trade-offs

- **税区分を従属行に移すと、触るのに視線移動が増える** → 例外ベースレビューでは medium/low を
  精査するときにしか触らない想定。頻度が高いと分かれば主行へ戻す（配置だけの変更なので安い）
- **摘要の省略で一覧性が落ちる可能性** → `title` で全文は残す。実際に使って気になったら
  折り返し許容の2行クランプ等を再検討する（利用者が明示的に「一旦これで様子を見る」と判断済み）
- **px の見積りが実測でない** → 受入確認は実アプリを既定ウィンドウで開いて目視する。
  見積り値ではなく「折り返さないこと」が基準
- **`DraftRow` と取込明細で日付整形の実装がずれる** → 整形関数を `lib/format.ts` に1つ置き、
  両画面から呼ぶ。純関数なのでテストを付ける（`packages/web` は現状テスト0件だが、
  `docs/refactor-backlog.md` C7 が「web の純計算を lib へ抽出してテスト導入」を挙げており、その方向と一致）
- **過年度行に触れるが直さない** → 取込明細の年スコープ化と `journalizeRow` の期間ゲート欠落は
  本 change の対象外。D1 により過年度行が**見えるようになる**ため、別 issue として起票済み

## Open Questions
